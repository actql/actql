# ARRAY-parameter membership from public query source

## Selected contract and counterexample

Baseline: `b089642827e7c354195ecfec79e5e0aa3fa532b2`.
GoogleSQL accepts `search_value [NOT] IN UNNEST(array_expression)`; its
[ordered membership rules](https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/operators#in_operator)
first distinguish an empty set, then a match, then unknown equality. The
existing common membership law already gives NULL containers the empty-set
meaning, distinct from an ARRAY containing a NULL item.

Before the repair, a hand-authored complete Program with `in`/`not_in` and
`{$param:"xs"}` passed ordinary checking with `xs=[2,null]`. The corresponding
`SELECT 2 IN UNNEST(@xs) AS included, 2 NOT IN UNNEST(@xs) AS excluded`
failed query parsing. The executed counterexample was 0/1 in `run-YOvSXR`;
the failure is at source parsing after the independent Program was checked.

## Implementation

The bounded query expression parser recognizes the unquoted UNNEST invocation
at IN's RHS, with one expression argument, ordinary precedence and source spans.
The lowerer passes that operand directly to the common `in`/`not_in` node. It
does not make a singleton literal list, duplicate evaluation, produce rows,
change authorization, or add another executor. Grouped ARRAY parameters retain
ordinary declarations and binding. Existing scalar IN lists remain unchanged.

The selected implemented subset is whole ARRAY parameters. General ARRAY-valued
expressions are parsed but remain refused by common Expression admission;
`expression_syntax/admission.mbt` permits only `literal` or `$param` at `InRight`.
For example, `amount IN UNNEST(xs)` and
`amount IN UNNEST(IF(TRUE,@xs,@ys))` reach `Admission(InvalidArguments)` in the
focused test. They are valid GoogleSQL coverage gaps, not permanent language
restrictions. No row-dependent expansion or frontend substitute is provided.
FROM UNNEST, ARRAY constructors, subquery membership and STRUCT comparison are
not added by this change.
