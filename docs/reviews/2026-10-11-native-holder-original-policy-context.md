# Original custody for the Remote Review policy

The installed Review policy callback receives borrowed typed context from the
original completed producer and retained consumer, instead of a dispatch alone.
The holder selects that producer from its already-admitted retained edge. Both
existing physical Owners must expose the same original request, and cancellation
or retirement makes the context unavailable.

The context contains the original producer's nominal materials. Its invocation
method calls the existing producer publication issuer using saved journal Source
evidence and acquisition times. It does not issue another Source request,
reprepare a Program, refresh authorization/expiry or select an expected request
from the consumer's proposed material. These facts allow the independently
installed Catalog/grant caller to use the actual invocation and dispatch.

Current physical custody and evidence authorization are checked before and
after the policy callback. The existing Catalog Owner compares its binding to
the original producer-issued invocation and the actual consumer dispatch before
Review input pins are prepared. A lost fence denies adoption. The callback retains
its existing Catalog/credential response and cleanup responsibilities even if
its result cannot be used. A missing or unavailable read is not automatically
retried with another use. Review preparation still passes the original input
context to the existing normalization, Receipt, capture and Provider Owners.

The context is borrowed and ephemeral, not a new custody Owner, journal or
cache. It grants neither Provider permission nor Reviewer approval. No public
wire, CID, formal pin, current-policy interpretation or Local implementation is
changed.

## Remaining production work

The production callback remains absent until a real independently installed
Catalog/retention policy is connected. Named Catalog acquisition must use the
existing signed grant and credential service, bound to this original invocation
and consumer dispatch. Its actual response/use/hash and binding require existing
capture/journal/Store custody before reconstruction. The service's status-only
outcome and non-resending consumed use are not a recovered metadata body.

Publication installation, genuine producer reconstruction, actual approval,
Provider write, public Result and formal release are still separate unfinished
connections. Missing original custody remains pending; it is not reconstructed
from equal artifact bytes or hidden by Source requery.

The authored Native read-fence cases are not physical acceptance. Matching
Native compilation checks the real holder callback consumers. Physical execution
requires the separately assigned bounded window and fixed libraries; a skipped
or early-return Native crypto case is not successful acceptance.

This child follows OSS #1447 and its existing parents; the final merge target
is OSS main. Formal Cloud adoption requires the merged source and matching
package/Native cohort.
