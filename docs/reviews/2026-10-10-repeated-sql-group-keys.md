# Reuse repeated SQL grouping values

Baseline: main `89709b5c6ba851dbe9200bfa078cb85a4b5f948d` (#1170).
This is an independent Frontend unit, not a dependency on the Graph vocabulary
PRs or the separate QUALIFY capacity handoff. It introduces no common executor,
checker rule, resource ceiling, grammar production or fallback.

## Counterexample and scope

```sql
SELECT COUNT(*) + (pair.x + 1) AS n
FROM pair
GROUP BY x + 1, x + 1
```

The independently authored complete Program evaluates `x + 1` in one private
derive, groups that slot once, then adds the checked COUNT to the evaluated
key. It checks successfully before source comparison. The old Frontend instead
emits a private derive/key for each occurrence. The baseline selected test
fails 0/1 at complete Program equality after both Programs pass checking:
guard `run-PSoKBS`, focused receipt `focused-test-SKOMbB`. This establishes
avoidable duplicated lowering; it does **not** establish incorrect old rows,
a public Run failure or an overestimated common capacity formula.

The pinned GoogleSQL source `d82db99a923a46571f543a13899dc791a7b6f743`,
`googlesql/analyzer/resolver_query.cc` near line 8698, explicitly reuses the
computed column for repeated resolved grouping expressions. The existing
Frontend already reuses evaluated GROUP subtrees in SELECT/HAVING/ORDER. This
repair extends that same resolved-value comparison to the SQL key list. It
does not treat implementation text as proof of all GoogleSQL semantics.

Direct TRUE/String/NULL GROUP literals remain unchanged. An earlier unrelated
candidate to admit them was withdrawn after the pinned analyzer's explicit
literal refusal was found; it is not part of this repair.

## Minimal repair and independent obligations

`compile_steps` uses its original GROUP input snapshot and the existing
`same_group_expression_in_scopes` comparator. It emits one key only when both
expressions denote the same resolved receiver, property path, operators and
parameters. It neither compares spelling alone nor supplies new equality laws.
Expanded-star ordinals reuse their already checked physical field. Different
JOIN sides and distinct object receivers remain different values, even when
their path suffixes are identical. Comparisons charge the existing bounded
expression-work budget and retain an authored origin on exhaustion.

Pipe AGGREGATE keeps its separate named-output behavior: two authored aliases
remain two public columns. No output alias, input predicate, NULL, input
multiplicity, parameter value, order or limit is changed to obtain acceptance.
Ordinary checker/planner/Host admission remains required.

Independent complete Program tests cover computed keys with qualification and
parentheses, direct keys, expanded-star ordinals and repeated positions. Caller
tests include different property receivers, different JOIN inputs, GROUP BY
ALL and Pipe output scope. A dedicated work-limit counterexample checks the
exact typed refusal.

Eight public cases join the existing normal and focused ordinal corpus:
one full JSON control, nullable computed/parameter/ordinal source, repeated
direct fields, repeated star positions, output-alias/input collision, typed
empty input, separate Pipe aliases and distinct property receivers. Expectations
are author-written rows/types/order; the control's one computed key is not
generated by the product. Public checks retain complete streams, private-column
non-disclosure, Result.describe contracts, source acquisition counts, Result
rereading and same-request replay identity.

The six old ordinal refusals now explicitly require their established
`ClientProgramImplementationLimit`: `group_ordinal_test.mbt` checks
`UnsupportedGrouping`, and the unchanged common `client_check.mbt` maps that
issue to `implementation_limit`. Inputs, product classification and the general
error allowlist are unchanged. This corrects the fixture's omitted expected
category before packing; it does not turn invalid source into a successful Run.

No owned contract, grammar or generated pin changes. Programs for redundant SQL
keys can have different normal Program/Run identities because redundant derives
and keys are absent; no saved Run is relabeled with a new identity.
