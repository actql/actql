# Native original-holder approved Effect row

The actual retained Source/Compute holder already supplies the checked Provider
Preview, original signed Checkpoint and authenticated Resolution. This connection
uses that same holder to prepare one approved single-record update, claim its
common Ledger dispatch, perform the bounded physical write, retain the raw
response and commit the common row receipt and terminal entry.

## Scope and ownership

The installed caller supplies current independent reviewer authorization and a
trusted resume observation from the existing Owner. A submitted Resolution is
not a resume claim, Source permission is not Effect permission, and a saved
Checkpoint is not permission to send. The actual local fixture uses the common
resume Owner to construct its trusted observation; it does not prove durable
Cloud claim integration or public SDK approval.

The first connection is deliberately one checked Preview member and one update
row. It derives the logical scope, authored Program/stage, locator, dispatch key,
request CID and common Ledger basis from the original checked material. It does
not create a scheduler, second Ledger, approval issuer or compatibility path.
Current holder, original Run lifetime, signed approval lifetime, independent
authority and resume fence are checked again through the guarded Credential
Resource Owner at the physical send boundary. The write uses a separate current
credential grant for the checked operation, origin, scope and original attempt.

Only a confirmed new Ledger claim reaches the Provider. Failed or uncertain
claim/send/persistence results retain responsibility and never authorize another
send. Response-custody retry uses the same bytes, status and credential use.
Settlement reads the Store-owned response, applies the existing Provider catalog
projection, and commits the existing common row receipt and terminal entry in
one Site journal transaction. Exact repeats do not advance the head revision.

The review cannot retire while this physical row is pending. Failed response or
terminal persistence keeps the original holder and its reservations. Confirmed
row terminality discharges only that row obligation; it does not publish a Cloud
Result, finalize the Run or return the producer/receiver reservations.

## Focused acceptance

The existing original-holder fixture executes actual Native Source acquisition
and consumer Compute, physical local HTTPS Provider Preview, original signed
Resolution verification, real SQLite journal and credential operations. Its
independent target starts at Count 7; the checked approved update sets Count 3.

The added counterexamples cover authority refusal, a foreign resume intent,
settlement-only mode, another Site generation, raw response persistence failure,
terminal persistence failure after confirmed raw custody, retries and attempted
re-sending. Both persistence faults use a second handle to the actual original
SQLite journal. Cleanup remains blocked and the consumer reservation remains
unchanged until the row terminal is confirmed. The physical fixture requires
one Preview read and one write, including all retries, and verifies the resulting
Count 3. The unchanged no-write mode remains a separate selection.

The source SHA, executed counts and original receipts belong in the PR validation
record. A timeout with unavailable counts is a failed check, not acceptance.
Native caller and portable JS compilation are compatibility checks, not executed
callers. Generated interfaces are produced by the existing MoonBit toolchain.
