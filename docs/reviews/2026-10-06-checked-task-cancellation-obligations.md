# Checked task cancellation obligations

A persisted cancellation after producer completion can prevent the checked
consumer from ever acquiring a dispatch or physical start claim. The raw graph
progress correctly has no consumer execution or cleanup observation. Using that
raw cleanup flag as the whole Run cancellation obligation, however, leaves the
Run pending even after exact producer cleanup has been confirmed.

## Boundary

The unpublished whole Run projection discharges a never-started checked slot
only when the trusted Host supplies its saved cancellation fence and the slot
has neither an admitted Coordinator dispatch nor a saved physical start claim.
This does not create a Site Released observation. Raw graph progress and the
consumer's unobserved task status remain unchanged.

Every dispatched or claimed task still requires its own admitted terminal and
cleanup observations. Missing claimed custody remains unknown; historical
Accepted does not prove physical stop. Producer, Transfer, receiver holding and
borrow cleanup remain the responsibility of their existing Owners. The Host
must reread its cancellation/publication fence and revision before committing
the projection.

The projection supplies these obligation facts to the existing cancellation
eligibility Owner. It does not change that Owner, start work, release capacity,
commit Run state, or infer cleanup from resource counts.

## Interface

`ClientRemoteTaskRunProjection` carries its derived `cleanup_complete` flag.
The private projection field array appends that flag; the first four positions
remain unchanged. `projectTaskSiteRun()` exposes it through its existing
`cleanupComplete` property. The MoonBit interface is regenerated by `moon info`.
There is no wire, stored record, contract CID or independent expectation change.
Wrapper and compiled runtime must be built and adopted together.

## Evidence and remaining acceptance

The consuming Run Host package cases cover:

- Producer cleanup pending, releasing and confirmed, while the consumer has no
  dispatch or start claim.
- Missing claimed consumer custody and absence without a cancellation fence.
- Historical Accepted and dispatched consumer cleanup pending until exact
  terminal and cleanup evidence arrive.
- Existing normal publication, unknown, failure and recovered custody behavior.

An actual Cloud Run CAS and Coordinator Owner protocol test reproduced the
pre-fix stall. The corrected projection passes that case without creating a
consumer claim, offering work or changing the stored Run revision during
observation. This is a protocol connection test, not physical Native cleanup or
public Cloud acceptance.

The combined Cloud observation selection passed 12 of 13 cases; one existing
normal-path case reached its unchanged five-second timeout. That case and the
new cancellation case passed together in an isolated selection. The first
timeout remains unexplained; isolated success is not a cause diagnosis.

Formal Cloud adoption requires the merged OSS source and matching packages and
Native binary. The public two-task Run, physical cleanup, reconstruction and
fault acceptance remain separate requirements tracked in [#182](https://github.com/actql/actql/issues/182).
This change does not close old Run recovery obligations in Cloud #88.
