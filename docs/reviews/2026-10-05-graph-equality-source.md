## Counterexample and repair

An independently authored ordinary Program compares `g` with `g` and selects
the non-NULL Boolean `equal` column. It passes the ordinary checker. Equivalent
authored source was rejected by the Graph-to-Relation routing:

```aql
DATA n = SELECT 1 AS node_key, 7 AS p;
DATA g = PROPERTY GRAPH (
  NODE TABLES (n AS N KEY (node_key) LABEL Person PROPERTIES (p))
);
FROM g |> graphs_equal(with: g) |> SELECT equal
```

The baseline focused JS run passed the independent Program control and failed
the source lowering test (1/2). The new small lowering module emits the existing
`graphs_equal` step, resolving `with:` through the same DATA Graph namespace as
the left input. Terminal and DATA query branches pass that namespace to the
existing Graph-to-Relation path. Quoted names and retained DATA aliases reuse
the emitted producer; normalization changes the current left producer without
rebinding the right input or reconstructing a Graph.

Only the common output column `equal` enters ordinary Relation processing.
The checker owns compatible definitions/types, and the existing bounded owner
owns full-value comparison, identity, labels, properties and provenance. This
unit adds no comparison implementation, acquisition, placement, storage codec,
Graph fallback or execution owner.

## Independent acceptance obligations

The complete source-to-Program expectation is authored directly in
`src/query_program/graph_equality_test.mbt`. The ordinary packed public-query
corpus includes an independently authored JSON control and five source cases:
self comparison, normalized/quoted DATA reuse, a distinct right producer,
an empty typed Graph and a comparison filtered to an empty Relation. Expected
Boolean rows and full ordered column contracts are not generated by a compiler.

Ten preparation-refusal cases cover string/unknown/forward/Relation producer
references, missing/extra arguments, hidden Graph columns, a second Graph call
after the transition, incompatible key types and the common ordering gap below.
Local and authenticated HTTP must check rows, `describe()` columns, completed
streams and same-Run resend/attach/lookup. Refusals must leave Run admission and
provider I/O at zero. The `--graph-equality-only` option selects these same
normally registered cases; it is not a separate execution path.

## Separate common-owner ordering gap

Appending `ORDER BY equal |> LIMIT 1` is accepted and lowered with the exact
authored sort, direction, NULL placement and `{count:1, offset:0}`. Both the
emitted Program and its independently written full Program are rejected by the
ordinary checker with `PipelineOrder(UnresolvedOrder)` before Run admission.
This is an executed common-Program counterexample, not merely source inspection.

The minimal query and complete expected Program are fixed by the test
"Graph equality retains ORDER and LIMIT at the common unresolved boundary".
The common `pipeline_typing/contextual_orders.mbt` nonempty-sort check requires
`sort_order`, whose logical-order completion/tie evidence is absent for this
comparison output. The Frontend keeps the order and limit. It does not claim
total-order evidence or remove the sort to pass this example. The follow-up
belongs to the common order/evidence owner; it is not a permanent language
restriction. Ordered equality-result acceptance remains uncompleted.
