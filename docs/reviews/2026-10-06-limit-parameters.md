# LIMIT and OFFSET parameters: Frontend connection

Baseline: `64046e37a1cadb2148edeab7cbf85b96d125b518` on `main`.

## Existing contract and counterexample

The common `take` operation already accepts declared, bound parameter references
in `count` and `offset`. The public query parser accepted only integer literals.
These two authored queries therefore failed before reaching the same common
contract that accepts the independently written JSON Program in
`src/query_program/limit_parameter_test.mbt`:

```sql
SELECT id, amount FROM orders ORDER BY id LIMIT @p OFFSET @p
```

```aql
FROM orders |> SELECT id, amount |> ORDER BY id |> LIMIT @p OFFSET @p
```

The pre-fix focused check `run-7oI5fE` passed the independent Program through the
normal checker, then failed parsing the source (0/1). It establishes the missing
Frontend connection, not an execution-owner failure.

## Connection and limits

The parser retains each whole named parameter. One lowering helper writes the
ordinary `{$param: name}` operand in all three existing `take` construction
paths: regular/scoped queries, JOIN final operations, and set final operations.
CTE bodies use those same existing query paths. Declarations, values, safe
integer checks, stable-order proof and capacity remain the common checker's
responsibility. No expression evaluator, coercion, fallback, runtime owner or
capacity exception is introduced.

[GoogleSQL LIMIT/OFFSET](https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/query-syntax#limit_and_offset_clause)
admits nonnegative, non-NULL integer constants, including parameters. This
connection deliberately preserves the current common ActQL contract: positive
safe integer count, nonnegative safe integer offset, and proven input order.
`LIMIT 0`, general constant expressions and the broader reference order behavior
remain explicit profile gaps; they are not claimed to be invalid GoogleSQL.

## Independent obligations

- SQL and Pipe each match a complete hand-authored Program; the common checker
  accepts it without modifying the generated Program.
- Missing declarations/values and invalid bound integers stay checker refusals.
  Row-dependent and partial parameter expressions remain parser refusals.
- Public fixtures cover different count/offset values, literal/parameter mixing,
  omitted and zero offset, duplicates, NULL values, empty typed output, and CTE,
  DATA/set and JOIN consumers. The independent JSON control uses the common
  Program rather than compiler output.
- The existing packed consumer checks Named Result values, `describe()` column
  contracts/order, stream completion, private-column absence, Source read count,
  repeat request identity and rereading without additional acquisition.
- All eleven refusal fixtures use the existing admission-zero/provider-I/O-zero
  assertions. Eleven successful cases and eleven refusal cases are registered in
  both the narrow selection and the normal public-query corpus.

## Identity and generated inputs

The EBNF and query rules change the grammar manifest, which changes derived
compiled Plan/Run identity even for an otherwise unchanged Values Program.
The current Run vector is independently calculated from its canonical preimage,
not copied from runtime output. The former grammar/Run vector is retained with
its former inputs. The Values Unit and Result Plan expectations are unchanged.
The manifest generator, document metadata updater and canonical-test generator
refresh their owned outputs; independent expectations are not generated by them.
