# ARRAY source construction and remaining contract gaps

This unit connects bracket and ARRAY constructors to ordinary Program expressions.
It is an implementation unit within the ongoing Frontend migration, not a claim
of complete GoogleSQL ARRAY coverage or runtime conformance on every target.

## Existing boundary and selected connection

The common Program already accepts finite array expressions and typed empty
arrays, while source expressions lacked an ARRAY constructor. Independently
written complete Program fixtures establish the connection for SQL and Pipe,
element order, duplicate values, NULL context and explicit UNNEST offsets.

The parser accepts `[items]`, `ARRAY[items]` and annotations for BOOL/BOOLEAN,
STRING, FLOAT64, TIMESTAMP and JSON. An annotation is checked through existing
`empty_array` type evidence and a lazy constant-true `if` for nonempty arrays;
it does not cast elements, infer a second type system or evaluate them twice.
An unresolved empty list still requires context. The finite Number profile is
not a claim of exact INT64 support.

GoogleSQL excludes immediate ARRAY item types but permits a STRUCT between
arrays. The source profile reads common checked expression contracts, including
array-valued references and parameters, before durable admission. It preserves
machine JSON/YAML Program support for recursive arrays, and does not inspect
opaque JSON payloads as SQL ARRAY types. Existing checker locations are retained;
this unit does not claim newly restored authored-source coordinates through
serialized Program preparation.

## Independent public acceptance

The ordinary packed public-query campaign includes the new fixture; its narrow
selection is `node scripts/test-packed-public-query.mjs --array-literal-only`.
It contains ten positive cases, including a separately authored JSON Program,
NULL items, only-NULL typed items, empty typed arrays, empty rows and SQL/Pipe
UNNEST with ordered offsets. Five negative cases cover incompatible items,
wrong annotation, immediate nested arrays from literals and parameters, and a
malformed delimiter. Expectations include Result.describe contracts, declared
column order, rows and no additional acquisition or execution on reattach/resend.
Refusals must preserve typed error classification and cause no Run admission or
provider I/O. The fixture never patches the generated Program.

Pre-submission focused checks passed: 16 JS tests across the four ARRAY files
and the Values Run-materials caller, and five Node tests across public-fixture
registration and independent grammar/Run vectors. Public Local/HTTPS acceptance
and required submitted-SHA CI remain unverified at this preparation stage.

## Identity impact

Grammar and query specification bytes change the grammar manifest and its
normative imports. The compilation manifests and canonical test vectors are
regenerated by their existing generators. The current fixed Values Run vector
is calculated from independently assembled normative preimages; preceding
vectors keep their original pins. Values Program, Unit and Result Plan semantics
are unchanged; grammar-bound invocation, compilation and Run identities change.
Old retained identities are not relabeled.

## Remaining work

- Common constructor capability checks currently reject JSON items, including
  typed JSON null. The source and independent JSON Program both reach
  `Operation(Expression(ForbiddenConstructorValue))`; this is not positive
  ARRAY<JSON> execution evidence. Keep it as a separate common-contract unit,
  retaining hidden ResourceRef/ArtifactRef restrictions and common evaluation.
- Exact INT64 and the default untyped empty ARRAY<INT64> require the appropriate
  shared numeric contract; no Number or JSON substitution is made here.
- Additional declared item types and computed type coercion remain separate
  coverage obligations, not permanent restrictions of the target language.
- Cross-target interface compilation is distinct from Wasm/native execution.

## Public execution blocker and common-owner handoff

and each tarball digest were fixed before installation. The ARRAY-only public

The later ARRAY cases, refusals and HTTPS path were not executed. README Local
and HTTPS preflight success is separate from ARRAY execution evidence.

`installNodeClientProgramPreparation` accepted the same control. The existing


The independent control is retained in
[the minimal Program](fixtures/array-public-program-control.program.json).
Expected Named Result `answer` is exactly `[{"items":[2,1,2]}]`; its sole column
is nonnullable ARRAY with `max_items:3` and nonnullable Number items. Preserve
that value, type and multiplicity. The source `SELECT [2,1,2] AS items` lowers
to the same ordinary array operation; alias/step structure differences do not
justify a different execution meaning.

Common execution owner A needs to connect the existing typed `array` and
`empty_array` forms at `lowering_relation/expression.mbt` and its expression
wire/evaluation consumers. The current ExpressionBody has Object and Property,
but no Array constructor case; lowering explicitly rejects the array tag.
Use the existing expression-frame retention, capacity, cancellation and cleanup
ownership. This Frontend unit does not implement a parallel evaluator, replace
SQL ARRAY with opaque JSON, or fold the fixture into a different Program.

The public 500 classification is a separate Host preparation/error boundary:
a deterministic common compilation refusal should remain typed before durable
Run admission. Public refusal-counter evidence is not established by this
failed campaign. Keep that responsibility distinct from ARRAY semantics.
