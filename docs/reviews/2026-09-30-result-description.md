## Adapter handoff

The public operation is `result-describe` under `/actql/client/0.1/`. It uses the
existing connection/authentication and an exact Run reference:

```json
{
  "connection": {"mode":"remote","owner":"remote","consentRefs":[],"runners":[]},
  "ref": {"namespaceId":"example","authorityScopeCid":"sha256:...","runDefinitionCid":"sha256:..."},
  "resultName":"answer","format":"jsonl","attemptId":"metadata-request-id",
  "maxWireBytes":1048576,"maxNodes":10000,"maxDepth":64
}
```

The abbreviated CIDs above are explanatory, not admissible fixture values.
`WireResultDescription` and `WireValueContract` are exported by
`@actql/client-wire`. `validResultDescription(value, expected, limits)` validates
the generated type shape, exact Run/name/profile and structural budgets. The
SDK additionally verifies the existing Definition, schema and delivery CIDs.

`@actql/run-host-core` exports `describeCommittedResult` and
`describeAuthorizedResult` from its Result access service. Install explicit
`authorizeResultDescription` and `admitResultDescription` callbacks alongside
existing read authority. They are current Host authority, not Client consent or
a successful connection snapshot. The service requires the Store operation
`readCommittedResultDescriptionEvidence(key, definitionCid)`, returning checked
binding contracts, the exact Definition contract, schema wire, and an optional
retention extension. It deliberately does not require a live payload generation.
The control delegates all binding/retention/grant semantics to the existing
MoonBit owners. Adapters must also provide the existing Manifest grant-use
operation; `attemptId` identifies that use, not payload delivery.

```js
const execution = await client.attach(savedRunRef);
const description = await execution.result('answer').describe();
for (const {name, contract} of description.columns) {
  console.log(name, contract.type, contract.nullable);
}
```

The follow-on adapter owner F can use this package boundary. No platform-specific
implementation, private repository reference or deployment evidence is included
in this OSS completion unit.

## Independent acceptance

`scripts/fixtures/packed-result-description.mjs` is copied unchanged to a clean
installation outside the checkout. It consumes five packed packages with
install scripts disabled and no MoonBit toolchain in the consumer PATH. Both
embedded Local and an actual TLS HTTP Host execute the same authored Program
and expectations:

- two-column Values, declared as `z,a`, with NULL and non-ASCII text;
- empty Values with nullable array, nested decimal object, and vector contracts,
  declared as `vec,obj,arr`;
- matching description through attach, existing json/jsonl/csv profiles;
- whole-response byte boundary, node/depth refusal and unsupported format;
- payload expiration with description retained, then metadata expiration;
- unpublished Result and unauthenticated HTTP refusal, without new Compute.

Schema, Definition and serialization identities are independently calculated
from authored canonical bodies. Expected contracts/rows are not generated by
the new projection. Physical deletion/restart is additionally tested with the
Local Store fixture. SDK tests distinguish malicious response validation from
real Host acceptance; adapter sequencing tests explicitly use test doubles.

Run `node scripts/test-packed-result-description.mjs` using the pinned repository
toolchain to pack. Its summary records the source SHA, each tarball SHA-256,
child exit observations and logs. Successful and failed runs remove only their
own expanded artifacts after retaining evidence; `--keep-artifacts` preserves a
single diagnostic run. The Client CI job includes this acceptance and uploads
its evidence even on failure.
