# Original installed row reader custody

## Original installation preparation read

The existing Source publication Owner can retain an installation's original
funded read and workspace for a preparation consumer. This captures an already
issued pair; it does not create the installing Host, fund startup, admit a
business Run or authorize a metadata request.

- Responsibility: `InstallationPreparationRead` retains the existing Resource
  consumer and its exact original workspace through preparation.
- Inputs and outputs: preparation accepts the original read-pair, origin,
  workspace loan and complete simultaneous retained/execution envelope. It
  returns a private-constructor capture, not a Ledger or replacement loan.
- Identity: the initial pair lookup checks the same original claim, origin and
  loan before the read enters `Preparing`. Equal bytes, CIDs or a second loan on
  the same Ledger cannot replace those originals.
- Ownership: the installing Host retains read settlement and physical workspace
  stop/cleanup. The capture owns its one preparation transition and final
  borrowed-pair retirement; it does not close either physical responsibility.
- Synchronization: after each await, the consumer checks its same retained
  Resource consumer and loan. The old `Reading`/`Written` pair borrow is not
  reopened. Entry uses the original single-use Resource transition, and repeated
  entry refuses.
- Failure: a foreign pair or insufficient envelope refuses before claiming.
  Failed current checks retain the original capture and cleanup duties; they do
  not issue a new read, refund capacity or repeat provider I/O.
- Cancellation: stopping a read or beginning workspace closure revokes current
  preparation availability. Neither action confirms physical retirement, and a
  pending stop or cleanup keeps the original references held.
- Resources: the original envelope covers this capture, tuple and referenced
  origin/pair/loan/consumer, their overlapping users and construction workspace.
  Bounds and current predicates do not supply that funding. Retiring borrowed
  references is not GC reclamation, a byte refund or another duty's ACK.
- Extension: these private typed entry points add no wire, CID, credential
  domain, grant, numerical profile or alternate cleanup Owner. Host/Site/Account
  current authority, I/O admission and complete startup/phase funding remain
  independent prerequisites. An initial control/preparation-only bootstrap
  cannot supply metadata HTTP, Source, Model, Result or business-Run capacity
  through this capture; each consuming domain still needs its actual supplier.
- Verification: owner tests cover the post-claim phase, single entry, foreign
  originals, insufficient envelopes and both orders of read/workspace cleanup.
  Their explicit synthetic envelopes are not an installed physical supplier or
  a normal Host funding qualification.

members and duplicate keys; it does not interpret vendor fields or grant a
credential use. Each selected Connector's own reader admits its complete entry.
The outer document, connection entry and any declaration inside that entry are
distinct original byte sequences, not interchangeable source identities.

The Node acquisition stage accepts only the original issued Project and runtime,
resolves the original locator relative to its captured directory, and retains
the exact text from the existing bounded strict-UTF8 reader. It captures the
original Common callbacks before I/O and checks installation currentness after
the same awaited read and close. A missing or invalid selected document cannot
become an absent/source-free declaration. Close failure retains the original
file responsibility; it does not trigger another read. The projected originals
remain DATA, not publication custody, a Catalog, a read grant or an installation.

The existing installation inventory must cover the Project and view references,
captured callbacks/current closure, path and raw text, parsed tree and retained
entry strings, plus simultaneous read/decode workspace. The 65536-byte intake
ceiling is not a physical reservation or proof of adequate funding. Actual
publication, durable custody, Connector preparation and Run adoption remain
separate duties of their existing Owners.

## Accounted row acquisition

The provider-neutral installed row adapter may select a supplemental ordinary
reader envelope in its existing trusted installation. Its private
`providerReader` contains the original Common `ExecutionCapacity` declaration
and one synchronous, I/O-free `prepare` method. Both are snapshotted once;
neither a submitted Run packet nor current configuration can replace them.
This declaration is DATA, not a reservation, adequate physical measurement,
permission or normal numerical profile.

The existing Common installed-capture planner seals the same acquisition and
declaration. The Host passes that projection into the original Run Ledger's
planning path. The same declaration then reaches the original accounted
RowRun start. Common checks the additions and reserves them before the reader
factory, request encoding, physical read or its child work. Missing capacity,
foreign preparation and unsupported listing/keyed profile combinations refuse;
there is no unaccounted fallback or JavaScript byte arithmetic.

After the RowRun enters Reading, the Host binds its one original response
borrow and cleanup observation before entering the reader factory. The factory
receives the original request, authorization/current callbacks, acquisition,
Run and nonce. It returns one original reader with `read`, `requestStop` and
`observe` methods. The Host captures their original receiver and functions
once and rechecks current read authority after preparation and before read.
Failure of the factory, method access or current check retains the original
RowRun and its reservation; it never retries preparation to reconstruct them.

The factory's existing second argument retains its original preparation before
fallible constructor work. A failed factory or returned-method getter leaves
that same preparation and its captured own synchronous `retire` method in the
existing reader slots. Its managed alias retirement waits for its own partial
children; only exact `true` lets the original RowRun continue cleanup. Reentry,
replacement, truthy values and Promise settlement supply no acknowledgement.
One unexpected Promise remains the entered flight until it settles, without
repeating retirement while it is pending. The preparation is replaced by the
returned reader only after all returned methods have been captured and checked.
The original options receiver and third capacity-growth argument are preserved.
This connection adds no Run, physical cleanup owner, budget or permission.

The same private factory uses its third callback with the fixed
`announced-body` phase for native construction before any response exists. It
admits the fixed reader's complete cumulative constructor overlap on the
original Query or whole-input RowRun reservation.
The callback is usable only during that original read, after cleanup binding,
with no outstanding response ticket. It rechecks original Resource current and
the same reader after the callback, including when the declared peak is reused.
A copied borrow, smaller declaration, pending/closed reservation, insufficient
backing or reentrant stop cannot enter a constructor. A successful debit stays
held if subsequent construction or its current check fails.

This entry creates no page ticket, transfer allowance, attempt, permission or
physical acknowledgement. Charged response decoding keeps the one-argument
callback and exact latest-ticket requirement. Missing construction capability stays
absent; a native reader requiring it must refuse before allocation. The actual
native caller still supplies its justified request, parser, retained output
and failed-child overlap before each constructor. The callback alone does not
establish that recipe or qualify an installed native reader.

The reader's `observe().cleanupConfirmed === true` must represent actual
retirement of that same reader and all escaped custody. It is not inferred
from method return, Promise settlement, cancellation acceptance, credential
Site close, frozen arrays, raw EOF or capture completion. The Host also keeps
its own pending read and stop Promises unsettled until their original
settlement. A pending or failed cleanup stays with the original RowRun's
existing recovery path. No replacement reader, request, Run, Ledger or send
is issued. Rejections are handled without turning them into a successful read.

Supplemental provider retention and workspace remain reserved through capture
and any Store, diagnostics, callback or raw-response alias overlap. Captured
logical rows can have their own downstream custody without retiring provider
raw history. A driver that still exposes success/error response aliases and
cannot observe their retirement must keep `cleanupConfirmed` false. It cannot
enable normal retirement merely by supplying a finite byte declaration.

A completed acquired Model's Content prefix borrows the same Source reservation
and holding on its original Request Ledger. A provider's still-open reservation
keeps all remaining retention and scratch beside the prefix's own reservation;
starting the prefix does not settle or refund it. The Core prerequisite checks
the exact ordered tokens, holding-to-reservation association, one-shot attempt
history and absence of cleanup pending, both before reservation and after input
callbacks. Foreign tokens, read issuance, extra children and spent opportunities
still refuse. Prefix cleanup retires only its own child; Source cleanup must
observe and retire the original provider before the parent can finish.

The original Host/Run inventory includes the retained declaration and planner
pair, preparer and receiver, reader and three method references, request and
current callbacks, response borrow and its cleanup closure, pending read/stop
Promises and handlers, and any original failure. Their simultaneous target
layout and lifetime are part of the same selected envelope, not free control
bytes. Only after original Core close and capture cleanup succeed may the
Host sever its reader/method backreferences. This reference retirement is not
GC or a physical release acknowledgement of another Owner's resources.
## Original credential acquisition retirement

The existing Row Credential Site can explicitly select bounded Run-acquisition
custody. Its trusted installer supplies positive `maxBindings` and
`maxSecretBytes`, together with the original immutable Site profile, issuer,
resolver and Journal. Omission refuses the new acquisition entry; it does not
supply a normal numerical profile or change existing Run callers.

`openRunAcquisition` snapshots the original Run request and synchronous/current
observation callbacks before invoking them. It uses the same existing signing
path and seventeen-field grant preimage. The returned authorization and private
credential envelope retain the same control, Journal and resolver; the physical
binding keeps original material across separately claimed operations. Every
awaited observation is followed by the captured current fence. A copied scope,
matching CID or callback result cannot create an issuer, new permission or
current authorization.

When the same Site has already authorized and issued a grant,
`bindRunAcquisition` retains that exact returned authorization instead of
signing another grant. Its private issuer membership rejects a wrapper copy,
re-admitted grant or equal CID, even if all projected scope fields match.
The original grant, scope, control, Journal and resolver remain unchanged.
The binding does not replace the Account decision or each operation's claimed
use, current authority, expiry, revocation and quota checks.

An authorization can enter binding preparation only once. The parent records
the opening child before a captured current callback can reenter: a concurrent
close remains pending until that opening attempt has either produced its
original binding or failed without one. A failed opening does not issue a
replacement grant or silently retry the authorization. The same existing
Journal keeps its grant and any physical duties.

The parent Site owns every selected binding before returning a borrow. Its
close first retires those original bindings, including pending resolver,
response and socket custody, and only then invokes the captured original
Journal close with its original receiver. An unconfirmed child cannot release
the parent Journal. Failed Journal close remains pending in that same custody;
confirmed child and Journal retirement are not repeated. The metadata
alternative and existing Run callers retain their distinct purposes and
existing scope rules.

The binding count bounds retained original entries, not only currently open
sockets. Closing a child does not replenish that declared count or reclaim its
escaped credential/current/authorization aliases. The original acquisition's
budget must cover the entries, callbacks, request snapshots, immutable
credential borrows, grant/use references, material, response/error aliases and
simultaneous physical workspace through cleanup. No response loss or Unknown
claim is retried by cleanup. Journal retirement does not reconcile that claim,
authenticate a saved publication, release another Owner's holding or establish
GC/physical-byte reclamation. Actual Host/Account admission, funding and durable
publication remain independent requirements of their existing Owners.

Original issued-authorization membership also retains a private weak-map entry
and state record for each escaped authorization while bounded acquisition
custody is selected. The binding ceiling does not bound all grant issuances or
turn weak membership into free capacity. These records, opening-child entries
and escaped aliases belong to the original acquisition/issuer inventory; a
child or Journal ACK is not their heap-reclamation certificate.

## Managed Source parent current callbacks

The imported current callback can synchronously retire or replace that Run.
The Host therefore captures its original parent and rechecks the private Run
association, parent identity, closed state and recorded failure immediately

The existing Source wrapper still rechecks the same association after awaited

Root, Ledger, read grant, capacity or replacement cleanup responsibility;

The reused admission entry applies the same fence to its captured check. It
pins the existing Run value, propagates its original recorded failure, checks
the same installation again, and verifies the same Map entry and live-record
membership before returning that value. Reentry cannot substitute another
request, manager, profile or value, or cause another admission. A Host-current
failure remains that original failure rather than becoming a successful reuse.

## Canonical CREATE occurrence carriage

rows before either synchronous or child provider request preparation. The
returned ordering and `{content_cid, occurrence}` DATA determine the same rows
used for requests, Preview and claims. A JavaScript row index, value comparison,
request CID or future Preview does not issue an occurrence.

- CREATE carriage responsibility: forward the same original inventory result
  before a provider request can bind its logical tag or physical request CID.
- CREATE carriage inputs and outputs: complete mapped rows and the existing
  inventory bounds produce private ordered frames. Each CREATE request context
  receives its frame's immutable `createRowIdentity` DATA.
- CREATE carriage identity: duplicate contents retain distinct original
  occurrences. The same identity object reaches provider preparation and its
  completed Preview frame; no second inventory or identity guess is used.
- CREATE carriage ownership: the existing stage owns decoded rows and private
  frames. It replaces each frame's entry with the matching original request
  once, then freezes the completed frame and array. No new cache or Owner is
  created, and this DATA is not permission, a grant or a physical ACK.
- CREATE carriage synchronization: settle the inventory and ordering before
  invoking a provider callback or constructing its retained request child. The
  child keeps the existing prepare/release/current protocol.
- CREATE carriage failure: propagate the same inventory refusal and cleanup
  carrier before provider construction. Existing request/value/CID, current,
  claim and approval checks remain in their original owners.
- CREATE carriage cancellation: existing stage and child cancellation/current
  fences remain authoritative. Carriage does not issue a target-read grant for
  target-less CREATE or acknowledge native cleanup.
- CREATE carriage resources: the same preparation parent must cover inventory
  wire/parsed identities/frames while request construction is live. Moving the

- CREATE carriage extension: a cold request consumes the identity from its same

- CREATE carriage verification: actual enclosing caller controls with explicit
  Common inventory, Preview and provider ports establish forwarding and order.
  They do not qualify an installed compiler artifact, ordinary CREATE, provider
