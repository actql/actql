# Preparation-owned completion-free normalization

This finite Resident Effect profile certifies an empty semantic-completion
inventory from the original checked preparation. It does not declare every
ActQL normalization catalog empty, infer emptiness from a Program shape, or
reuse a test fixture as production evidence. The integration decision selects
this bounded path while other completion paths remain explicitly unavailable.

## Frozen artifact and identity

The authoritative artifact is
`spec/contracts/actql-resident-effect-completion-free-catalog.json`; its closed
schema is the adjacent `.schema.json`. Its applicability is one Source or
Values root, one or two checked stages, Filter/Select/Values operations, the
listed ordinary expression nodes, an explicitly selected Source view, and one
mapped-create Effect. Any broader rule set or applicability requires a distinct
content-addressed artifact. The artifact is immutable once adopted.

The catalog preimage is the complete artifact body serialized as canonical
JSON: object keys in lexicographic order, no insignificant whitespace, UTF-8,
no trailing newline, no self-CID field. Its SHA-256 CID is
`sha256:ea21a2a2ab522cbf960c5e97120648e351db7c127768101502210ed7d8fcfb38`.
The independently fixed preimage is published in
`scripts/resident-effect-normalization-catalog.test.mjs`.

The normalization journal retains the existing normative preimage:

```json
{"entries":[],"rule_catalog_cid":"sha256:ea21a2a2ab522cbf960c5e97120648e351db7c127768101502210ed7d8fcfb38","version":"actql-normalization-journal/0.1"}
```

Its CID is
`sha256:849788c9eede8ad674223eb06775c2dba2cf0ed1d02ceb0a5de6ccfeec2cb087`.
Program, semantics and check-environment bindings are carried by the original
preparation and outer materials/Receipt chain. They are not extra fields in
this normative preimage. Grammar decoding, fixed language laws and Contract
proofs are not semantic-completion entries.

## Inventory ownership and refusal

The checker retains an independent `CompletionFreeAudit` on the original
`CheckedProgram`. The audit walks actual Source resolver selections, checked
pipeline operations and typed expression nodes, rather than caller-supplied
syntax or diagnostic absence. Its fixed 10,000-work bound is separate from
checking success: exhaustion only makes this optional profile unavailable.
It never extends the checker's limits or changes acceptance of the Program.

The Source resolver's `SoleView` selection records real completion; a checked
Source with that selection cannot enter this empty path. A checked template
macro or implicit-null completion likewise refuses. Other operators and node
forms refuse as `ProfileNotInstalled`, preserving the original preparation.
The fixed profile covers only audited paths; successful checking alone is not
an inventory certificate. Mapping/type-derived closure remains with the
existing static Effect Owner and does not issue completion entries here.

`effect_program_completion_free_inventory` returns a nominal projection of the
original checked Owner. `issue_prepared_client_effect_normalization` issues
through the existing run-evidence codec and caches the original projection on
the preparation. Evidence extraction verifies exact preparation, inventory and
issued-projection ownership. Equal source bytes or copied projection fields do
not substitute for that Owner. Issuance performs no Source or Provider I/O.

## Restoration and responsibility

`restore_prepared_client_effect_normalization` verifies the original projection,
frozen catalog and exact saved evidence bytes before existing-codec admission.
It neither parses nor prepares another Program, and does not refresh identity,
authority or lifetime. This API is the original-preparation restoration boundary;
cross-process restoration must additionally verify the original durable
materials and custody through the existing material inverse and Receipt Owner.
An arbitrary empty journal is never sufficient for that restoration.

The next connection carries these issued original bytes before dispatch through
original Effect materials, `ResidentEffectReviewInputContext.capture_result`,
the existing computation Receipt/Captured Run, and
`prepare_native_resident_effect_review_from_context`. Independently trusted
Provider policy, Transfer/borrow custody and pending cleanup remain owned by
existing Owners. This preparation/catalog unit does not establish installed
Native review, public approval, actual Effect execution or final release.

## Original material projection

`issue_prepared_client_effect_run_materials` projects the existing admitted Run
from its original preparation, compilation and definition. Its interface has no
replacement Program, parameters or environment argument. The preparation
retains its immutable originally supplied parameter cursor; the existing bounded
source writer preserves authored text and order. The environment is emitted
from the original checked static candidate. Definition/request binding is
checked before encoding, and the existing remote materials encoder retains the
original invocation, authorization, identity and lifetime. No preparation or
compilation is repeated by this projection.

The optional `normalization_journal_json` string carries the original issued
journal in the existing bounded materials wire, before dispatch. The issuing
API accepts only the nominal projection owned by the same original preparation.
An absent journal stays absent; Effect-free admission refuses this Effect-only
custody rather than silently dropping it.

## Admitted material custody and Native review

`issue_prepared_client_effect_normalization_materials` issues exact material
bytes under the original preparation's normalization Owner and returns an opaque
`ClientEffectIssuedNormalizationMaterials`. Its private nominal issuer identity
is checked together with the original preparation, exact bytes and Run CID.
There is no public wire-to-proof constructor. The wire accessor does not confer
trust on another string.

The proof belongs to its caller and any admitted material custody. Issuance
adds no reverse index of issued Runs or material bytes to the preparation. The private
issuer identity retains no proof or preparation, so dropping the last caller or
custody reference makes those per-Run bytes reclaimable by the runtime. Repeated
issuance can return another valid proof; wire equality does not acquire proof.
This adds neither a Run count limit nor a new resource reservation Owner.

For an in-process original Work, `bind_prepared_client_effect_original_materials`
connects that existing opaque proof to the same checked preparation and physical
compilation. The proof privately retains its issuing compilation; this is not a
new field in materials wire or a changed CID preimage. The connection verifies
the nominal issuer, original inventory, Run definition, request, profile and
exact existing materials bytes before installing the preparation's first live
material custody. It neither prepares nor recompiles another Owner.

An already-bound preparation reuses only the same exact custody. A different
Run, request or physical compilation, even with equal wire bytes, is refused;
corrupted retained custody is not repaired. This binding does not issue a
replacement normalization journal or refresh the original lifetime. The
existing bounded materials encoder bounds the temporary exact-byte comparison;
the retained custody borrows the issued original bytes and journal. Durable
capture, current authorization, cancellation, work-start claims, settlement of
unknown Effects and physical cleanup remain independent responsibilities of
their existing Owners. Material binding grants none of those operations.

For a Run compiled without the finite profile described below, journal-bearing
Effect material admission requires this original projection. It verifies exact
original bytes and Run CID before execution preparation. An appended fixed
journal, a changed material, or a journal-bearing wire without original issuance
proof is refused as `UnverifiedOriginalMaterials`. The ordinary absent-journal
path is unchanged.
The admitted custody retains the original issuance projection as well as the
restored execution Owner. Restoration verifies both before admitting saved
journal bytes; it does not issue, prepare or compile a replacement.

The nominal issuance projection is process-local. It cannot be serialized as a
transport credential. The existing poll envelope does not sign arbitrary
material bytes; a digest or self-described receipt cannot replace provenance.

## Original Run-bound finite profile

For a completion-free Run that must restore across processes, explicitly pass
the original normalization projection to `issue_prepared_client_effect_compilation`
before issuing the allowed Run. The compiler verifies the exact original
preparation and inventory, then includes the existing frozen catalog under
`actql-resident-effect-completion-free/0.1` in the Bound Invocation Template and
compiled plan's `required_profile_contracts`. The saved invocation and Run
identity transitively bind that selection. The runtime package exposes this
selection as `compileEffect(prepared, {normalizationProfile: 'completion-free'})`.
It does not infer the profile from Program shape or silently retry another one.

At execution-material admission, a journal-bearing wire without a local issuance
projection selects this profile only provisionally. The actual checked inventory,
saved invocation, saved authorization and independently selected original Run CID
must match. A fixed empty journal appended to a Run compiled without that profile
fails: it cannot change that original Run identity. The canonical fixed journal
is admitted without issuing another journal. Profile-bearing issuance refuses
if the original journal is omitted.

The Run CID does not bind a logical caller request. Wire-only profile restoration
also compares the admitted request with `expected_request`, selected independently
from the original durable Host/journal context. Absence is compared as well; a
candidate cannot add, omit or substitute another request from the same Program.
The runtime package accepts that existing typed request as the fifth argument of
`admitEffectRunMaterials`. Choosing either expected identity from candidate wire
would violate this API's trusted caller boundary. These identities are not
current authorization, Site delegation, an approval or a mutation permit.

After those checks, the existing bounded projection codec verifies the entire
canonical material wire. The admitted custody retains the verified compilation,
original Run/request, journal bytes and a correlation digest. No issuance cache,
new trust root, signature scheme or cleanup ledger is introduced. Restoring the
journal from that custody performs no preparation, compilation or issuance.
The existing initial execution-material admission still reconstructs execution
ownership once; this is not a serializable compiler snapshot or a claim of
no-repreparation for the whole execution path.

The production Native/Cloud caller must connect the independently retained Run
and request context before using this wire-only entry. This common/runtime
connection alone does not prove that trusted transport, physical Native review,
approval, Provider execution or public Cloud Effect is installed. Previously
issued Runs do not acquire the new profile or a new identity during recovery.

### Binding materials to a retained compilation

A Host that already retains and funds the original `ClientEffectCompilation`
passes it to the existing material codec as `original_compilation`. The Node and
RelA `clientProgramAdmitEffectRunMaterialsWithCompilation` entries require that
opaque compiler and the independently retained `ClientRequestIdentity` directly;
JavaScript does not construct an Option or recreate either original.

This route uses the compiler's same prepared Owner and compares the complete
canonical material, saved Run and original Request, including Program,
Parameters, Environment, Source selection and compiler policy. It does not parse
or check the Program again, restore another policy compiler input, or compile a
replacement. A different compiler, request, material or normalization profile
refuses. A supplied original Source must also retain the same prepared Owner.

An existing live material custody is reused only for the same compiler,
Run, Request, complete material CID and journal bytes. A new binding cannot
displace it. This admission neither returns physical resources nor grants
current authority, an approval or permission to write.

The existing installed `validateRun` caller supplies its already-owned compiler
through this route. Its method and receiver are captured at installation;
a missing typed entry or refused binding does not fall back to wire-only
preparation. Independent wire-only callers retain their existing restoration
contract. Connecting a cold Host's same-Request Plan construction and adoption
remains a separate caller obligation: this projection does not create that Plan,
fund its constructors or establish ordinary restoration acceptance.

### Original request in the Source dispatch binding

For an explicitly selected completion-free Run, the existing Effect Source
binding issuer receives the original typed request before dispatch. It wraps
the existing checked Source binding and that request's existing bounded record
wire in a canonical `actql-effect-source-input-binding/0.1` object with exactly
`original_request_json`, `source_binding_json` and `version`. The 8192-byte input
binding limit remains in force. The Source path and Provider credentials stay
in trusted Site configuration. A different caller request changes the input
binding CID and therefore the dispatch CID even for the same Run and Program.

Native Source admission first checks current Site delegation and the binding's
exact match to the trusted dispatch. It re-admits the request from that separate
binding through the existing request Owner and supplies it as `expected_request`
to material admission. Finally, the reconstructed original compilation must
produce exactly the same complete Source binding before acquisition. Reading
the request from candidate materials would not satisfy this boundary.

The binding CID is not a transport signature. The caller must still establish
the original dispatch through the authenticated Cloud/Site entry, retain its
exact envelope in the existing journal and recheck current authority before
protected operations. Source permission does not approve an Effect. Legacy Runs
compiled without the profile retain their original Source binding; recovery
does not upgrade either binding or Run identity. Consumer routing/restoration
must use the retained original producer context, not infer a caller request from
another consumer material body. This producer admission adapter alone does not
establish the complete consumer, approval or release path.

`prepare_native_resident_effect_review_from_original_materials` obtains this
journal from the actual holder context's material Owner before calling the
existing Result capture/Receipt/Captured Run and review preparation path. It
accepts no caller-supplied normalization argument. Independently trusted Provider
policy is unchanged. If restoration or review preparation fails, the existing
context close/retry Owner retains any pending pins; Source, Transfer and holding
custody remain separate. The existing trusted-context API remains available for
other explicitly installed normalization profiles. No profile fallback or
Native CLI installation is implied by this adapter.

## Consumer reconstruction from the original producer

An Effect consumer selects its original producer only as a bounded journal
lookup address from the retained-input binding. This projection is not checked
edge admission or completion evidence and does not grant a borrow, reservation,
start claim or current authority. The existing full retained-task route admission
still verifies the checked edge, producer evidence and Transfer receipt.

Before consumer material admission, the Native Host reads the exact producer
envelope from its existing journal. Its dispatch identity must match the lookup,
and its Source binding must match the original checked Source issuer. The
request admitted from that separate original binding supplies the expected
request for both the saved producer materials and candidate consumer materials.
Candidate materials cannot select or replace this original request. Run,
authority and the installed same-Site execution scope must agree.

The retained consumer uses the same journal context at preparation, acceptance
and execution. Receiver custody, current authorization and lifetime, exclusive
start claims, cancellation and cleanup remain with their existing Owners. A
journal lookup or normalization restoration alone does not establish any of
those facts. Missing original journal custody is refused; it does not create a
replacement request or repeat Source acquisition.

The legacy direct executor has no independent producer context and refuses
normalization-bearing materials, including a finite-profile candidate with an
absent request. Its shared material decoder can compare an independently trusted
absent expected identity, but the direct executor cannot select that expectation
from the candidate. Ordinary absent-journal materials retain their existing path.

## Mapped-create Preview from a retained consumer Result

The Native review connection projects create requests from the actual held
consumer Result through the existing checked proposal export and Catalog request
Owners. It checks the original preparation, Run definition, typed request,
member, mapping and current receiver borrow. Only a complete export with its
matching Receipt produces the opaque, bounded `NativeResidentEffectCreatedTargets`
projection. Its request array is private; callers cannot replace rows after
projection. Failure leaves physical input and cleanup custody with the original
Owners and grants no write permission.

The shared create-row inventory Owner derives sorted content/occurrence
correlations from those requests. A create Preview has absent before-state and a
`not_applicable` guard, rather than an observed existing target or an update
version guard. The Native review therefore makes no Provider target-read call for
this operation. Duplicate equal rows retain distinct occurrences. Source,
local-artifact, request-scope, capability and Preview binding remain with the
existing Owners.

Mapped create has a checked create-row terminal, not a correlated update Plan
terminal. It does not mint a substitute update Plan proof. The existing captured
Run path requires that proof only when a Plan identity is present; update review
continues to require and verify its Plan proof. The nominal create projection is
process-local and remains tied to the same consumer and captured inputs. It is
not durable approval, a physical target observation or a mutation permit.

The approved-row adapter supports one admitted create or update request. For
create it retains the original Catalog binding's origin, validates the exact
content/occurrence correlation against the held request, and does not fabricate
a target observation. Update continues to require its original observed target
and version guard. A current credential scope must match the typed request's
distinct mutation operation, original invocation, dispatch, Site generation and
resource origin. Only create selects POST; only a guarded update selects PATCH.

The original review and resolution Owners still establish approval and the
current resume fence. Before either verb is sent, the same journal claims the
existing Ledger dispatch; an existing claim is a reconciliation obligation,
not permission for another send. Both operations retain their raw response
through the same save/retry and typed outcome projection. Reconstructing row
custody never grants permission to write. Empty or multiple create rows remain
explicitly unsupported by this single-row adapter; those implementation
boundaries are not restrictions on the language's create semantics.
