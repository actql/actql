# Durable submission identity

A durable submission identity precedes checking and Run-definition issuance.
It consists of an authority-issued authenticated epoch and a caller-allocated
nonce. The Client retains both, together with the exact submitted intent, before
the first send. A reconnect does not replace either component or retry work.
Neither this identity nor its digest is execution, lookup or cancellation
authority. Those operations still check current authorization.

The common logical-request owner admits the epoch body and derives the
submission identity. The Host authenticates the body's provenance and retains
the validation material and expiry watermark in the existing request journal.
An unverified ticket must not be passed to execution as an authenticated fact.

## Fresh Journal initialization durability

A new request Journal is not exposed until all original SQLite initialization
transactions and marker-file writes, file syncs and closes have completed,
followed by one actual sync of their common containing directory. These names
belong to the same unpublished initialization, not separate business commits.
An existing database's additive format adoption retains its immediate per-marker
directory acknowledgement. Unchanged reopening does not repeat initialization
writes or issue another epoch key. A failed final directory acknowledgement
returns no Journal and follows the same captured native-connection cleanup;
neither cleanup nor visible files stand for that failed acknowledgement. The
original typed format, key, current authorization and business transaction
checks remain independent.

## Identity domains

The `actql-submission-epoch/0.1` canonical body has exactly these fields, in
canonical key order:

- `authority_scope_cid`: the admitted Host/authority scope CID.
- `epoch_nonce`: 32 authority-generated bytes encoded as 64 lowercase hex digits.
- `expires_at`: exclusive upper bound in integer Unix milliseconds.
- `not_before`: inclusive lower bound in integer Unix milliseconds.
- `version`: `actql-submission-epoch/0.1`.

Both times are nonnegative, exactly representable safe integers; negative zero
is not admitted. The upper bound must exceed the lower bound. The epoch CID is
SHA-256 of the exact canonical body. Physical authentication also covers that
whole body, including the authority and both bounds. A digest alone does not
authenticate an epoch.

The `actql-submission-identity/0.1` canonical preimage has `caller_nonce`,
`epoch_cid` and `version`, in that order. Its SHA-256 CID is the submission's
internal caller ID. The nonce uses the common 0.1 logical-request caller-ID
domain: at most 256 UTF-8 bytes, already NFC/LF canonical, and no controls.
Invalid nonce spelling is rejected, never normalized. This identifier rule
does not normalize submitted source, parameter values or other data strings.

The existing `actql-logical-request/0.1` Run/Effect scope and checked-intent
preimages remain unchanged. A new submission's CID can be supplied to that
existing owner as its caller ID. Historical records retain their original keys;
they are not rewritten or relabeled as epoch-bound submissions. A submission
identity must not be presented as a Run-definition CID before a Run exists.

## Admission and custody

The SDK captures and deeply freezes the original submitted body before
publishing it. Its public snapshot shares those exact input and parameter
subtrees in a shallow-frozen wrapper. The connection owner freezes its captured
wire and scalar arrays; the SDK freezes the new lookup context separately.
Constructing the wrapper does not traverse the submitted body again. External
input still takes full capture and deep protection, including mutable children
of a caller's shallow-frozen object.

The Common input preparation can consume the admitted intent together with its
same immutable canonical value and bounded decoder view. An already canonical
input reuses its original parsed source; differently spelled input retains the
canonical-wire parse used for diagnostic coordinates. These facts stay within
the immediate preparation, without extending the intent's stored fields or
creating a cross-operation cache. Program, declaration and value checking,
current authorization and durable request admission remain separate.

Journal acceptance captures bounded admission evidence as owned DATA and checks
the actual serialized payload. An intent CID added by the same Journal retains
its identity and final byte-bound checks. Selected saved evidence can reuse the
captured facts only for identical complete wire, or wire with only that checked
CID added; changed bytes take full admission. The captured value and decoded
Model binding stay within this acceptance. A new stored observation admits its
current evidence independently. These facts supply no epoch authentication,
Run issuance, Source permission or Effect permission.

The Node journal issues tickets with a configured positive lifetime no greater
than seven days. It retains one authentication key and a monotonic observed-time
watermark in the same journal, rather than an unbounded per-epoch list. Tickets
from another journal cannot authenticate, even under the same authority scope.
Missing or malformed retained validation material is not recreated as though
the original history had never existed.

Admission time is checked against the maximum of the current clock and
the retained watermark. An expiry observation survives process restart and
clock rollback. A missing request record under an expired identity cannot
authorize issuance. Nor may a lost replay record under an unexpired identity
be interpreted as unused: the existing submission-custody fence still applies.

For an epoch-bound admission, the original binding is authenticated before
Run-definition issuance. One public operation retains its deeply frozen epoch,
Common handle and authenticated key binding through its internal continuations;
an internal await or trusted Journal read does not repeat that authentication.
Atomic acceptance still checks the same current key, authority scope, retained
intent and interval. A changed key must authenticate again, and a new public
operation acquires its own facts rather than inheriting the previous operation.
One durable clock floor covers unchanged internal observations. Crossing an
interval boundary records the new monotonic observation before returning it;
the actual retained row, not a pending memo, establishes durable acceptance.
Expiry at that boundary commits only the watermark, not a Run or
an issuance-count advance. A retained matching acceptance may still be
identified after epoch expiry without issuing another Run. Changed intent
remains a conflict under the existing common identity relation.

Run resolution admits its supplied logical-request identity once. If all seven
stored identity fields exactly match that admitted original, the same entry
uses it for the common relation rather than admitting identical bytes again.
A distinct saved identity is independently admitted before the existing
conflict decision. The admit-or-lookup entry uses the same private resolution
step before issuance; a retained Run never calls its issuer. Atomic acceptance
after an issuer callback retains its original validation and race handling.
No identity or permission is cached across resolution calls.

Expiry is an admission restriction, not proof of nonexecution. Missing,
expired or inaccessible outcome evidence must preserve the unresolved original
reference. Durable terminal rejection consumes an identity; noncommitted
attempt refusal does not. An accepted preparation failure remains accepted
even if no Run definition was issued. These facts must remain separate in the
public protocol, and unknown replies cannot establish any of them.

Starting deliberately new work after an unresolved original requires the
explicit authorized risk-acknowledgement transition and its retained link.
Changing the epoch silently is not that transition. It does not permit automatic
resending of unknown Effects or bypass their existing reconciliation owner.

The Node public `restart-intent` operation carries the ordinary submitted intent,
an explicitly retained fresh submission reference, and `unresolvedHistory`:
`{submissionRef: originalRef, acknowledgement: 'possible_prior_execution_and_effects'}`.
The SDK exposes this through the matching submission option; an acknowledgement
without a caller-retained fresh reference is refused before send. Ordinary
submission, reconnect and lookup never choose this operation automatically.
The intent CID retains its existing preimage: the decision is a separate binding.

The existing journal authenticates both references in the currently authorized
scope and checks the original's expired, unresolvable history before preparation
and again at atomic receipt acceptance. The fresh receipt and decision link are
saved in one transaction. The audit link also records the Host-authenticated
actor, never a caller-selected actor. A matching fresh identity cannot change
its intent, original reference, acknowledgement or actor. Deliberately distinct
fresh identities each require their own explicit decision. Increasing epoch
expiry bounds prevent cycles in these links.

Authorized lookup of the fresh reference projects the retained original reference
and acknowledgement with its outcome, including after journal reopening. It
does not resolve the original outcome. The public projection does not expose the
audit actor. Missing link custody fences admission and cannot be repaired as an
ordinary submission. Link storage is independently bounded and is not retired
when a pre-Run receipt is retired.

This connection admits new work only when original intent custody was formally
retired, or the expired original has no retained intent and the journal's issuance
custody remains intact. An existing original Run requires its existing
reconciliation owner; the risk acknowledgement cannot discharge Model, Effect,
publication or cleanup responsibility. Lost issuance custody also refuses new
work. Neither refusal nor successful new work establishes that the original did
not execute.

## Scoped durable request names

The public Python `request_id` and Node SDK requestId-only conveniences denote
a scoped durable name for
one original submitted operation, not a nonce to reuse under each connection's
new epoch. The existing request Journal resolves or binds the authenticated
workspace/actor/name key before preparation or I/O. Its authority scope and
original submitted intent are immutable. A changed scope, input, readOnly or
stopBefore choice conflicts instead of issuing another Run. Names are not
lookup, cancellation or execution authority; the Host rechecks current scope.

The physical index belongs to this same Journal and transaction owner. First
binding records the original epoch-bound preparing intent and its name together
under `BEGIN IMMEDIATE` and confirmed COMMIT. An existing binding returns that
original reference and outcome; a newly supplied connection epoch is not its
replacement. Only the first confirmed insertion can enter preparation. Merely
observing a preparing record, including after response loss or reopening, does
not establish permission to repeat its work.

The private index is authenticated with the existing Journal's epoch custody
key, covering namespace, actor, exact name, authority scope, submission identity
and intent identity. This authentication is neither a canonical public CID nor
a bearer permit. The key and original Common-admitted epoch/intent remain
necessary. Equal-looking data from a different Journal cannot issue a reference.
Old explicit epoch nonces are not searched, inferred, or retroactively named.

The SDK retains the exact candidate reference in its captured submitted input;
that input is not a durable binding certificate. Its named invocation envelope
is validated against the original name, intent, attempt and current authority
scope before an observed older reference can be used. An explicit
`submissionRef` with an optional matching `requestId` remains the old nonce
assertion and unchanged explicit submission packet. Transport loss retains
Unknown; neither an error code nor an unavailable named supplier selects a
legacy operation, automatic restart or new preparation.

An existing same-Run submitted-content handle retains its admitted request,
Run and intent facts. Its current check still reads the selected Journal rows,
epoch key and restart linkage under the same transaction and checks issuance
custody. Identical scalar rows reuse those immutable facts instead of repeating
decode, hash or reference serialization. A changed row or key re-enters the
existing validation, and a failed observation discards the retained facts.
The decoded intent remains private to that handle; public submission records
retain their wire shape. A new handle performs its own admission. None of this
supplies current Account authority, a resume/physical-start claim or an ACK.

Names have finite admission capacity under the existing Journal limit. There
is no automatic eviction: formal pre-Run intent retirement leaves its named
binding unresolved and occupied rather than making the name unused. Missing
or corrupt custody refuses new binding. A transaction-maintained retained count
and monotonic issued count fence deleted names; physical startup checks the
index/cardinality and trigger definitions without retaining an all-history JS
array. Normal resolution uses the exact indexed key and singleton control, not
a scan of historical Programs or a process-local name cache. These controls are
not a claim of whole Host heap funding or unlimited permanent name capacity.

The Native adapter uses the original generic SQLite record table for this
extension. Its issued control is updated by the existing Journal CAS, while
exact insert/delete triggers maintain retained cardinality in that same
transaction. Trusted fresh initialization creates the extension; restore only
checks it. Startup verifies the original trigger definitions, closed controls,
indexed census and authenticated name rows. Ordinary name resolution reads the
exact name key and the original controls, without repeating the name-wide audit.
These predicates do not discharge the inherited Run/Policy/Effect custody
validation at the outer transaction boundary. That independent dependency must
also close before the public ordinary path is described as historical-scan-free;
its checks cannot be skipped or cached as proof for the name index.

The closed `submit-named-intent` packet carries the exact `requestName`, ordinary
submitted intent and intent CID, operation attempt, and a newly retained candidate
submission reference. The candidate is used only when this same Journal confirms
that the name has never been bound. An observed reply correlates the same name,
intent and attempt with the original authenticated reference, which can differ
from the candidate on reconnection. Refusal certifies only this uncommitted
attempt; conflict does not replace any saved original. The name uses the same
bounded caller-ID string domain, without normalization or coercion.

The old explicit-epoch submission response still requires its original exact
reference match; it is not weakened to accommodate named resolution. A named
observation can include the existing initial check observation, but never
manufactures it on a later lookup. Missing retained outcome, formal retirement,
and ambiguous transaction outcomes stay unresolved. An existing preparing name
is observation-only; it does not grant automatic continuation or resend.

This is an intentional extension of the initial contract, not reinterpretation
of a bare legacy request ID or a per-client mapping from a name to a fresh epoch.
The existing explicit-epoch and explicit-risk-restart paths retain their own
identity and uncertainty rules. The private Journal primitive alone does not
establish a public installed Python producer/consumer or whole Host funding.

## Submitted intent and outcome projection

`actql-submitted-intent/0.1` identifies the original JSON submission before a
checked Program or Run definition exists. Its canonical preimage contains
`intent` and `version`. The intent has exactly `input`, `kind` (`program` or
`aql`) and `parameters` (object or null), with an optional `stopBefore` whose
only admitted value is `"commit"`. Omitting that choice preserves the existing
three-field canonical original and CID. Selecting it adds the field to the same
preimage; it cannot be changed for an already retained submission identity.

### Original short-query continuation

The initial0.1 contract deliberately extends this same original with optional
`readOnly: true`. Absence preserves every previous byte and CID; false, null
and alternative spellings are not admitted. The choice participates in the
same canonical preimage and retained journal intent. Reusing a submission
identity with another choice is an intent conflict, not a replacement Run.

The installed preparation pairs that opaque intent with the same original
Common preparation. Common reads its complete checked Effect inventory before
Source acquisition, Model invocation, Effect Preview or dispatch. Any Effect
occurrence is incompatible, including zero-row, unreachable or currently denied
Effects. A final stage, emitted count, source keyword or separate check cannot
prove that restriction. General startSource without the choice is unchanged;
Node and Python short queries select it on their original submit packet.

This restriction is not an Account grant or stop-before-commit request. Even
when both choices occur, approval cannot release read-only into a write.
Effect-free Source and Model work retains all existing current authorization,
egress and resource obligations. Recovery reads the original durable intent
and existing Run/material admission, never a current configuration or caller
label; no equal-CID substitution or new preparation supplies original custody.

### Requested first-Effect stop

The choice restricts the original Run's first Effect continuation through the
existing Checkpoint owner. Its approval releases that user-requested restriction,
not Account authorization; current Deny and genuine Delegate requirements remain.
The closed DATA shapes are registered as `submitted_intent` and
`installed_effect_continuation` in the existing Client–Host machine contract.
The selected private continuation carries `requested_stop.intent_cid`, the same
Run Definition, explicit Effect Unit and sealed Preview, alongside the original
provider DATA and optional target-read binding. The existing evidence owner hashes
the exact canonical bytes. A requested-stop Checkpoint must bind that exact
continuation content CID; omission, substitution or a noncanonical rewrite is
not an alternative representation of that selected original.
Cold continuation uses the same saved Effect Run-materials codec and its actual
original request, compiled owner, policy evidence and Run Definition. A selected
target's retained original already carries that codec and is not duplicated.
For a requested stop without that target record, the existing request journal
retains the bounded `effectOriginalRunWire` in its original admission evidence.
Missing material is not reconstructed from current installation configuration.
The Common owner binds the re-admitted material to the historical Preview and
Invocation before projecting the same requested-stop continuation. It does not
recreate a captured live input borrow, Compute, permission or a resume claim.
The existing Journal's approved Resolution, same-Run claim and one-shot entry
separately own fulfillment; current Account decisions still own dispatch.
Source text, declarations, parameter
values and data member names are preserved by the common value canonicalizer.
This receipt provides no checker verdict, execution authority or Run CID.

The existing request journal separately retains the authenticated epoch/nonce,
intent CID and canonical original, admission time, phase and observation
revision. Known preparation refusals committed before acceptance are terminal
`not_accepted` outcomes. After acceptance, preparation failure is
`preparation_failed`; it cannot retroactively become a pre-acceptance rejection.
`preparing` records contain no invented Run reference. A supported `held`
request retains the existing prepare-attempt/Checkpoint owner. `ready` refers
to a Run whose binding is independently checked against the same request
journal. Terminal outcomes are immutable; stale observations cannot replace a
newer committed outcome.

The initial epoch-bound public path does not admit pre-Run approval waits: its
complete response, cancellation, expiry and lost-response recovery contract is
not yet exposed. Preparation and Source-read delegation without an immediate
permit use the existing authorization gate's unsupported outcome before
sealing evidence or creating a Checkpoint. A refusal after the intent was
accepted is a preparation failure. Run-scoped Model and Effect approval paths
continue to use their existing owners.

An accepted preparing or held intent can finish preparation after its epoch's
new-admission interval ends. The original persisted receipt establishes this
fact, rather than a supplied flag. Its current authorization is checked again
after asynchronous preparation or lookup. Missing intent custody fences writes;
a missing original is publicly unresolvable, never proof that nothing executed.
The journal stores intent rows and their issuance counter atomically. Storage
admission is bounded independently of checker or execution capacity.

An explicit trusted-Host retention operation can retire an expired terminal
pre-Run refusal or preparation-failure receipt at its exact revision. It
authenticates the original epoch and current scope, uses the persisted monotonic
expiry watermark, and removes the row atomically with an advance of the existing
journal's retirement counter. Issuance remains monotonic: issued intents equal
retained rows plus formally retired rows. Unrecorded row loss still fences writes;
adopting the retirement feature records zero retirements and cannot repair lost
history. No admission automatically evicts records to make capacity.

Preparing, held and Run-connected receipts are retained by this operation. It
does not delete a Run, Effect responsibility, response, Result or cleanup receipt.
Retirement is not cancellation, rollback or proof that no work occurred. Lookup
of the expired original becomes unresolvable, while its expired identity cannot
admit new work after restart or clock rollback. The explicit authorized
risk-acknowledgement and old-to-new submission link use the separate public
restart operation; this retention operation alone does not implement that exit.

Both ingress transports validate the original submission reference and intent
CID. The Local ingress owns nested JSON before awaiting caller authentication.
A submit exception can follow a successful Run COMMIT, so the adapter looks up
the original Run before projecting a typed preparation failure. The public
request lookup does not carry a Run control revision: projecting a `ready`
admission obtains that revision from the authorized journal record.

Only an input-bearing submission preparation can lend its original submitted
intent to that operation's Journal scope. Read-only submission lookup retains
the epoch operation and rechecks current Journal authority, but does not ask a
Source producer for an input borrow or recreate a live preparation lineage.
Missing history remains unresolvable. This distinction supplies neither
capacity nor execution permission and does not bypass stored-record admission.

The SDK allocates a submission reference before sending and retains it with the
detached input on the returned Promise, Run or original error. Callers can save
the original before the first send; this in-memory snapshot is not durable
custody or proof of acceptance. A known unsent local attempt is distinct from
an unknown response and from an Owner-issued terminal rejection. Lookup takes that exact
reference; a newly issued connection epoch cannot replace it. Historical
bare-request observations remain in their existing identity domain and are not
reinterpreted as epoch-bound receipts. Starting new work with a bare historical
request ID or a Host without an epoch does not select a legacy execution path.
