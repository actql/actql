# Local input preparation ownership

## Responsibility and scope

The Node Local preparation owner bounds construction before the ordinary SDK
snapshot and retains the resulting checked Program through dispatch retirement.
It is not a second evaluator, a Run permission, or a replacement Store budget.
The selected own-data numeric Values recipe invokes the existing parser,
normalizer, checker, lowering and installed sequence implementation.

Other frontends and input shapes must keep their existing semantics while
joining this ownership protocol. An inapplicable shape proof is not a language
restriction or permission to invent a resource grant. The presence of this
recipe does not establish complete funding coverage for every Local route.

## Inputs and outputs

An original input reference and the installed Local resource policy enter the
protocol. Work-authorized inspection produces checked extents, not authority.
The same preparation owns the SDK snapshot share, input document, parsed
indexed source, checked Program and retained sequence preparation. Read-only
capacity observations expose scalar counters only; no mutable Ledger escapes.

Installed contract originals contain validated immutable contract data. They
do not issue resources or permit dispatch. Request originals, installed
contracts and resource children are separate identities.

## Identity and currentness

Every transition checks its original preparation and original input/child.
Equal-shaped objects, copied records and a different installed runtime cannot
substitute for the original. The Common owner remains authoritative across
the SDK's derived request associations and the Node manager/handler/dispatch
holders. No serialized receipt recreates that authority.

Stopping forbids new funded work and reservation growth. Cleanup may construct
its required wrappers and has a separate same-original check
that permits disposal after stopping while still rejecting an unavailable or
foreign child. A refusal, an exception, or a cleared JavaScript reference is
not evidence that the child's physical cleanup completed.

## State and lifetimes

The initial reservation precedes input inspection. Phase transitions resize
that same reservation before construction; they do not obtain a second pool.
Retained extents cover references that survive a phase. Temporary extents
cover the constructors that are actually live in that phase. Overlapping
owners are additive. Sequential phases may share capacity only when source
lifetimes prove that the earlier constructors returned and no temporary alias
escaped. This reuse applies to successful returned constructors; failure-owned
Issue, Cursor and raw-cause references remain funded while live.
Garbage-collection timing is never a refund witness.

The SDK may publish an immutable submission snapshot to its caller. The
publication receipt records that handoff; it does not revoke the caller's
value when the Host closes. Host-retained aliases remain funded until their
own cuts. Returning a consumed holder and retrying retirement must not return
the same accounting debit twice.

After adoption, the existing manager, handler and dispatch holders retain the
same preparation. A submission-journal failure before dispatch still requires
retirement of that original owner. Uncertain outcomes retain their existing
custody and retry identity rather than being converted into definitive refusal.

## Work and storage units

The representation policy prices named record headers, reference slots,
scalar words, UTF-16 units and wire bytes using checked arithmetic. Constructor
inventories and the runtime consume the same policy. A logical charge is not
an operating-system allocation measurement or an RSS guarantee. Opaque engine
and selected Host-service support must remain explicitly qualified.

Wire length, parser node support, retained values, publication metadata and
durable Store capacity are different quantities. For JSON value-node support,
UTF-8 wire extent provides a structural upper bound, subject to an explicitly
narrower installed policy; it is not an additional memory grant.

The Ledger exposes reserved retention/execution, held bytes and its stored
retention peak. A sequence of execution observations is a sampled maximum,
not a stored execution peak. Reports must identify the exact runtime/model
cohort and distinguish requested bounds, actual reservations and observations.

## Failure, cancellation and publication

Refused growth must leave the previous reservation intact. Cleanup preserves
original identity and requires witnesses for child cleanup, retained-alias cuts
and settlement of the same reservation. Their order follows custody: pre-adoption
alias cuts may precede child cleanup, whereas an adopted owner is fenced first.
A pending cleanup remains pending; a retry cannot grant
new execution or silently drop retained references.

Result publication and physical-stop observation are independent. A successful
Run can expose a Result before cleanup finishes. Tests must observe the actual
cleanup barrier and durable stop state rather than infer stop from an earlier
terminal-status snapshot. Current-version close/reopen must retain the exact
published result and identity; no old-runtime migration path is implied.

## Extension boundary

Additional shape recipes must enter the same original owner and use the same
units, checked arithmetic, holder transitions and cleanup witnesses. They must
not retain an obsolete evaluator or bypass a failed proof with an unowned
path. Source acquisition additionally needs its own native-session/resource
custody; a Compute quote cannot substitute for a Source owner.

## Verification boundary

Repository regressions cover exact and one-short budgets, foreign originals,
stopping versus growth, consumed-holder retries, concurrent failed submission,
caller snapshot handoff, actual public publication/readback/close/reopen and
streamed result count/value oracles. Source-runtime guards validate workspace
package realpaths, selected Core artifacts, canonical adapters and module
hashes. Separate calculators must match that complete model cohort before
their numbers are attributed to an executing runtime.

Source-only checks, diagnostic instrumentation, a different backend, and a
hosted distribution/CI gate are distinct evidence. None may silently stand in
for another.

## Selected Model limit composition

The common Ledger owner composes nonnegative `LedgerLimits` in their six
original dimensions, refusing overflow before a sum is formed. Retention and
execution remain independent. This immutable DATA operation does not select
a policy or create, reserve or debit a Ledger.

Installed Model requirements add the existing Model allowance and two
simultaneous read/bootstrap contributions through this checked owner. The
private six-number Run projection is updated only after every dimension fits;
refusal leaves it unchanged. The original read reservations, census, current
checks and cleanup remain with their existing owners. A composed numerical
limit supplies neither physical backing nor permission.


## Canonical normalization construction inventory

The canonical-value owner declares the logical construction inventory of its
existing NFC-plus-LF operation. Local snapshot preparation projects those named
units into its existing representation model rather than retaining a second
Unicode expansion or string-builder formula. This preserves the original Local
reservation; byte pricing and resource admission remain with their existing
owners. The input String is borrowed, and the returned String is covered beside
current constructor scratch. Multiple retained results require cumulative text
and reference inventory.

The pinned canonical decomposition expands to at most four scalars per input
scalar; compatibility normalization and casefolding are separate operations.
JS concatenation and the pinned non-JS doubling UInt16 builder have different
backing lifetimes. Growth and the final `to_string` copy do not coexist. Both
recipes fit the declared logical bound, including preceding NFC and first
LF-pass text during the second LF pass. This is a constructor inventory, not
allocator/RSS, physical backend supply or complete preparation funding evidence.


## Structural Program container owner

The syntax owner supplies the retained shallow Program container inventory from
its existing bounded structural construction facts. It owns the Program/Stage
records, original import variants, public export tuples, array spare capacity
and name-index maps. The same record projection supplies their coexistence with
constructor scratch, so the Local adapter does not repeat their field layout.
Shared preparation representation rules still perform byte conversion and
composition. These facts issue no execution, physical allocation or permission.

The fixed Closed Values shape consumes that same owner for its established
one-Stage/no-import/one-export envelope, preserving the original quote. General
structural facts can include multiple Stages, imports and Results without
pretending that their Source body is a numeric Values document. The bounded
inspection remains with the original indexed source; it is not another parser
or semantic checker.

This inventory excludes source/index backing, normalized identifier text,
temporary object views, inspection/diagnostic controls and semantic
checking/lowering/module construction. Those actual simultaneous owners must
be supplied before a generic preparation driver can claim complete funding.
The existing narrow constructor scratch proof stays scoped to Closed Values.


## Preparation count arithmetic below domain constructors

The existing capacity arithmetic owner supplies exact nonnegative Int64
sum/product composition for preparation counts. Domain constructors below the
execution layer can use that same operation without introducing a dependency
cycle or a second overflow rule. The execution preparation API delegates to it;
its positive coefficient rule and the original representation tariff remain
unchanged. No raw source, physical allocation, permission or Ledger is issued.

Language capacity Values keep their separate nonnegative safe-integer range.
An Int64 preparation result cannot be promoted into that opaque Value, and a
large count never widens a language bound. Zero/negative coefficients, negative
counts and overflow keep their original preparation refusal. The existing
accounting and actual backing/retirement owners remain responsible for admission
and physical duties; arithmetic alone does not establish complete phase funding.


Installed Effect demand keeps its distinct zero-byte domain case: a
nonnegative original count adds no bytes to a nonnegative total. Its positive
products delegate to the same checked arithmetic owner as the Local preparation
tariff. That domain case does not change the shared operation's requirement
that its coefficient be positive, nor grant capacity or refund consumed work.

### Ledger usage observations

The Core `LedgerUsage` declaration owns usage field order and primitive width.
The existing transport generator projects both the complete typed usage array
and the spent-field exclusions from Core's pending-resource predicate. Strategy
and MultiCaptured observations use that same projection; the shared Host
adapter refuses missing, extended or malformed layouts without padding them.

Cleanup distinguishes current occupancy from cumulative spent work and history.
Zero-byte reservations, attempts, holdings and delegations still remain current;
the generated predicate alone supplies the exclusions. Diagnostic decimal text
preserves every original counter. No counter projection grants capacity or
permission, resets spent facts, proves physical stop or replaces the existing
Site/current/retirement duties and preparation-isolation checks.
