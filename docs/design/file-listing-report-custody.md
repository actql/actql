# File-listing report custody

The completed listing requirements in [Source Evidence](../spec/protocols/run.md)
remain unchanged. Original five-field report correlation, the same captured
scan and funded lifetime are required for corrected report conformance. The
ordinary resolved listing path retains its original capability scope and
evidence bytes during corrected-writer activation. It does not satisfy those
report requirements, supply report authority or establish Model admission.
Missing original correlation cannot be relabelled as a completed empty report.

Only the dedicated accounted listing entry selects report backing after the
original Source Ledger reserves the supplementary envelope. The same Row
acquisition, capture and cleanup owner retains that backing and execution
allowance through evidence encoding. The explicit report-evidence issuer
refuses an ordinary resolved listing, including a genuinely empty one. Selecting
this path does not change the Source-declared listing input, Source permissions,
wire identities or the evidence writer's existing bounds.

## Declared listing metadata

The existing listing Owner admits a required canonical role base: `resource`,
`version`, `name`, `path`, `media_type`, `size_bytes` and `modified_at`. This is
not an exclusive seven-column schema. The complete published Source schema
also governs additional typed metadata, including Local `size:Int64` and
`modified_time:Timestamp`, which remain directly visible through `LIST_FILES`.
Canonical nullable metadata may be refined to nonnullable by that schema;
missing or NULL values then fail its ordinary row admission. Required role
presence, Resource kind, nonnullable resource/name and version capability do
not change. Extra fields do not repair a missing or mistyped canonical role.

The profile's `listing_schema_contract_cid` identifies the complete actual
output schema. Schema checking, acquisition, duplicate comparison, capture,
Result and restoration retain that same full typed row, including empty
listings' schema. Additional contracts, fields, values and bytes consume the
existing bounded work and retention budgets under the same Source lifetime.
No Int64-to-Number or Timestamp-to-Host-Date coercion is introduced. Related
native and canonical metadata originate from the same physical observation.
Unchanged seven-role bodies keep their original bytes and identities.

The corrected report remains its separate fixed correlation record. Extra
Source metadata is not a report member, issuer, grant, funding proof or cleanup
acknowledgment; its original scan/capture/funded-lifetime obligations remain.

The ordinary installed Host wiring does not yet provide the justified physical
report supplier or the Source-to-prefix dependency/debt handoff. Ordinary LIST
success must not be advertised as corrected report support. Report activation
requires those existing-owner connections and their physical lifetime checks;
neither a numeric declaration nor legacy Source evidence substitutes for them.
The existing closed-prefix guard remains required, and no new Owner, grant,
cleanup queue or Model funding profile follows from these primitives.

## Physical timestamps and logical listing values

The GCS listing transport retains the original response and charges its exact
bytes before projection. The ordinary provider projects `updated` through the
same exact GCS temporal function used by its object table. The resulting
`modified_at` is canonical UTC Timestamp data; it neither replaces the retained
physical report nor changes Resource/version identity. Short physical fractions
are padded to milliseconds, and finer fractions retain their exact instant with
only surplus trailing zeros removed. No Host `Date` or binary64 conversion is
involved. Invalid metadata refuses before any item is offered to the Resource
issuer. The explicit historical source-only ABI remains a distinct unchanged
compatibility boundary, not ordinary provider qualification.

The normalized timestamp references and strings coexist with the original
decoded page until its bounded envelope is consumed. They remain part of the
same read's finite projection/capture inventory. Normalization supplies no
transfer allowance, Source grant, listing completion or physical cleanup ACK.
