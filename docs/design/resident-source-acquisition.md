# Resident Source acquisition

## Selected installed runtime verification

Source and Effect installation bind their Site to the exact selected runtime
byte digest. Each installation rereads its original runtime file: an ESM module
namespace, path, timestamp or previously observed CID is not immutable artifact
custody and cannot replace that read. The shared configuration-file custody
keeps the original open handle through both reading and close; a pending close
refuses installation and retains the same retry without reopening or rehashing.

Runtime hashing updates SHA256 incrementally with one reusable 64 KiB input
Buffer. It preserves the full byte preimage, including partial reads and binary
bytes, without accumulating a full runtime Buffer. That local workspace choice
is neither a file-size/work ceiling nor a numerical funding or whole-RSS claim.
The digest does not replace original module/runtime correspondence, current
configuration, credential authorization or installation admission. Configuration
JSON/text readers retain their original bounds, codecs and failure behavior;
streaming hashing does not turn those materialized configuration values into a
shared cache or change their identity.

The resident Site executes a checked acquisition task with the existing native
DuckDB acquisition owner and the standard remote runtime. Its initial installed
profile supports one read-only Source, one checked task and one named Result.
Other checked shapes require their dispatch and retained-input edges to be
installed; sharing a Site does not combine those tasks.

The Program and Run materials contain logical Source references. The Site
operator supplies `--source-ref`, `--source-contract-cid`, `--source-database`,
`--source-schema`, `--source-table` and `--duckdb-library`. All six settings are
required together. The Site checks the original Program's admitted Source and
the exact logical input binding before accepting dispatch. Physical database
opening happens only after the existing exclusive start claim, current lifetime
check and executor-entry observation. DuckDB opens the configured database
read-only with external access disabled.

The engine root contains the pinned `registry.json`, `values.json` and
`fragment.json`, plus the installed acquisition contracts `query-contract.json`,
`query-evidence-contract.json` and `query-two-receipt-contract.json`. The
expression-fragment contract admits the same filter/select sequence used by the
existing Local query-requirement owner. These files and the physical mapping
are operator configuration, never dispatch authority.

Run materials reuse the bounded materials codec and reconstruct the original
checked compilation, authorization, Run identity and lifetime. Source-free
Values keeps its existing compilation. Both enter the same resident admission,
start, Output, transfer and release lifecycle.

The live acquisition owner issues the captured input's logical identity and
Source evidence. A bounded `actql-remote-source-observation/0.1` binds their
original wires and capture interval to the dispatch, Run and task ordinal. It
is persisted atomically with the native managed Output observation and retained
with the Coordinator's first completed Output. Exact replay preserves its
bytes; another observation cannot replace it. Source-free observations omit
the optional member.

This transport observation is a candidate for publication, not read authority.
The receiving Host derives the expected Source and policy from the original
checked Catalog, verifies the dispatch's Run/task binding, rechecks current
authorization, and uses the existing completed-observation and task Invocation
owners. Neither authenticated transport nor a matching CID permits another
acquisition. Result schema and projection come from the checked Result port;
an additional publication Plan node is not an additional physical task.

The standard runtime retains the acquired input and its cleanup owner through
Output export and formal release. A failed export releases its pins; pending
payload cleanup retains capacity until physical deletion is confirmed. Export
cancellation uses the existing captured-input owner. Durable outbound
cancellation and restart guarantees remain separate contracts.

## Builtin DuckDB installation custody

The builtin profile supplies a complete checked Environment rather than a Row
Site or restored RowDeclaration. Its normal loader enters the same initial
Source owner before that Environment is checked. The profile's exact Source
reference selects its snapshot member; that member's original view-contract CID
selects the owning Catalog connector. A missing or ambiguous match refuses
construction. URI spelling and connector DATA do not issue a declaration or a
read grant.

The bound builtin constructor reserves the Account input, proportional physical
binding projections and retained wrappers on that same Source successor before
Account admission. The checked Environment keeps its original construction and
retained overlap. Static acquisition contracts use the same original FD reader,
including pre-read extent reservation, decode overlap and close-only retry. The
constructor registers its own adapter before returning; no provider callback
can register another object or bypass the bound factory.

A newly acquired authorization gate is retained before the installed-profile
wrapper or native constructor can fail. Its original close method is captured
before the first await. Closing prevents new preparation/acquisition immediately;
a false or failed close keeps the same gate and Source live. Only that gate's
true cleanup acknowledgement closes the registered Source construction. Query,
capture, publication and physical acquisition retain their existing owners and
checks; an initialization success does not authorize a read.

## Bounded installation documents

Source profile, Site and publication document acquisition shares a bounded
incremental reader. Each Connector retains its declared byte ceiling; JSON
profiles retain their own ceiling, while a publication identified by its exact
UTF-8 text uses the text projection without parsing and reserialization.
Binary signing keys and CA material are separate inputs. The ceiling limits
acquisition, not the decoded tree's heap size or a resource admission grant.

A failed or false close retains the original FD through the existing
initialization cleanup protocol. Retry is single-flight and close-only: it
never opens, reads, parses or starts another installation. No parsed value or
text is returned before that initial close succeeds. A frozen or readonly
failure is retained as a cause, not mutated into a substitute cleanup owner.
Snapshots retain first/latest close diagnostics and their original error
graphs; bounded reference count is not a byte bound.

A thrown read failure may be any JavaScript value, including `undefined`.
The cleanup facade retains that exact primary separately from the close
failure. Diagnostic message access is best-effort, never coerces non-String
values, and cannot prevent exporting the original FD's cleanup responsibility.

Namespace observation may remain unresolved when metadata cannot be read.
Pending original cleanup is not namespace uncertainty: installation must stop
and hand that same handle to initialization custody. If an adapter was already
acquired, its existing initialization cleanup retains it until the failed read
retires. Error projections must preserve the cleanup facet at the receiving
boundary rather than leaving it only on a nested cause.

The existing read buffers, chunk array/views, joined bytes, decoded String and
JSON tree overlap during projection. On failed close, original FD, retry/status
closures, single-flight Promise, exported carrier/cause, first/latest errors
and frozen status arrays remain owned until actual close. The explicit read-failed
flag, original primary reference and any diagnostic message alias also remain
within that same responsibility. An acquired adapter
and the outer initialization carrier can overlap them. These are explicit
holding components, not zero-priced allocations or a normal Model profile.
The same cleanup facet also retains the exact primary failure reference for
existing installation error projections, including read-plus-close failure;
consumers do not reconstruct that reference from error names or nested causes.
