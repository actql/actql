# Native Local Host binding

## Saved Run Plan inspection

The first ordinary Run acceptance retains the original compiler Plan and
logical-map view in its existing Run observation metadata, in the same Journal
transaction as admission. A private first-capture ticket joins the actual
checked preparation, compilation, Run definition and original admission
evidence. The saved metadata reader cannot issue that ticket. The optional
metadata preserves the prior encoding when absent and the existing per-record
intake bounds; an overflow refuses rather than omitting required new evidence.

`explain --run` selects the authenticated original Run through current RunRead
and the same targeted Journal lookup and physical operation route as status. It
rechecks the compiled Plan, Program and logical-map identities and current
authority before returning the exact saved view. It never reads a replacement
Program or parameters, replans, initializes a missing installation or starts a
Run. Legacy missing Plan evidence remains unavailable and cannot be backfilled
by lookup or repeated admission.

The returned existing RunPlanView contains the recorded compiler map. Its
static observation and unmeasured quantities remain explicit. This metadata
does not assert unrecorded runtime engine choices, measurements or execution
history, and the human renderer distinguishes it from a new static EXPLAIN.

## Same Request Effect preparation lifetime

The Native submitted-Request entrance retains the checker's original Pure or
Effect preparation and its corresponding typed constructor borrow. Common
finishes compilation and continues the same capacity once; Native does not
check, compile or continue it again to project that result. Effect first-sequence
preparation uses that same retained Request while the original Journal Read is
suspended. A Pure operation is activated only for the actual Pure requirements.
This handoff is preparation, not approval, Account authority or a durable Effect
Run supplier; unsupported execution remains unavailable.

Finite Policy lifetime preparation binds the original checked Effect identity
to the same submitted intent and Request before selecting execution support.
It does not require the legacy one-task Values execution profile. A pending
Retention neither admits a Run nor starts Source, Model or Effect work. The
actual material constructors and first acceptance retain their own shape,
current-authority and custody checks, including the legacy Values guard.
An already accepted Request instead reads its saved original Policy without
resampling it; changed identity or lost current authority still refuses.

The Native Model Effect caller activates its already retained Store operation
after accepting the same Effect originals and before borrowing that operation's
SQLite original. Activation checks the original current Journal Read and
unentered backed execution; borrowing an inactive operation is still refused.
This route does not construct another operation or confer Effect approval.
Activation or Store failure stays on the same command's cleanup owner.

The fixed Request's existing 4KiB internal control group covers the Native
completed-body carrier (one header, original-borrow reference and variant word)
after its resize has returned. Variable Program, compiler and provider bodies
remain separately reserved on the same parent before construction.

Cleanup returns the original constructor borrow before retiring its capacity.
Live borrowers or a failed logical settlement keep that exact capacity and
original prepared Effect. After successful logical retirement, the Request
severs the Effect's cached normalization/material backedges and drops completed
continuation/quote aliases before the physical Read waits for its last alias.
The normalization cache is not a physical owner; severing it cannot free an
escaped original, acknowledge cleanup or authorize reissuance. Physical-only
retry retains the same initial owner and never settles the transferred Unit
capacity again. Unknown stop outcomes stay Unknown; only actual Native Read,
domain and arena retirement supplies their respective acknowledgements.

## Native Project Mock declaration intake

The Native Project reader selects the same original configuration/profile and
reads its explicit connectors, Model registry, Catalog and answer declarations
through the existing bounded UTF-8 Reader. The Source data locator is retained
without opening its payload; the same Request's admitted Source must read it
under its own checked payload bounds and current custody. The declaration
Reader's 64 KiB limit is not a Source payload or Run limit. Task paths are relative to
the original registry file; Catalog, data and answer paths are relative to the
Project. Common admits the original connection/Catalog/registry documents and
public Task contracts. A Task's registered name and original provider selection
must correspond to that same registry and declaration. Equal separately decoded
registries cannot replace those originals. Missing or physically unclosed
files retain their original Reader failure; no empty-document fallback exists.

Successful intake remains in the existing command's Project record. The
profile's nominal cycle retires on both refusal and ordinary command exit,
before the enclosing Read can acknowledge cleanup. Partial intake retires that
profile while preserving any original Reader failure. This is declaration DATA,
not Source installation, a Model provider, Account permission, Reviewer or a
Run grant. Declaration intake does not select Native execution availability.
Only the actual same-Request Source/Model/Effect assembly, installed Host and
approval supplier can admit execution. Intake cannot select the packaged
source-free Host as a substitute.


The same command retains its Project before constructing Mock Model originals.
Each original answer, normalization and installation is retained before the
next fallible constructor. Construction invokes no Model callback or clock.
Its first failure remains sticky, so the caller cannot reinstall or silently
replace an incomplete original. Retirement visits those same installations
before answer/profile originals. An installation with live users keeps its
same entry and retirement position pending; it does not acknowledge the
command's physical Read. Only the existing Read/domain/arena owners report
physical closure after all command-held aliases retire.

Fresh check/business callers extend the exact selected installation Environment
with those same normalized Task originals through the common Task projector.
The ordinary Native Environment admission still checks the complete result;
no Host-side Task or contract table is reconstructed. One command retains the
original base and projected Environment once. Configuration-file currentness
continues to compare its original captured bytes, while the Request/check
reference consumes the projected semantic identity. Saved routes do not rebuild
current Project Tasks or replace a retained Run's Environment.

The same Project retains its Catalog's Source declarations before Model
construction. The Native adapter translates only public document fields into
the existing Relation restore input; Common remains the schema, acquisition,
correlation and contract owner. Private restore-field spellings cannot be
injected through public view fields, and unfamiliar fields are not dropped.
Original connection/Catalog correspondence and partial declaration prefixes
stay on the same command holder. These are initial declaration contracts;
File physical capability facts, published query aliases, Source/Content
capture and Effect installation still require their real same-Request owners.
No Source payload is read by this metadata construction.

Source Environment assembly retains the exact base and the complete generated
Catalog, contract, view and evidence members. It sorts their canonical member
identities and coalesces only byte-identical bodies; the ordinary Common
admission retains conflicting-selector refusal. Task projection consumes that
same Source Environment. A publication retains its exact final Environment,
restored view handles and requests once, and the original Request caller uses
that prepared publication rather than reconstructing an empty namespace.
These contracts and aliases remain trusted declaration DATA. Metadata alone
never grants alias disclosure, acquisition, Model execution or Effect authority;
the normal installation still requires its original current/account/service
connections before opening those operations.

## Ordinary literal query caller

Trusted public `sql` and literal `aql` select the ordinary Local Host when no
explicit Remote connection or legacy installation overrides that choice. A
project selection retains its configured Store and declarations. Outside a
project, the default Local installation is selected through the same bounded
configuration and current-authorization owners.

Operator-selected Program, declaration and parameter inputs split bounded
absolute or input-directory-relative metadata into an original filesystem Root
and an exact ordinary basename. The command's entered Read uses the existing
bounded UTF-8 Reader and retains its same partial failure through cleanup.
Managed installation/configuration names keep their separate entry. Reading a
file does not supply a parameter contract or bypass Common admission.

A genuinely absent default source-free installation may be initialized by
this caller under the existing Product exclusion and initialization intent.
The same adoption Session independently admits the Account, Store and required
purpose-confined physical crypto material. An existing initialization intent,
interrupted installation or missing adopted original never selects another
initializer, regrant or rekey. This caller does not register a Reviewer,
authorize an Effect or infer Mock consent from project metadata or query text.

The complete business facility is selected before acquisition. The original
submitted intent is read-only; its checked Program and current Run-submit
authority are admitted before epoch issuance and durable Submission admission.
The returned Run alone selects Result restoration, with independent current
Result-read policy. A same-command read uses the Store that published the same
request and keeps its Values, publication and delivery children until their
actual acknowledgements. It does not open a second Store or rerun the query
after an uncertain response.

The source-free Local entry quotes the original prepared graph before physical
acquisition. Its finite task inventory includes each input port and retains
predecessor outputs beside dependent task work on the same Run Ledger. The
executor follows the existing checked DAG, imports only its exact completed
producer references, and finalizes each original task once. It neither flattens
the submitted Program into a synthetic Values task nor turns a source-free
selection into Source, INFER or Effect admission. The legacy single-task Effect
entry keeps its separate admission and authority boundary. Named Result export
selects its checked physical task, not an assumed task zero. Refusal after a
completed predecessor retains all acquired task cleanup without restarting that
predecessor or selecting a replacement Run.

JSON, JSONL and CSV stdout retain their actual bytes-receipt route. A table
requires its own admitted material receiver followed by a separately observed
bounded table write and flush. A stdout encoding receipt is not material
custody, and an unsupported table or file destination refuses before durable
Submission admission.

The selected initial table route retains a distinct Material selection original.
The saved Run still joins its original read-policy CID and expiry; the table
selection does not replace that original or reuse its stdout permission. Its
read preimages bind the actual receiver, committed schema and ordering. The
receiver rechecks each copied row against those original field contracts and
keeps the same Session/Store through receipt and cleanup. Material completion
ends the payload reader; a separate current output decision and one actual
stdout write/flush produce the table receipt without reopening the reader.
The finite Native selection holds eight installation files plus config and
environment, with Account separately retained by the same initialization Owner.
The corresponding ten-file selection and eleven-file Product intake retain their
existing byte/node/depth limits; these counts issue no permission or resource
credit. A partial write, lost flush acknowledgement or failed current check never
repeats output. Older installations missing the selected Material original
refuse before submission instead of acquiring it through a read operation.

This records the adopted trust and credential boundaries for the standard
Native Local CLI. These are implementation requirements, not claims that Local
execution or Provider approval has passed public acceptance. The existing
Native Remote CLI, its wire contracts and distribution remain intact.

## Original file Result delivery

An explicit `result --output` or repeated `--deliver` selection uses an
independent adopted File read original. It does not redirect a stdout or
Material grant. The original Run, committed Manifest, physical Store and
current Run/named-Result authority are checked before acquiring the destination.
Literal SQL/Pipe file presentation carries the bounded selected path into the
same exact returned-Run Result request. It selects File authorization separately
from the saved Program and Run; it does not redirect a stdout grant. Destination
selection and missing initial File-original refusal precede Submission. A later
delivery refusal retains the original Run correlation and never resubmits it.
The separate Material/table stdout route is unchanged. Outside project metadata,
exact public saved-Run `result` and `status` operands select the existing default
Local installation, subject to explicit Remote/installation precedence. Their
original restore-only path does not join the quick-query initialization rule;
missing adoption/current/Run state remains unavailable.

First initialization retains the File selection alongside the unchanged stdout
and Material originals; existing installations lacking it remain unavailable.

The caller retains the actual parent observation and exclusive staging Writer
before fallible work. Read/egress preimages bind the destination path, parent
identity and Writer identity. The sink acknowledges only actual append and
seal operations; partial writes, uncertain close and failed current checks keep
the same cleanup duties and never authorize another send. The final name is
created exclusively, and existing files are never overwritten. Payload and
receipt destinations are checked before acquisition against the original Host
and managed Store namespaces; neither may create files inside those roots.

A private stable attempt correlation binds the original request, Run, format
and canonical destination. Lookup precedes Writer creation. A prior unresolved
attempt refuses; a prior success is reused only after the same authenticated
Journal evidence, Store receipt, current authority, parent/file identities and
actual bounded byte count and hash match. This comparison does not reconstruct
a Writer from saved inode DATA or issue another payload read.

Per-delivery session and file children acknowledge before the next destination
opens. Receipt export uses a separate bounded exclusive Writer after those
children; a failed export cannot undo or resend outputs. A multi-delivery
receipt file preserves the authored order of successful existing receipt
objects without claiming an atomic aggregate outcome. Business success,
physical cleanup and unresolved delivery remain separate observations.

A public Program `run` submits once before forwarding any requested output to
the same saved-Result/File path. Input representation and output encoding remain
separate; `--output` selects JSONL while each `--deliver` item selects its format.
The Run receipt is the existing commit view's original `run_receipt` contract,
retained by the same accepted publication observation. Export rechecks independent
current RunRead and excludes Host/Store namespaces. It does not issue another
receipt, substitute a Result delivery receipt, certify aggregate output success,
or make an uncommitted/Unknown Run committed. The original observation and every
partial export child remain with existing command cleanup until their own ACKs.

## Ordinary product startup boundary

The [ordinary Embedded Host contract](../spec/execution.md#initial-node-control-preparation)
and its [decision rationale](embedded-host-trust-boundary.md) apply to the public
Native CLI as well as Node and Python. A normal main entry, supported loader,
standard libraries and OS are trusted. Public output uses supported write/flush
APIs, bounded encoding and error handling; libc-private FILE fields, pristine
stdio, pre-main allocation provenance and process-wide arena coverage are not
command admission requirements.

Actual shared native buffers, SQLite/crypto contexts, FDs and in-flight work
retain their explicit ownership and release rules. In particular, do not
convert a real busy arena/context with live users into a false release ACK.
Legacy complete-process bootstrap descriptions below are selected implementation
material, superseded as ordinary startup requirements. Preserve applicable
per-resource containment rather than extending them to libc or runtime caches.
Trusted explicit Mock initialization may perform the adopted limited setup
through the existing adoption/signing Owners; retained reopen never regenerates
missing adopted configuration, keys or authority.

## Explicit configuration adoption

The operator explicitly selects the configuration, execution account and private
user-owned Host state. Directory discovery, a Program or a URI cannot select
trusted authority. Merely passing a file to the preparation-only CLI is not an
adoption operation.

Adoption durably binds the exact selected source/configuration, admitted account
configuration, account, adoption/profile identity and managed-root identity.
Retain the original bytes and their identities; configuration identity rules do
not normalize Program, Model or Effect data values. Physical containment must
bind the selected root and reject symlink/path aliases that escape it.

Use the existing Native journal and its physical custody boundary. Do not create
a second Local journal, execution Owner, scheduler or approval mechanism.
Current admitted operator configuration determines current authority. A Run
retains the historical configuration and authority binding under which it was
admitted; current settings cannot silently replace those originals on restore.
Authority expansion requires explicit adoption. Restriction or deletion never
causes automatic profile reapplication or regeneration of removed grants.

An initial profile is published content whose finite body, identity preimage,
CID and containment rules have independent expectations before shipping. Empty
authority is valid. Connectivity, Connector registration and adoption do not
generate Provider read/apply permissions. Source read and Effect apply remain
independently authorized at their existing boundaries. Approval does not supply
otherwise denied authority.

Ordinary reconnection is retained-only. It cannot create a state child, stage
an absent account copy or initialize a database, key or epoch. Only the explicit
adoption operation may continue a matching unfinished initialization. The
trusted default query caller may perform the first initialization described
above only when the installation is genuinely absent. It selects the ordinary
private configuration root; an explicit configuration must likewise have a
trusted private root before its physical libraries are loaded.

## Initialization and interrupted adoption

Freshness requires an exclusive, explicitly selected private Host-state creation
and matching durable initialization intent. A missing configuration, adoption
row, key or database is not freshness evidence. Bind the real private state and
managed-root custody rather than accepting caller-supplied labels as proof.

Persist a one-time initialization intent under an exclusive fenced claim before
creating configuration content. Create without overwriting an existing file.
Confirm the exact created file identity and durably finalize adoption before
protected dispatch. Config creation and a journal commit are separate physical
events; their combined result is not assumed atomic.

| Observed state | Required action before protected I/O |
| --- | --- |
| Explicit fresh state, exclusive claim, no conflicting content | Persist intent; create exclusively; confirm identity; finalize adoption. |
| Matching recorded intent, creation not yet performed | Continue only under the original fenced claim and exclusive creation. |
| Matching intent and exact created content | Recover that initialization; finalize the original adoption without rewriting content. |
| Finalized adoption with matching custody/configuration/account/root | Open existing Owners and evaluate current admitted authority. |
| Concurrent initializer | Refuse or observe the original claim; never create a second initializer or combine grants. |
| Existing config without matching initialization/adoption proof | Refuse protected dispatch; require explicit recovery rather than overwrite or merge. |
| Divergent file, foreign account/root, ambiguous creation or lost custody | Refuse protected dispatch; do not reset keys or infer that execution never occurred. |
| Adopted configuration removed | Preserve adoption and original Run evidence; do not regenerate permissions. |

An unknown commit response requires reopening and inspecting the original
durable intent/adoption under its original identity. It is not permission to
retry fresh initialization, send a Provider request or create another Run.
Physical cleanup failures retain the existing Owner and retry handle; the
failure must not convert unfinished adoption into a fresh environment.

The first assembly slice selects private user-owned configuration and state
parent directories explicitly. It exclusively creates one named state child
and binds both real roots, the source file generation, exact source bytes,
admitted account/CID and original initialization nonce. The account document
budget is 1 MiB; initialization and physical configuration witnesses are
bounded to 8 KiB each. Explicit entries, including an empty entry set, are
accepted without generating a bootstrap profile. A named bootstrap profile is
refused until its original is installed and verified.

The immutable initialization intent precedes exclusive configuration creation.
The separately persisted configuration witness binds its actual device, inode,
length and original intent CID. An existing state child without its intent,
or copied configuration without its creation witness, cannot become fresh by
retrying adoption. Completed staging and an intent preceding creation can be
reopened under the same filesystem lock and original bindings. This staging
boundary is not final journal adoption and grants no protected execution.

Restoration uses the existing SQLite adapter's retained-only open, after format
and custody admission. It refuses missing/empty databases and missing schema
constituents without creation, migration or schema repair. Fresh initialization
has a separate exclusive creation proof; ordinary open or physical absence is
not that proof.

The explicitly selected runtime configuration originals accompany account
adoption. The bounded selection admits at most ten distinct single-component
file names, each with at most 64 KiB of exact bytes. It excludes the separately
bound account file. Its immutable manifest records raw-content digests, source
file generations and the actual selected private managed-root identity. The
manifest is bounded to 8 KiB and is included in the initialization intent.

Finalization stores this manifest and the selected original bytes in the
existing SQLite transaction with Submission epoch custody and final adoption.
Reopening checks the selected manifest and original bytes, source generations
and managed-root custody before returning configuration or authorization material.
Missing stored originals are not copied back from a currently available source,
and a byte-identical replacement file cannot assume its predecessor's identity.
These configuration records confer no execution permission; the existing
execution-account Owner evaluates each current access tuple.

Selecting bytes from an open adoption Session projects the captured original
DATA; it does not reread every selected file or authorize a dispatch. Closed or
failed physical custody still refuses selection. Protected staging observes the
source installation once on entry and retains the copy's exact body, generation
and creation custody. Trusted copy I/O does not repeat that source admission.
Journal opening consumes this observation through its closed Read/SQLite steps,
while retaining the actual opened database target, selected stored originals,
adoption/epoch anchors and each physical return or partial-failure duty.
The same-pair command read may perform its first Journal open inside that entry
and consume the actual opening observation. A read entry on an already-open
capture observes current state afresh; no persistent opening success skips it.
Inactive Store routing metadata may precede opening, but cannot activate without
the acquired original Host/pair/Library. If opening leaves a pending flight,
that original return precedes retirement of the inactive routing metadata.

### Operation-scoped Journal reads

Ordinary open uses the existing-only SQLite entrance and fixed adoption,
epoch and issuance anchors. It does not copy the database or enumerate all
retained Runs, Effects or submissions. Explicit integrity inspection and bounded
compatibility indexing remain separate operations. Existing-only open refuses
missing schema or custody; it cannot initialize, repair or regenerate keys.

A selected read admits its own canonical Run and nested originals, target
Effect witness, original Submission and epoch. Unrelated historical corruption
is diagnosed by integrity inspection instead of invalidating every ordinary
read. Mutations retain the original transaction, local CAS/claim and sticky
COMMIT-Unknown behavior. Account decisions remain action/resource-specific;
immutable admitted facts do not replace current authority or physical cleanup.

A subordinate scope/Run-ID locator commits in the same transaction as fresh
admission. Arbitrary Run IDs remain valid and duplicate IDs remain ambiguous.
Lookup verifies the indexed original identity and epoch. Without a locator,
the ordinary CLI's Run-ID/Submission-ID equality is only a candidate until the
retained original proves it. Other legacy IDs require explicit bounded indexing
through the adopted Host's `index_saved_run_ids`, with current RunRead before,
inside and after the transaction. Until coverage of the exact issuance snapshot
is established, a missing locator returns `RunIdIndexIncomplete`, not absence.
Later admissions invalidate that absence coverage. Indexing authenticates the
existing originals and changes only subordinate locators; missing or inconsistent
history never permits a new execution or resend.

The captured Read path retains validated immutable facts for the same public
operation while its original pair, thread, entered Read and failure latches
remain current. A trusted metadata read, transaction, phase exchange or pure
getter does not create another authorization frame. Each distinct unchanged
permission tuple is evaluated once; pure DATA work performs no authorization.
Actual relevant target/policy/key changes, uncontrolled application reentry and
the next public operation require the corresponding fresh observations. A real
lifetime failure consumes the relevant observation instead of allowing a later
cheap check to revive it. Close retires all operation facts. Uncaptured public
entries retain their required entry checks. A publisher predicate consumes the
same scope, Account, selected configuration and Run facts without rebuilding
them between trusted reads.

Source-free Compute separates cheap original-lifetime polling from authority
validation at task dispatch, transfer and finalization entry/return. Existing
callers keep their original guard by default. Native polling observes its actual
entered business domain and unentered preparation Read; it neither queries the
Journal nor enters a scope or acknowledges cleanup. Durable first-start checks,
next-task denial and current checks before publication remain independent.

An unchanged availability observation returns its retained state and revision
without another serialization or durable update. A changed logical observation
still commits with the existing revision/CAS owner and current Store binding.

### Initial signing-key material

The selected Native Crypto Library can generate fresh Ed25519 material for
trusted initial installation. This synchronous operation returns secret PKCS#8
PEM bytes and the corresponding public SPKI PEM. Its temporary private DER is
explicitly cleared after encoding; that does not retire the returned PEM,
copies, Writer or escaped aliases. OpenSSL key/context handles are released
before return. Optional generation symbols do not change legacy Library load,
verification or signing requirements.

Generation does not adopt a Store, signer, physical key generation, public-key
CID, grant or credential use. The existing installer must first establish its
exclusive original initialization, then retain the actual private Writer and
file generation through durable creation and close acknowledgements. A missing
key in an existing or ambiguous Store cannot select fresh generation. Current
Reviewer/Checkpoint authorization, original key/public-key correspondence and
operation-bound signing uses remain independent of these newly generated bytes.

### Exclusive initial signing material

The existing adoption session may consume the original exclusive directory
creation once to generate a private signing file. Eligibility is a shared private
cell across session aliases, never an input Boolean or a condition recovered from
missing files. Reopened, partial or conflicting initialization is refused without
key generation. The same actual Writer is acquired before secret generation; an
unconfirmed write, seal or retirement preserves its original issue and partial
names. A retained-close acknowledgement concerns only the original descriptor and
directory sync, not publication or namespace cleanup. An unsuccessful constructor
likewise retains its actual Writer for cleanup without granting write authority.

The resulting private view binds the original session, Store root, file
generation and private projection. The public key remains DATA until the existing
authenticated installation journal adopts the same physical original. It is not a
source-root key original, configured signer, credential grant or current signing
permission. Missing old key originals are not repaired by generation or capture.
The Library, temporary key buffers, private/public encodings, Writer and escaped
view overlap still require the existing actual caller resource supply; format
lengths and a diagnostic ceiling are not numerical funding.

### Authenticated initial Store signing original

A trusted explicit first installer can carry that same session's opaque material
and the pinned Common bootstrap policy into the existing journal initialization.
The original marker and physical database inspection, not a caller Boolean,
select the first branch. The existing initialization transaction establishes the
epoch key and authenticates a closed initial-signing payload with that same key
before inserting the installation control row and confirming COMMIT. It retains
the original initialization intent, Host adoption, Store-root file projection,
public-key body/CID and original PEM, exact policy body/CID, issuer identity and
ReviewerProof purpose. The issuer identity comes from the Common policy Owner's
original-intent projection; the payload does not issue an operational grant.

The ordinary launcher requests this initial material path only after admitting
the installed Native image and exclusively preparing the project for explicit
`init`. Its private adoption request does not prove freshness: the same Native
session must independently consume its original exclusive creation. Ordinary
adoption without that request retains the legacy journal path. A request against
existing or ambiguous state refuses instead of falling back, replacing a key or
backfilling policy. Neither successful initialization nor a restored original
selects a default signer or supplies Reviewer, issue, claim or signing permission.

This is a closed alternative in the existing installation `host` control row.
The historical raw adoption body remains a separate exact alternative. The
adoption body/CID and initialization body/CID themselves do not change. The
`issued` counter, setting-original rows and their `files.length + 1`, eight-object,
8192-byte reservation and 2048-byte authenticated-payload bounds do not grow.
The complete nested record must fit the existing codec/snapshot limits or the
same transaction refuses it. Intake bounds are not physical read or workspace
funding. No extra row, issuer file or replacement policy ledger is introduced.

Restore authenticates the exact retained payload with the current original epoch,
admits policy and public-key originals through their existing Common Owners,
checks original intent/adoption/purpose/root role, and restores the same physical
private-file projection. A returned view retains its Host, Library through that
Host, original projection, policy and public metadata; current access fences the
same retained row and physical generation again. A configured source-root key
stays source-root, and a HostAttestation key cannot alias this ReviewerProof key
by physical file or raw public-key identity. An old raw row, missing metadata,
foreign policy/epoch/key, changed control revision or Unknown initialization
never chooses a fresh capture. Lost COMMIT acknowledgement preserves the same
operation and its uncertainty; lookup can observe an authentic committed original
but cannot create a replacement key, policy or claim. Read failure retains its
original typed cause; if transaction retirement also fails, both causes survive
in the same existing Host error path, and the database remains fenced.

This physical metadata seam is not default-signer selection, Account/Reviewer/
Run authorization, first issue, use claim, signature or public approval. Those
existing operational gates must independently bind the exact original purpose,
Checkpoint, preimage and use. First issue alone samples the trusted clock and
persists the finite absolute expiry; initialization and restore do not sample or
renew it. Configured/named signers and the generic explicit issuer-file route
retain their separate original authorization, and a missing legacy supplier stays
unavailable. The actual caller must retain the overlapping session/material,
HMAC/codec workspace and escaped view until their own physical acknowledgements.

The private initial Reviewer registration joins that same physical original to
an already-adopted public Host configuration without explicit signers and the
actual selected machine actor's independent current `run:resolve` Account
decision. The actual public-key CID labels the key; the actor labels the
Reviewer. Neither label supplies authority. Named selection and any explicit
signer map refuse default fallback. Replacement of the Host configuration,
Store key generation or original installation retires this view. Configured
Reviewer/key readers cannot consume the initial registration as their own file.
The subsequent binding uses the configured route's same original Checkpoint,
Client read and paired-scope checks. This registration still supplies no issuer
grant, private-key acquisition, durable claim, signature or approval application.
Its original Host/configuration/key and Account reads retain their overlapping
workspace and lifetime; parsing ceilings are not reservations or close receipts.

The initialized key may also supply the existing opaque Reviewer proof material
through a closed key variant. Its configuration identity is the existing digest
of the authenticated initial control body, and its generation identity is the
existing digest of the retained Store file projection. This introduces no CID
domain, configuration file or permission. The same original Checkpoint snapshot,
unsigned proof, authenticated Submission and paired-capture readers remain in
use. A final noncallback key/Host generation check follows the existing original
subject fence. The explicit issuer-file operation retains its configured
source-root key and cannot consume the initialized key variant. This connection
reads projection metadata only: actual private-key correspondence, durable
first issue/sample/expiry, same-use claim and signature remain independent.
The key variant and its small scope record retain the original Host, policy,
projection and installed Reviewer throughout overlapping current callbacks;
these references, record storage and read workspace are not free aliases or a
physical cleanup acknowledgement.

The default-only first-issue storage phase uses the same immutable grant packet
and Journal transaction, with an additional closed authenticated installation
payload. The original epoch HMAC binds the first clock sample, any earlier
original validity bound, pinned policy, initialization, exact grant/operation
and selected Host configuration/connection. The grant retains the absolute
expiry and one-use limit. The existing full grant/Run custody census and original
Submission authentication remain in place; the default branch additionally
restores the same Store-root key generation. The configured issuer-file branch
and its packet bytes are unchanged. Existing payload, packet, work and per-request
reservation bounds apply without relaxation.

That private storage phase reads an existing operation before sampling the
clock. Its exact original use/outcome is history only; missing or corrupt use
custody cannot select another sample, expiry, claim or ordinal. The first
retained default operation also fences its same original Submission, Checkpoint
and purpose; a different operation/attempt plus decision preimage cannot bypass
claimed or Unknown custody. This default-only restriction leaves configured
issuer-file operations' existing exact key/preimage rule intact. A first append,
exact attempt-bound use claim and trusted-clock lower bound share the existing
transaction and rollback. Lost COMMIT acknowledgement fences that original
responsibility. Neither the private stored result nor authenticated metadata is
a physical signing permit: the enclosing original operation must retain its
paired Checkpoint, current Client/Reviewer/key gates, exact purpose/earlier bound
and material custody through actual physical signature and final acknowledgement.

### Original private-file signing
