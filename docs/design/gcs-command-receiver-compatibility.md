# GCS Command receiver contract boundaries

A receiver Environment is DATA. Environment integrity, Catalog membership,
Command target-kind selection, input-role correspondence and same-Environment
STORE binding have distinct purposes. Their success neither admits an execution
Account policy nor issues a Resource, grant, physical dispatch or approval.
Catalog integrity explicitly leaves complete body semantics and execution
admission to their corresponding owners.

The frozen receiver/provider input remains an immutable predecessor. Its
unsupported Command `minimum_approval` member is historical DATA, with its
original identities and export LF. It is not a current canonical Command body.
The standard installed constructor refuses that exact predecessor before any
grant. Reading its historical integrity and purpose bindings does not upgrade it
into a current installation or an Account decision. No saved bytes are rewritten,
converted or re-signed.

Current GCS generation emits a Command without that property. Its complete
Command and role preimages, Catalog, STORE Mapping and Environment are checked
against separately authored literal identities. The Mapping retains its separate
existing minimum and references the current Command and Catalog identities.
The receiver comparison includes every ordered member and the complete wire,
not only a schema shape or selected CID. The original export LF remains a
noncanonical input; canonical runtime wire is never obtained by general trim.

The original Account/Host decision, exact Set Checkpoint and Resolution when
required, current installation/target/key selection, funding, claim, response
custody and cleanup remain separate duties. This DATA correspondence provides
none of them and cannot authorize resend or reinterpret Unknown state.
