# Native Client CLI

`actql-native-client` is a Node-free native binary that uses the public
Client–Host HTTP protocol over mTLS. Remote operations use the existing bounded
native HTTPS adapter; the selected Host owns Run admission and retry. The source
also provides explicit embedded Local operation through the common checker and
existing Native Host/journal/Store. The source-free Darwin arm64
private-integration cohort at `eb2f8b3b0a096e8dd86548bffbc6bafb6e79fc20`
passed external installation and seventeen Local CLI operations on macOS 26.0
or newer: explicit adoption, SQL check/explain/run, same-Run fresh-process
lookup/status by reference and ID in JSON/human form, bounded Named Result
delivery/release and retained reread. Three refusals were expected; skip count
was zero. This is not latest-main or complete Source/Model/Effect/approval/
cancel/Debug and other-platform acceptance. The earlier `109564ef` cohort keeps
its original eleven-case `aql`/Result evidence and binary identity. Preparation
alone does not admit a Run or establish authority.

For the installed source-free profile, use the product default configuration
with `actql --mode local adopt --json`; no Host/token/mTLS, internal JSON or
library path is required. Remote remains the default. See the [accepted Local
command guide](../../../docs/cli.md#accepted-source-free-local-baseline).
Fixed-cohort acceptance is separate from public npm availability.

## Embedded Local preparation

Select `--mode local` explicitly. Advanced operator-supplied installations can
also select `--config-root` and `--config-file`; these are not requirements for
the installed source-free default. The configuration selects a bounded Check
Environment original and its evidence bundle CID.
`check --program-file <file> --format <format>` prepares the input
through the existing Native frontend/checker. External parameter declarations
are allowed only for `aql-text` and `sql`; parameter values remain separate.
Remote endpoint and authentication flags are refused in this mode.

Human output states that no Run was admitted. `check --json` returns
`kind: prepared`; it is not a verified public diagnostics report. Unsupported
inputs or operations are refused. Source alias discovery,
Local Run commands, Checkpoint answers and cross-process Local Run recovery
are not completed by this preparation entry. The source fixtures are in
`scripts/fixtures/native-local-cli`; current source changes do not establish
fresh installed-artifact acceptance by themselves.

The focused developer acceptance command
`node scripts/test-native-cli-local-install.mjs <fixed-CLI-RC>` installs the
existing `actql` launcher and matching platform artifact into an external npm
prefix using the fixed-artifact private registry. It reuses the Native ingress
cases with the installed launcher, checks exact source/artifact identity, and
retains command and nonzero-test evidence. It does not require an SDK RC or
run the Remote acceptance campaign. Its scope is preparation, value preservation
and refusal; it does not establish the installed execution baseline described
above or complete approval and other recovery profiles. Run this through the
existing heavy guard after preparing a clean-source Native CLI RC with the
existing artifact/release producers.

## Static Local explanation

The source-level `explain` command accepts the same `--program-file`, explicit
`--format`, separate parameter values and declarations as Local `check`.
It uses the same selected Check Environment and original prepared computation,
then returns the existing compiler-owned PlanView for effect-free input or the
separate closed `actql-effectful-static-plan-view/0.1` for checked Effect input.
`--json` emits that closed value directly; human output states that no Run was
admitted.

This connection covers source-free computation. The Effect envelope retains the
original computation Plan/map and declared unit/member facts; that component is
not a full physical Effect DAG. Mapping targets, Command Resource kinds and
Result/Table inputs remain declarations. Actual targets/values and current
permission/gates/approval stay unknown; sealed Preview is unavailable. Contract
minimum none/required/not-represented is distinct from current permission.
Source acquisition and executable Effect normalization remain unavailable here.
The view reports static observation, zero Provider I/O and unknown quantities,
with Inspect and durable controls unavailable. It neither runs the Program nor issues authority,
opens a Result or creates a Submission. Remote mode refuses the command before
opening connection or input files. The packaged route retains explicit trust
adoption and the original selected configuration, rechecking existing original
custody and the current package after projection before returning metadata.

The source-free SQL explanation is covered by the fixed `eb2f8b3` installed
cohort above. The Effect envelope and the broader input/profile combinations
remain source-level evidence; they are not newly installed Effect acceptance.
The earlier `109564ef` binary retains its original digest and evidence.

## Original Local run entry

The source-level `run` command delegates once to the existing Local `aql`
intake. It requires the same explicit format, original Submission reference
file and operation-attempt ID; optional nonce and separate parameters retain
that Owner's existing meanings. Submitted content still has `kind: aql` and
passes the existing lookup-first acceptance and execution path. This command
creates no substitute identity, automatic retry or new execution model.

JSON output preserves the existing Owner response exactly. Human output labels
it as the original Submission response; acceptance or exit status alone is not
Run completion. Remote mode refuses this Local entry before reading connection
or input files. The fixed `eb2f8b3` installed cohort exercised this Local `run`
entry. The earlier `109564ef` baseline keeps its original `aql` command and
source-specific evidence.

## Saved Local status

`status --ref-file <run.json> --submission-ref-file <submission.json> --json`
reads the original durable observation. `status --run-id <original-run-id>
--json` locates that same authenticated original; omit `--json` for the human
label and the same metadata. Use the actual `state.run_id`, not another CID.
These forms were exercised in separate installed processes at `eb2f8b3`,
including after Result read/release. Missing legacy originals are Unavailable,
not reconstructed from current settings or a new execution.

The closed reply has `kind: local_saved_run_state`, the original `ref` and
`submissionRef`, `state.version: actql-run-state/0.1`, and the original control revision.
Current RunRead and original bindings are checked independently of saved
metadata. Run success is not Result availability: the accepted original kept
`result_available: false` and `answer` availability `unknown` with reason
`verification_pending`. The separate authorized Result delivery supplied its
own payload and release evidence; status did not rewrite the saved observation.

## Explicit Local Host adoption

`adopt`, `connect` and `new-submission` in explicit Local mode connect the
existing account, adoption, journal and Submission epoch Owners. These operations
alone do not execute or publish a Run. The source-free installed baseline also
uses `aql`, original Submission lookup and Result delivery; its evidence is
separate from the earlier preparation-only fixture.

`adopt --json` explicitly finalizes a private Host. `connect --json` opens only
the same retained Host and refuses absent state or unfinished initialization;
it never initializes keys or repairs missing originals. Both return account and
adoption identities, without a Run or Provider grant. The human form says that
no Run has been admitted. `new-submission --request-id <nonce>` returns the
existing epoch/nonce reference only when the selected execution account permits
the `principal × connection × run × submit` tuple. A reference is not acceptance
or Provider read/apply authority. No-match and delegated permission are refused
in this first slice.

`lookup-submission --submission-ref-file <file>` opens the retained Host and
authenticates the saved original epoch/nonce through its existing journal. The
reference file is read from the input root, separate from the private
configuration root. Product defaults use the current working directory for
input; an operator-supplied configuration defaults to its configuration root
unless `--input-root` is selected explicitly. Current
account permission for the same submit scope is required; the reference itself
grants no authority. Lookup never prepares, acquires or executes a Program, and
does not replace an expired epoch. Its Local CLI JSON has
`kind: local_submission_lookup` and the exact `submissionRef`; `history:
unresolved` is not evidence of nonexecution or permission to resubmit. Retained
records expose `preparing` or `ready` admission facts with exact decimal
revisions. A ready admission is not an execution outcome or published Result.
The source-free installed baseline confirms original Submission lookup after
execution and publication in a different process. This does not establish
Source/Effect continuation or all attach/failure-recovery profiles.

The current source connects `start` and `aql` to the same original
Submission journal, ordinary frontend/compiler, Native Source/Compute Work,
original Local normalization audit and Native Result publication Store. It is
verified with the fresh installed cohort above for source-free SQL and its
original Result. The separate Source-bearing profile requires an explicitly
installed Source, a supported linear Effect-free Program, explicit view/no
semantic completions and selected Run/retention originals; its product
acceptance remains unfinished. Effect execution and its full process recovery
remain unfinished as well.

Input is durably recorded before preparation. A rejected preparation can be
looked up as the same retained submission; it is never treated as absent or as
permission to replace its input. An already-admitted submission returns the
original lookup facts without recompilation, a new Run or another acquisition.
`ready` still means admission only. A retained admission resolves the same
original Run definition into the common closed Run reference and separately
observes its control revision; neither comes from current Run settings or
from the admission revision. This reference is not an execution or read grant.
`local_run_published` is emitted only after
the original Store confirms publication and temporary Source/Compute cleanup
and Store close succeed; it is not a Result delivery receipt or read grant.
The selected Result retention original supplies the Run validity ceiling.
Current submit and Source read authority are independent. A publication error
retains original Store materials for reconciliation rather than deleting them
or opening another Source. Pending cleanup is reported as incomplete.

The source candidate also connects Local `lookup-cancellation` to the existing
original-operation journal. Provide both `--submission-ref-file` and
`--ref-file`, together with the original `--cancel-id` and
`--expected-revision`. The Host authenticates the original Submission, resolves
its retained admitted Run, requires an exact Run-reference match and rechecks
current `principal × connection × run × cancel` authority. Submit permission
does not supply cancel authority. Remote mode refuses the Local-only Submission
binding; the existing Remote request and wire remain unchanged.

The Local reply has `kind: local_cancellation_lookup`, the exact `ref` and
`cancelRef`, and `history: unresolved` or `retained`. A retained record projects
only its original `action` and exact decimal `recordedControlRevision`; this is
not a new Run-control snapshot. An unresolved history certifies neither refusal
nor absence of side effects, physical stop or resource release. Lookup does not
issue a cancellation, reopen payloads, load a Provider, recompile or resubmit.
The Host must close successfully before stdout publishes the reply.

Local `cancel` accepts the same original bindings and additionally requires
`--operation-attempt-id`. It opens the original existing Store without format
or database initialization and passes its real publication observer to the
existing cancellation journal. That Owner atomically records the request and
its original witness. The reply has `kind: local_cancellation_operation` and
the same original-record fields as lookup. `invocationRef` correlates this CLI
invocation; it is not an independent durable invocation refusal certificate.
Reusing the original cancellation identity returns its immutable original
record. A distinct operation against an already-requested Run records
`already_requested`; it does not rewrite the earlier operation.

After entering the cancellation transaction, an unconfirmed result or later
close failure reports `LocalCancellationUnknown` with the exact original
`cancel-ref` and `lookup=lookup-cancellation`. The reason can describe a local
conflict or cleanup failure, but is not a durable refusal certificate or
permission to resubmit. Lookup uses the original Submission, Run, cancel ID
and revision; it does not need to reopen the Store or replay Source/Compute.
Store and Host close must both succeed before a successful stdout reply.

Cancellation acceptance is not confirmation of physical stop, terminal Run
state or resource release. Physical-stop/cleanup restoration and actual
fresh-artifact cancellation CLI acceptance remain unfinished. The process
fixtures include discarded stdout after a real exited command; that case is
not a pre/post-commit fault injection. These fixtures are defined and checked
for syntax separately from runtime acceptance.

Local `lookup-preparation-raw` observes one retained Preparation credential use.
It requires `--submission-ref-file`, `--ref-file`, `--grant-ref-file`,
`--operation-cid` and `--use-id`. The grant reference must match the original
admitted request, and current Account permissions must independently allow the
original Run and saved target resource to be read. The existing Host reader
verifies original grant/target/use and Store custody. It needs neither a live
Work nor an HTTP client, secret or the original issuer's issue permission.

The bounded JSON reply reports the original use outcome/status and the retained
raw response status, byte count and digest. It does not include the raw body,
request or credential configuration; Result stdout settings do not authorize
raw-body export. A claimed/unknown use remains claimed/unknown when retained
response bytes exist. Missing or invalid originals, unavailable raw bytes,
expired/revoked permission and cleanup failure refuse; none cause another GET,
grant use or new execution. Store and Host close precede successful stdout.
This command is source-connected; fresh-artifact exited-process CLI acceptance
is still required and is not established by compiler-only fixtures.

Local `delivery-attempt` observes only the original saved read attempt. Supply
`--submission-ref-file`, `--ref-file`, `--result-name`, `--purpose` and
`--attempt-id`. The trusted account must explicitly permit both the current
`principal × connection × run × read` and
`principal × connection × result/<name> × read` tuples. Submit or cancel
permission is not Result read authority. Local-only purpose and Submission
options are refused in Remote mode before transport setup.

The existing original-Submission Owner authenticates the exact admitted Run
and original Store custody. The Result access Owner rechecks current lookup
authority before and after reading metadata. This lookup service does not
provide read admission, delivery or receipt hooks and cannot issue/consume a
grant or reopen payload. `history: unresolved` supplies no replay permission.
A retained reply contains the original `attempt`, optional latest `record` and
optional `hostReleaseReceipt`; missing records/receipts are explicit NULL.
These independently obtained facts are not an atomic Run snapshot. Store and
Host close must succeed before the reply is published. The installed source-free
baseline verifies this lookup after a real read, including its digest and Host
release receipt. Other process fixtures remain separate from this acceptance.

Local `checkpoint-state --submission-ref-file <file> --ref-file <file>` reads
only the original accepted Submission's retained Checkpoint metadata. Current
adopted Host/Account `run × read` authority is required again on every lookup.
The reply binds the exact original Submission and Run reference; an admitted
Run without a Checkpoint returns `checkpoint: null`, while unresolved history,
missing admission or lost Run custody refuses. It never starts a replacement.

The Checkpoint object contains its original CID, the exact decimal-string Run
control revision, retained Checkpoint Owner state and `cancellationRequested`.
The latter is an accepted request, not confirmation of physical stop,
cancelled settlement or cleanup. This metadata is not an atomic snapshot of
all Owners. Lookup does not read Preview bodies, resolve/approve/reject a
Checkpoint, claim resume, open Result payload or issue credentials. It is
Local-only; Remote mode refuses before transport. The source and typed callers
are connected, but Native runtime and exited-process CLI acceptance remain
unexecuted and this command does not complete the approval path.

An optional `native.local.read_file` selects a separate closed
`actql-config/0.1` file with `native.result_read` settings. It must also occur
in the existing finite `installation_files` selection. The existing exclusive
adoption Owner retains and rechecks its exact bytes and physical generation;
replacing even a valid selected original is refused rather than silently
adopted. Run settings, Source Policy and Account contracts are unchanged.

Read settings explicitly name `enabled`, `principal`, `connection`, literal
`result_names`, existing `formats`, `purpose`, `sink: "stdout"`, original
`data_policy_cids`, and finite `max_bytes`, `max_uses`, `expires_at`. Missing,
unknown, duplicate or excessive fields are refused. Admission of these settings
is not current read permission, a grant or validation of the referenced Policy
originals. Actual payload admission, issuer and original Policy checks are
connected and accepted for the source-free installed profile. Missing read
settings do not disable the independent metadata-only
`delivery-attempt` lookup.

settings, the selected `actql-config/0.1`
document requires `account_config` (one file name in the selected private root)
and `native.local`:

The config file and Check Environment original are durably bound with the
account and managed-root identity. Optional `installation_files` explicitly
selects up to six additional originals in the same private configuration root,
each bounded to 64 KiB. Names must be distinct single components and cannot
repeat the account, config or environment file. The same adoption transaction
stores their exact bytes and generations; reconnect cannot replace or repair
them. Selecting an original is custody only: it does not install a Source or
Policy, prove a normalization journal, or grant Provider access. Changing selected content, replacing a
source file even with identical bytes, or losing custody refuses reconnection.
No missing original is repaired from current source files. Source-bearing
execution, typed Direct Local credentials and approval-backed Effect remain
separate from the accepted source-free Run/Result recovery baseline.

An optional `native.local.source_file` names one of the explicitly selected
`installation_files`. Its bounded `actql-config/0.1` document contains only
`version` and `native.source`. The Source settings decoder admits the closed
physical binding, contract originals, Ledger/dispatch/search/import limits and
estimate profiles into the existing Native Source/Compute configuration types.
It does not load DuckDB, open a Source database or grant read permission. All
numeric settings are explicit; physical byte budgets are at most 512 MiB, and
unknown keys, missing required values, fractional limits and escaping DB names
are refused before Host initialization. The DB name is one component under the
adopted managed root; the execution connection must separately validate that
physical binding and current Source authority before opening it.

## Remote transport

Build with the pinned MoonBit toolchain using `moon build --target native
--release src/cmd/native_client`. The resulting binary is
`_build/native/release/build/cmd/native_client/native_client.exe`. Supply an
HTTPS endpoint, CA, client certificate and key, the installed libcurl library,
and a bearer token file. The token stays out of command-line arguments.

The connection JSON contains the public `mode`, `owner`, `consentRefs`,
`runners`, optional `durability` and Hybrid `movementPolicyRef`. Local-owned
Hybrid also requires a registered `cloudConnectionRef`; Cloud-owned Hybrid
requires at least one selected Runner. The CLI
negotiates that exact connection before each operation and rejects a Host
profile with a different mode or owner, or a downgrade from requested durable
to volatile. The `aql` command takes an explicit `--format`: `json`, `yaml`,
`aql-json`, `aql-yaml`, `aql-text`, or `sql`. It sends the bounded source to the
Host without inferring its language from a filename. The installed Host must
provide the selected frontend and admits the generated Program through the
ordinary checker. Query-only source can take a JSON
`--parameter-declarations-file` in the existing Program `params` shape; values
remain separate in `--parameters-file`. JSON/YAML Program documents cannot
take external declarations. `start` takes a JSON Program object. Both
commands require a caller-saved `--submission-ref-file` and an explicit
`--operation-attempt-id` for the invocation. Allocate deliberate new
work with `new-submission --request-id <nonce>` and save its full epoch/nonce
JSON before sending input. `--request-id` on `start` or `aql` only asserts that
saved nonce. `lookup-submission --submission-ref-file <file>` observes the
original identity, including after a reconnect or epoch expiry; it never
replaces the original epoch or dispatches work. Retain input and parameters
alongside that file. A missing lookup record is unresolved, not retry permission.
`lookup-request` only queries existing request history and rejects malformed
Host replies instead of reporting them as successful lookups.

`attach`, `status`, `wait`, `cancel`, `lookup-cancellation`, `reconcile`, `read` and
`delivery-attempt` use an explicit Run reference file. `read` requires a
caller-saved attempt ID. It accepts only a complete JSONL response with the
normal terminator and writes exact payload bytes to stdout after completion.
The whole response is bounded by `--max-response-bytes` (default 1 MiB,
maximum 16 MiB); this is a bounded CLI read, not the streaming SDK reader or
a JavaScript heap limit. A failed read reports its attempt ID and does not
cancel the Run. `delivery-attempt` admits the published MoonBit attempt,
record and Host release receipt contracts, binds them to the requested
attempt, Run and Result, and rejects missing or contradictory evidence. It
does not request payload replay or hash payload bytes.

`cancel` requires a caller-saved `--cancel-id`, `--expected-revision`, and
`--operation-attempt-id`, in
addition to the original Run reference file. Obtain the revision from the
Run's current control observation before issuing a new operation, and retain
the Run reference, operation ID and revision. The attempt ID correlates this
invocation; it is not a cancellation identity or a lookup authority.
`lookup-cancellation` takes the original Run reference, cancel ID and revision and only
observes the original operation; it does not cancel again. Replies must match
the exact Run, operation ID and original revision. An accepted cancellation
must advance that revision. Lost cancel replies report `CancellationUnknown`
with the exact `cancel-ref` and lookup command. An unknown lookup is not
evidence that cancellation was refused, physically stopped, or released.
Typed invocation replies distinguish `accepted`, `already_satisfied`,
`refused` and `conflict`. A Refused certificate says only that this invocation
did not commit or consume cancellation identity. Another invocation may have
been accepted. Generic HTTP errors carry no such certificate.

The Remote mTLS fixture in
`scripts/test-native-client.mjs` uses a mock Host. The mock verifies request
shape and response handling; it does not prove Host frontend admission or a
native end-to-end Program Run. `scripts/test-native-sga-public-source.mjs`
separately exercises authored WITH / GRAPH queries through an installed
public HTTPS Host and Named Results. Its machine-Program control remains distinct
from source execution. Run the focused installed acceptance with
`node scripts/test-packed-public-query.mjs --graph-native-only`; see the
[fixed-source acceptance record](../../../docs/reviews/2026-10-03-native-property-graph-source-acceptance.md)
for independent rows, descriptions, refusal counters and its coverage limits.
That historical record covers its fixed predecessor grammar; current WITH
acceptance requires execution against the new source and package cohort.

A held submission prints the validated request control reply as JSON. It has
no Run reference: `lookup-submission --submission-ref-file <file>` observes the same intent
without approving or resubmitting it. Once lookup returns `ready`, its `admission.ref` can be used with `attach`. The native CLI does not yet provide
Checkpoint answer commands; use the existing public Client operations for
that workflow.

Confirmed Host preparation rejections preserve the public input error code.
An unrecognized or lost submit response remains `SubmissionUnknown` with the
original submission-ref file; it is not a claim that no Run was accepted.

## Query source example

This example requires a Host that publishes the `records` alias and supports
query source input. Host routing acceptance is tracked separately from the
native transport tests. Keep the following files in one protected directory:

`connection.json`:

```json
{"mode":"remote","owner":"remote","consentRefs":[],"runners":[]}
```

```sql
-- query.sql
SELECT id FROM records WHERE amount >= @minimum ORDER BY id;
```

Use `{"minimum":{"type":"number"}}` in `declarations.json` and
`{"minimum":20}` in `parameters.json`. The token file contains only the scoped
bearer token; keep it and the client key readable only by their owner.

```sh
./actql-native-client \
  --endpoint https://host.example/ \
  --connection-root "$PWD" --connection-file connection.json \
  --token-root "$PWD" --token-file token.txt \
  --http-library /usr/lib/libcurl.4.dylib \
  --ca ca.crt --cert client.crt --key client.key \
  aql --program-file query.sql --format sql \
  --submission-ref-file saved-query-submission.json \
  --operation-attempt-id saved-query-submit-001 \
  --parameter-declarations-file declarations.json \
  --parameters-file parameters.json --request-id saved-query-001
```

The example library path is for macOS; select the installed libcurl library
for the target platform. For Pipe, change the source and explicitly select
`--format aql-text`. File extensions never select a parser. A successful Run
admission prints an object containing `ref`; save that exact object member
as the reference file for `wait`, `status`, and `read`. A held request has no
`ref` and must not be converted into one.

First run `new-submission --request-id saved-query-001` with the same
connection flags and save stdout as `saved-query-submission.json`. Then run
the command above. After an uncertain submit, use
`lookup-submission --submission-ref-file saved-query-submission.json`. This only observes the original
request. Once there is a Run reference, `read --ref-file run-ref.json
--result-name answer --attempt-id saved-read-001` reads that named Result.

| Diagnostic | Meaning and next action |
| --- | --- |
| A registered `ClientProgram*` or `ClientParameters*` preparation error | Confirmed input rejection; correct the source or declarations/values. Parameter values are not interpolated into source. |
| `SubmissionUnknown submission-ref-file=...` | Admission was not confirmed. Preserve the original epoch/nonce file and exact input and use lookup. Do not infer failure or automatically create another request. |
| JSON with `kind: "held"` | No Run exists yet. Observe the request and use the existing Client Checkpoint workflow for answers. |
| `IncompleteResultStream attempt-id=...` | The read did not reach its normal terminator. This does not cancel the Run or prove the Host sent nothing. |

## Query text and machine input

`aql-text` accepts the implemented query language, including Pipe and admitted
Graph patterns; `sql` selects SQL query heads. The retired
`AQL / PROGRAM / STAGE / STEP / OP` envelope is rejected by the Host before
Run acceptance and provider I/O. JSON/YAML Program remains supported machine
input. Text is never retried as another format, and extensions do not choose
a language. Removal of the old surface does not claim that every adopted
Graph, VecA/TEA or Effect surface is implemented.

The Native Project adapter retains the admitted Mock implementation with the
SAME selected execution contract. It consumes the normalization's original
prompt and the retry/backoff material already produced during metadata
preparation, rather than regenerating those dependencies in the Run caller.
Lookup accepts that exact execution object; equal separately admitted material
cannot select it. Retirement first removes this metadata alias and then waits
for the original installation's users before releasing its other originals.
This is implementation selection, not Account, Model dispatch, Scope funding or
a physical cleanup acknowledgement. Run executions remain per-Run children.
