# HubSpot execution Mapping derivation

The original bounded property Catalog derives a candidate of the existing
`actql.mapping_contract/0.1`. This is the provider projection used by the
existing Host Row Effect Owner, not a new execution, permission or publication
Owner. The Host must obtain the connector manifest CID from its actual
Common-issued RowDeclaration and admit the resulting Mapping in that same
Check Environment. A well-formed supplied digest is not proof of that binding.

Create, update and positively enforced-key upsert keep the original property
contracts. Exact decimal(38,10), arrays and their item contracts are emitted by
Common `value_contract` and `encode_core`; they are not lowered to primitive
string fields or inferred from sample values. The non-null top-level `id`
remains distinct from alternate property keys. Unsupported, unconfirmed and
readonly selected fields refuse preparation. Company domain false/missing
uniqueness is still not an enforced key. Upsert candidates require the same
existing unique/writable property facts; no candidate creates a grant or an
absent-record proof.

The canonical Mapping body binds the actual manifest, resource, target schema,
primary identity, sorted writable fields, original row Mapping and exact
operation permission rule. Common remains responsible for interpreting it at
Program preparation and compilation. Encoder-owned preimages and final bodies
use checked UTF-16 key order; the tests independently hash their literal
preimages. Common also owns connector identifier grammar; this derivation
only bounds scalar input and requires the original Catalog resource.
Changing a manifest, selected type or source Mapping
changes identity; DATA equality does not substitute current Site/Account or
credential checks. No old Run is re-prepared here.

Only an explicitly declared create `omit` source allows a missing value.
`write_null` retains explicit null; it is not omission. The existing bounded
Source/Decode and write-body Owner rejects missing required fields, extra
values, inexact numbers and non-roundtripping provider spellings. The metadata
is rechecked before accepting a mapped body. Row values, provider spellings
and simultaneous schema/preimage/final writer documents are retained DATA;
caller byte/node/depth/field limits are not a normal numerical profile or
wholephase funding proof.

The current boundary tests use the real Common declaration/Mapping reader and
Effect preparation, plus the original Credential/Account/SQLite/loopback TLS
write fixture. This is component evidence. Full installation, sealed Preview,
legitimate approval, durable claim/request-marker/history reconciliation,
Named Result, same-Run recovery and release remain the existing Host pipeline's
required connection and acceptance. No live HubSpot action or new public
support/profile claim follows from a Mapping candidate.
