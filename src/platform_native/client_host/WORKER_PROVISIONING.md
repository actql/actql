# Original pre-Core worker provisioning identity

The existing Native Host adoption/journal Owner issues one child provisioning
operation before the worker child acquires its physical resources. Existing
Host initialization/backing and the child operation are separate lifetimes. Its parent
is the original adoption and Submission epoch. The child key is independently
issued random identity, not the parent nonce/CID, Resource DATA, PID or FD.
`OriginalLocalInstallation._project` and Wasmtime are not involved.

`issue_worker_provisioning` requires the current Account's explicit
`resource=worker, operation=provision`. `lookup_worker_provisioning` independently
requires `worker/read`. Neither is inferred from Run submit/read. Selection is
an opaque original from the existing installed arena Host;
metadata selection does not supply a numerical profile or permission to acquire.

Fresh Host adoption initializes the child custody witness in its existing
transaction. Missing custody on older/partial installations refuses; this unit
does not repair or migrate it. A retained child intent precedes the immutable
SQLite row and selected-key CAS. The same Host retains the partial carrier before
file/SQL I/O. Failed file closure keeps the existing Writer/Root responsibility.
A lost COMMIT reply fences that journal. Reopen uses the same intent/key in the
same Store and only observes; it never writes, reserves, acquires or launches.
A known absent SQL row after the durable intent remains `UnresolvedOriginal`
with `NotRecorded`, not retry permission. An issued witness with a missing row
is custody loss. The parent witness stores the existing adoption CID rather than another full
adoption body. The child intent/SQL/live body copies are bounded to 2048 bytes
each; their 8192-byte metadata reservation uses the existing settings budget.
This reservation does not account for native control/loader/VM overhead.
The existing bounded settings metadata reservation is consumed;
no capacity limit is increased. This is not full bootstrap physical funding.

The closed intent binds adoption, original epoch fingerprint, independent child
key, selected source, recipe and provider generation. The first key phase has no
worker-child ticket/backing yet. The subsequent existing live Resource DATA and
actual provider/child/backing projection must attach under this SAME key; it must
not create another attempt. Source/recipe/generation substitutions refuse.
All cold results are unresolved DATA, never a nominal child, Ledger, borrow,
zero-debt claim, launch, stop or settlement acknowledgment.

A successor issuer is deliberately unavailable in this slice. Full actual
worker/descendant/FD/alias retirement has no complete typed supplier here yet.
Closing an unacquired selection, missing records, direct-PID exit and finishing
Host initialization cannot supply that proof. Once the existing Owner connects
its genuine retirement evidence and new current authorization, a separate child
identity may be issued. This refusal is not claimed as a successful successor
acceptance or complete worker recovery.

The focused Native tests cover actual isolated SQLite commit/reopen, lost first
COMMIT reply, uncommitted first write with retained intent, foreign epoch and
generation, missing original records, and independent Account refusal. Runtime
selection is metadata only: physical arena acquisition, Python Wasm Core, worker,
Engine, ordinary installed wheel and public Python product execution remain 0.

## Original live Resource observation

The same child attempt can record one initial observation from the exact domain
registered with its nominal installed selection. `record_resource_original`
accepts an opaque domain, not caller-created DATA or an allow/commit Boolean.
The existing provider/Resource Owner jointly projects its original FD window,
child, loan and accounting values. Current Account, adoption/Store epoch and
unchanged original child rows are checked before and inside the existing Store
transaction, and current physical/account facts are checked after its commit.
The same partial carrier retains the domain before the first Store write.

The closed observation binds the full original provisioning body, selected
source/recipe/provider generation, actual device/inode, capacity and relative
mapping/payload extent/access, and Resource-owned bounded original DATA. The
physical bounds and the existing Resource cross-field validator are both used.
PID and FD numbers never become the backing identity. The immutable resource
row uses `resource/<original-child-key>` in the existing provisioning namespace;
it neither issues another operation nor mutates the original key selection.

This snapshot is the initial saved observation, not a claim that later usage is
unchanged or that final usage was observed. Cold read exposes only
`UnresolvedRecorded` or `UnresolvedNotRecorded`. A lost COMMIT reply fences the
same journal; reopening uses the same key lookup. A live write attempt cannot
be repeated even if its row is absent. No nominal ticket/domain or write/start/
stop/settlement permission is reconstructed. Complete current usage persistence
and cold physical adoption/retirement remain separate unfinished connections.

The body is bounded to 4096 bytes. Four raw byte slots are charged to the
existing 65536-byte/8-entry settings metadata budget in the same transaction;
those limits are unchanged. Decoded/control objects, loader/VM/FD overhead and
physical bootstrap funding are not declared covered by that metadata entry.
Actual domain cleanup remains with its original Host/child Owner and aliases;
Store acknowledgment never releases a loan, closes an FD or confirms a worker.

## Explicit Python worker first adoption

`client_local_product_python_worker_bootstrap_originals` selects a distinct
Account under the existing authorization Owner. The original `local-cli` /
`local` Run and `result/answer` entries are retained; the only additional entry
is `local-worker-provisioning`, with resource `worker` and exactly `provision`
and `read`. It has no named bootstrap, Source, Model, Effect, launch, stop or
settlement grant. The existing Host methods additionally bind the original
private Host, adoption/Store epoch, child key and selected provider generation.
An Account entry alone is neither a provisioning identity nor physical funding.

The existing Native/SDK Account remains
`sha256:fd6d54cc5bcc0a7af2a7919981b4e06604a3380897bcf9ceb51cf764ecdfb396`.
The new Account is 746 bytes, 223 bytes above the original, within the unchanged

`begin_native_local_python_worker_configuration` explicitly selects and retains
these nine exact bodies through the existing durable product-configuration
session. Call `stage_configuration` and close the session before ordinary Host
adoption; this session itself grants no protected operation. An existing intent
must match the original complete selection, so this entry cannot upgrade a
retained run-only Account. Reopening uses
`restore_native_local_product_configuration`, authenticates the saved bodies and
generations, and never invokes the fresh issuer. Missing/changed originals refuse;
a removed Account cannot be regenerated to restore authority. The current Account
is still checked at every existing provisioning/lookup boundary.

This is first-adoption configuration and original-key lookup connectivity, not
an installed Python worker, complete cold worker recovery, normal numerical
profile or public wheel acceptance.
