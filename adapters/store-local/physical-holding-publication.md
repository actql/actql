# Physical holding metadata publication

## Original Index admission within publication

The publication caller passes its original immutable Index wrapper alongside
the existing wire, inventory and evidence. The existing contract control may
recognize that exact wrapper under the current limits. Unrecognized wrappers,
copies and legacy controls retain full wire admission; a refused or malformed
nominal response cannot become fallback success. The supplied wire, identity
and identity field must agree with the selected original.

The same commit's private Effect inspector consumes that already-admitted Index
and its parsed body. Independent stored-evidence inspection still admits its
own input. Its public Store method forwards only the preparation and supported
reader port; caller-supplied extra arguments cannot inject the private retained
observation or replace the parsed Index body. Neither path retains
authorization, present-disk integrity or a
durability acknowledgement. Selected physical evidence, current permission,
claim/CAS, original Unknown confirmation and real cleanup remain independent.
No cross-operation Index cache or additional publication authority is created.

After a new Store commit acknowledges the exact issued Index identity, the
same publication caller retains that original wrapper for finalization and its
return value instead of reading the same contract again. This does not replace
the actual Store commit, evidence validation, Index installation or cleanup.
Idempotent commits, different winners and reconciliation still select their
actual stored Index; an unsuccessful or pending commit cannot select this path.
Attempt finalization and terminal/Unknown computation retirement stay separate.

## Selected native evidence originals

Known publication kinds select the existing publication metadata table directly.
A missing selected row keeps the original file fallback without searching
delivery attempts. Untyped reads and delivery kinds retain their existing
generic lookup; schema reads remain file-backed. Representation selection does
not replace contract admission, physical verification or per-operation reads.

The existing publication operation reader receives the same issued evidence
wrapper already held by its caller. A native read still selects the actual row
by CID and compares its name, identity and complete wire before the existing
contract control may recognize that original under the current limits. A
changed row, unrecognized original or omitted control takes full admission;
refusal or a malformed nominal response cannot become successful fallback.
This only removes re-admission of equal immutable input, not the selected read.

The existing commit-local original map owns that observation. A later public
reader or commit reacquires and admits its own selected row; no Store-wide
permission or disk-health cache is installed. Full admission cannot make a
copied evidence wrapper nominal for the final chain Owner. Actual payload
verification, physical FD cleanup, current checks, claim/CAS, durable mutation
and same-original Unknown confirmation are unchanged.

Independent verification adapts its default reader to the two supported CID
and representation arguments. A private commit's optional contract hint never
becomes the low-level reader's distinct generation-retention flag. Supplied
operation readers retain their explicit original-forwarding contract.

## Original ownership retirement

The existing Store ownership handle remembers successful owner-record unlink
and ownership-directory removal separately from final root durability. An
error after one acknowledged phase cannot force a retry to reconstruct that
record or repeat its deletion. Once the original directory was removed, only
root durability remains; a legitimate successor's owner record is not read or
modified by the predecessor's retry. The original key stays held until the
whole original release returns success.

Root device/inode are observed before acquiring ownership. During original
retirement the handle pins ownership-directory device/inode before removal;
retries refuse a replacement directory or root. Initial absence and foreign
token/pid remain refusal, not evidence of retirement. These path checks do not
claim hostile-filesystem race isolation. Unknown syscall outcome is not an
acknowledged phase. Initial acquisition and other directory-FD failed-close
paths remain separate from this retirement boundary.

Two additional phase Booleans and four device/inode scalars remain in the
existing handle, overlapping temporary Stats objects, read/parse state and
the existing close Promise/error/key. They are explicit lifetime components,
not a new Owner, lease, byte price or a normal numerical resource profile.

Final root retirement also keeps its original opened directory FD inside that
same ownership handle until close acknowledges success. An explicit false or
rejected close leaves the Store unclosed and its private key held. After a
successful sync, the next single-flight Store close retries only the original
FD close, without opening or syncing another directory or touching a successor
owner. If sync itself failed, its original failure and any close failure remain
distinct; only after that FD closes may original-root durability be attempted
again. The acquired FD's device/inode is checked against the original root.
An already-owned pending FD drains before pathname-dependent refusal, even
after the original root is renamed or replaced. The foreign/missing-root
refusal still keeps the Store unclosed and its key held; no replacement open,
sync or ownership operation is allowed without the original root check.

One nullable FD reference and one acknowledged-sync Boolean extend the existing
handle. The transient FD Stats, sync-failure flag/reference, close cause and
diagnostic wrapper overlap the existing close Promise, ownership phases and
key. Native directory lifetime remains the selected Host responsibility;
managed references and pending cleanup are not free or numerically funded by
these filesystem tests. This does not generalize retirement ACKs to other
directory readers or publication paths.

## Original opening directory custody

Ordinary opening observes prepared-custody and pending physical-holding-deletion
and Result-deletion directory names without mutating them. Committed holding
and retention-extension namespaces are not enumerated at this boundary.
Those read-only observations and unchanged namespaces
need no new directory acknowledgement. This is not a durable-write shortcut:
the selected custody unlink, holding installation/deletion, retention append
and Result retirement retain their own actual acknowledgements. Pending
recovery still owns its same cleanup, and a failed required ACK cannot become
success merely because the containing directory was observed during opening.

The existing staging, prepared-schema staging, metadata-deletion staging and
clock directories likewise need no new acknowledgement when opening removes
nothing. Their selected namespace/type checks remain. Actual interrupted
temporary-file removal still precedes the same directory acknowledgement, and
a failed acknowledgement refuses opening rather than returning a live Store.
Initial format creation, ownership acquisition and later clock/publication
writes retain their independent durability and close responsibilities.

Manifest read grants follow the same selected-operation boundary. Ordinary
opening does not enumerate their committed grant/use history. A selected new use
checks its own grant directory and use names, recovers legacy staging files with
their real directory acknowledgement, and preserves the existing use limit.
New use files borrow the Store's existing exclusive final-link writer and its
file-sync, close and directory-ACK responsibilities.

A visible existing use is not acknowledgement of a prior failed directory sync.
The selected reader confirms its same bytes after the real directory ACK before
returning idempotent success. One last acknowledged target may be retained in the
same Store lifetime; it is neither an authority cache nor a grant-use refund.
Cold Stores and distinct targets establish their own selected observation.
Failed original FD cleanup stays in the existing writer set, with captured child
methods/receiver and single-flight close-only retry. Store retirement waits for
that same child acknowledgement; cleanup does not repeat grant issuance or reads.

Directory durability during initial format and ownership acquisition keeps its
original opened FD through false or rejected close. The failure exports the
same close-only, single-flight cleanup facade, without reopening the pathname
or repeating sync. If sync also failed, the raw primary (including null or
undefined) and the close cause remain distinct. Diagnostic attachment defines
own data properties when safe; frozen/readonly errors or a preexisting cleanup
facet remain original causes of a wrapper, never overwritten responsibilities.

The existing ownership release closure is constructed immediately after the
original token is written and before either ownership-directory or root sync
is awaited. The existing opening-failure receiver drains the failed FD first,
then retires that same ownership. Its copied private key remains live until
both acknowledge cleanup. A format-root failure before ownership uses that
same receiver without inventing an owner token. The caller must still retain
the failed initialization carrier; this is not a new global opening registry
or a claim that all publication callers consume every directory-sync failure.
Missing/foreign roots and original ownership validation remain refusals.

The FD reference, sync-failure flag/raw value, original close cause, status and
retry closures, single pending flight, descriptor workspace and optional
wrapper overlap the existing opening configuration/key and ownership record.
Native directory adapter lifetime remains selected trusted Host responsibility;
none of these managed references or pending duties is zero-priced, a new lease
or a normal Model four-role numerical supplier. Cleanup acknowledgement is not
Store initialization success, durability replay, Provider permission or send.

## Bounded metadata reader close acknowledgement

Private evidence reads admit the selected holding metadata once and acquire its
selected ciphertext once. The existing physical reader hashes that same FD's
bytes and observes its close before AEAD authentication can return plaintext.
The intermediate bounded buffer is private, not an application callback; no
plaintext escapes on a digest, extent, authentication or close failure. The
same physical-holding reader count prevents retirement while that FD's close
remains pending, and close-only retries never repeat the read or decryption.
A new operation reacquires its holding and payload; no successful admission is
cached across operations. Generic public holding consumption retains its full
pre-callback payload inspection and its original refusal behavior.

Private confirmation captures its supplied scalar binding before the first
await and serializes the actual read and acknowledgement with the existing
material-retention queue. Its selected holding and authenticated payload are
internal facts of that operation, not fresh inspection inputs for its pure
helpers. Confirmation still syncs the holding directory and adopts the exact
prepared objects only after that acknowledgement. The existing reader count
remains held through this boundary, so close and retirement cannot discard it.
Model raw reads likewise retain the one selected holding across descriptor and
content acquisition, verify both AEAD envelopes and the original plaintext
content CID/byte count, and never expose bytes after a partial read or failed
original close. Neither reuse path persists an Allow or supplies a new grant.

If confirmation's directory sync exports a still-pending acquired FD, the same
Store retains that child in its existing failed-writer collection and retains
the holding reader through the child's actual close acknowledgement. Captured
cleanup methods and receiver are retried single-flight; only the original
own-data `pending: false` observation retires that duty. Store close drains this
same child, and holding retirement waits meanwhile. Cleanup neither reopens or
syncs the directory again nor repeats payload reads/adoption or returns a saved
confirmation. The original sync/close failures remain causes of the outward
pending-cleanup failure. A later confirmation still performs its own actual
read and required acknowledgement.

New and idempotent holding commits, shared holding publication and borrowed
holding directory acknowledgements use that same failed-writer custody. A
later successful read or reconciliation may establish the exact holding's
durability, but cannot acknowledge another acquired directory FD's close.
The same original FD keeps Store ownership and its holding-retirement fence
until close-only retry confirms; it is not replaced by the reconciliation FD.
Prepared payloads are adopted only after the final holding acknowledgement.
Borrowed pre-publication and shared-holding acknowledgements do not adopt
prepared payloads or publish a target before their original boundary succeeds.

The existing bounded metadata reader does not publish bytes or invoke its FD
retirement callback after an explicit false close. Its existing cleanup facade
keeps the same native handle and callback through rejected or false close-only
retries, without reopening the pathname or repeating a read. Only successful
original close clears the reference and acknowledges that same reader duty.
The ordinary mutable primary failure is retained where diagnostics can safely
be attached; readonly diagnostic fields use a fresh wrapper with the original
failure as its cause. Field inspection or attachment must not mask that failure
or discard the cleanup facade. Existing frozen status snapshots stay unchanged.

The three-name descriptor-check Array, temporary property descriptors and an
optional error wrapper/cause can overlap the original error, raw metadata,
callback and pending retry Promise. Their finite reference count is not a byte
price or a bound on arbitrary Error graphs. The original read reservation and
Store reader count remain responsible until actual acknowledgement; no new
grant, reservation, Owner or normal numerical profile is supplied here.

## Existing atomic metadata publication

Effect capture cleanup custody retains one bounded same-Store observation of
its last acknowledged record. A repeated update still admits its incoming Run
and holdings, reads the selected current record and rejects conflicting
holdings. It does not rewrite unchanged bytes when their device, inode, extent
and modification/change timestamps still match the record installed after the
actual file-sync, close and directory acknowledgement. Changed records,
replacement files, failed acknowledgements and fresh Store instances retain
the original physical write protocol. Forgetting the custody or successfully
closing the Store clears this observation. It is not capture completion,
permission, publication or a physical holding release acknowledgement.

The admitted Run is an internal fact of each custody operation. Record reads
and final custody unlink use that same original rather than admitting it again
at a pure helper boundary. Retirement still validates the selected holdings and
keeps their actual cleanup acknowledgement before removing the custody record.
Cheap current/closed checks remain at the queued update's actual entry and
immediately before final custody unlink after asynchronous holding retirement.
They do not admit the Run again, and a closed Store cannot use a retained Run
or durability observation to mutate its former custody namespace.

Physical holding creation, sharing and deletion intent use the existing Store's
staging directory and exclusive hard-link publication. The complete original
record is written, file-synced and closed before it receives a final name.
The original containing-directory durability acknowledgement remains separate;
visibility alone never adopts prepared custody or confirms an unknown commit.
Existing record bytes, CIDs, conflict comparison and reclamation rules remain
unchanged. Incomplete bytes occupy only an unpublished `object-<UUID>` staging
alias, which the same Store's existing restart recovery removes. A crash after
the exclusive link leaves complete final bytes, not a new commit receipt.

This does not repair a corrupt final record. Each selected holding read admits
its bounded body against the exact requested holding CID before using it;
unrelated immutable records are not all read at ordinary startup. Selected
holding reads retain their own no-follow/nonblocking FD, regular-file,
extent, generation and exact record-identity checks. Ordinary open does not
enumerate or stat every committed holding name. A malformed or wrong-type
unrelated entry is left intact; selecting it refuses rather than treating it as
missing or repairing it. An actual pending cleanup may still inspect shared
references when needed to retire its original allocation.
Required pending-deletion recovery still reads its own original records and refuses
invalid identity or bytes. No missing/empty record is interpreted as an
unapplied operation, permission or cleanup success. Physical capacity accounting,
other Store recovery and their actual acknowledgement duties are unchanged;
this does not make all remaining opening inventories history-independent.

Committed publication owner links are also selected-use facts. Ordinary open
does not enumerate and admit every committed Index merely to check all of its
inventories and holdings. Index inspect, public durable confirmation, lookup,
and Result Binding selection read the selected inventory and require its exact
Index CID, namespace, authority scope, Run and publication attempt. Only that
inventory's holding links are read; missing, retiring, malformed or foreign
owners refuse the selected operation. A later operation acquires new originals.
Already inspected Pure/Effect evidence reuses its own holding facts when joining
the same inventory rather than reading the same bodies again in a pure helper.

During one serialized Index commit, a newly written semantic body may also
retain its private bytes and digest in that commit's existing observation map.
This observation is published only after the original file sync and close,
both new physical and semantic links, their actual directory acknowledgements,
and writer cleanup succeed. Its metadata inventory consumes that same original
without reopening and hashing it immediately. Existing objects or aliases,
including names left by an interrupted attempt, still use the actual semantic
reader and its hard-link validation. Failed durability never publishes this
observation or retires the pending writer. The map is operation-local and its
bytes never escape; the next public read acquires its own original and detects
a changed or replacement alias. No permission, claim or physical ACK is cached.

Internal index durability reconciliation remains separate from public selected
use. It still confirms the representation's real durability and original custody
outcome, including before metadata has been fully staged or during retirement.
This is not a durable ACK or permission cache. Pending deletion, prepared custody,
and quota accounting retain their original responsibilities. Payload accounting
and legacy file shared-reference discovery still walk history; indexed publication recovery
does not establish history-independent Store startup or replace an explicit
integrity inspection.

### Indexed pending publication recovery

The existing Store database retains only unfinished publication inventory
originals in its private recovery index. Before acquiring an inventory file,
the Store stages its exact Index CID and bounded inventory wire in a real native
transaction. An existing file representation retains its own write, close and
directory acknowledgements. The pending row is removed only after the original Index
durability acknowledgement and schema adoption. At that point the same Store may
retain the exact bounded completion original and include its removal in the next
already-required transaction of this database. Retention is not a durable ACK:
the original pending row remains until actual COMMIT, and an interrupted process
uses the existing targeted pending recovery. If no later transaction occurs,
close performs the real completion write; an existing physical-quota seal can
include it without a second transaction. Native close remains a separate duty.
These transitions do not replace file acknowledgements or establish a minimum
barrier count. Strict recovery completion remains immediately durable.
The retained map is bounded by the existing pending-entry and wire limits; it
keeps immutable originals, not permission or a new byte allowance. Successful
COMMIT retires exactly those originals. Lost replies retain them for the same
mutation or close retry, and actual native close releases their managed aliases
without claiming an unrelated uncertain mutation succeeded.

Only current-format recovery may complete pending inventory coverage. The
Store confirms each selected Index's actual durability, retains only
unfinished originals, and commits coverage with the pending rows atomically.
Older private database versions are refused before mutation, not migrated.
Subsequent opens read pending rows rather than enumerating committed inventories
or Indexes. Missing adopted tables, coverage or malformed selected originals
refuse; they never rebuild coverage from absence or recreate authority.

A lost native reply retains the same mutation kind, CID and inventory wire.
Only a real same-original confirmation write settles that Unknown; observing a
row is not its acknowledgement. An unfinished publication may restore only its
retained inventory bytes, not dispatch or replay a Run. Once a durable metadata
deletion marker owns the same complete inventory, recovery transfers the pending
original to that marker before physical retirement and never reconstructs its
already removed file. Failed transfer or physical cleanup retains the original
retry duty; no quota refund, permission or cleanup success follows from a callback.

For a file-backed Index, inventory staging precedes the public Index commit's
payload-custody owner.
If its native COMMIT reply is lost, the Store therefore retains that exact
staging original in its existing pending-writer collection and returns its
storage-only, single-flight finalizer with the original Unknown failure. The
finalizer calls the captured same native method and receiver with the same
inventory; it neither selects a replacement mutation nor treats a visible row
as an ACK. Concurrent finalization shares one attempt. An unresolved original
continues to block native reads and Store retirement; close may drain this same
writer but cannot erase its duty. A successful confirmation retires only that
staging acknowledgement, not the Index or Run publication. The next commit
still performs its normal current, evidence, ownership and Index transition.
Legacy file-backed staging retains the same protocol and separate file ACKs.

New inventory bodies are durable originals in that same native staging
transaction, not duplicate filesystem preparations. Completion removes only the
pending lookup; the exact bounded inventory wire remains available to selected
reads. A file-backed Index and its actual directory acknowledgement still
determine that publication. Stage and completion remain distinct logical transitions;
storing the body with its pending lookup removes the redundant inventory-file
write/sync/close and directory sync, not those logical transitions or payload ACKs.

Private native-inventory count and wire bounds are enforced before insertion.
Initial current-format creation installs their tables and count atomically; adopted
missing tables or invalid count refuse without resetting originals. Prior
file inventories remain files and use the same selected-use checks. They are
not copied into a second representation during ordinary open. Retirement binds
the same complete durable deletion marker before removing the native original
and its pending lookup together. Same-original Unknown confirmation is retained.
Shared contract and holding cleanup checks both representations before reclaim.

### Indexed native metadata references

The existing Store database indexes native inventory owners by reference kind,
exact contract or physical-holding CID, and original public Index CID. Selection
excludes only the retiring original owner. Each returned inventory is admitted
at selected use and must actually contain the requested CID; the existing Run,

is neither loaded nor parsed for this ownership question. A selected physical
holding remains until its last real owner retires and actual unlink and directory
acknowledgement complete; an absent owner lookup is not a physical cleanup ACK.

Insertion and inventory-wire update triggers derive these references from the
same bounded native body inside its existing transaction. Foreign-key cascading
removal deletes its references in the original retirement transaction. Body,
pending lookup, usage and references therefore share actual FULL/fullfsync
COMMIT, rollback and original Unknown confirmation. No additional per-publication
transaction, authority, capacity allowance or refund is introduced. The selected
statement belongs to the same connection and is acquired only on use; real
native close precedes retirement of its managed statement reference.

One bounded private-format transition reads prior native inventory originals,
checks count and wire bounds, and installs reference rows, triggers and version
coverage atomically. Later ordinary opens admit that schema without reading
native inventory history. Missing adopted tables, index or triggers refuse;
they never silently rebuild coverage. A lost adoption reply remains Unknown even
when a later open observes the completed transition. The retained inventory and
pending original are not reissued, replaced or treated as dispatch permission.

Prior file inventories keep their selected admission and legacy ownership walk.
That legacy path and other accounting work remain separate costs; this index
does not establish fully history-independent Store startup or public latency.

### Native Index publication

A native publication attempt can commit its public Index through the same
exclusively owned Store SQLite connection. The exact namespace, authority scope,
Run and derived metadata key locate the original Index body. The complete
logical tuple and immutable Index CID are unique under that actual transaction;
the Index body, inventory, pending lookup, derived material references and quota
delta become durable together. The transaction checks the original attempt/Run
and the exact previously admitted committing-record CID before insertion, as
well as the existing whole-Run retirement fence. A changed progress original
refuses instead of publishing from a stale preparing or committing observation.
This preserves the separate logical Index commit; it does not merge it with
an execution claim, a delivery START/END, approval or protected dispatch.

The Store first admits the actual incoming Index and validates its captured
chain, bindings, schema, payload and existing holdings. Staging retains only a
bounded intended inventory and an Index-body reservation, not an ACK or stored
evidence. Payload custody is acquired before the real native COMMIT. New native
Index bodies consume the same object/UTF-8-byte quota, without also creating an
object file, semantic hard link or filesystem Index. Independently adopted file
Indexes and file attempts retain their real write/link/directory protocol.

A selected native read admits the actual stored Index body and binds all tuple
fields and the CID before use. A conflicting file representation refuses.
The existing last-confirmed-CID observation is installed only after a real
native write/COMMIT ACK. Cold independent confirmation compares the complete
selected original and performs an exact-revision native write, not an ACK from
mere row visibility. Later reads still select their actual Index original and
current Host permission remains independent. The existing file path keeps its
real directory ACK and post-ACK selected read.

Lost native replies retain the same captured method, receiver, key, body,
inventory, bindings, progress and quota reservation in the existing writer
collection. Concurrent acquisitions share that existing unresolved duty; they
cannot replace it with another writer. Cleanup confirms storage first through
the same original write/COMMIT, then resolves the original payload custody.
Repeated lost confirmation replies keep the original supplied revision fixed
for identity, while the same native holder tracks the before/after revision of
its most recent actual write. Each retry accepts only that bounded pair and
performs another real write/COMMIT; an unrelated revision jump still refuses.
It neither resends an Effect nor issues another Run, receipt or approval.
Failed custody construction returns only its unconsumed staging reservation.
Native close, actual payload cleanup and the original publication/computation
holder remain distinct duties; no successful `finally` or GC event issues ACK.

Derived material rows select only native owners of the requested physical CID,
in bounded pages. The Store checks each selected Index, exact binding and Result
deletion marker before deciding whether the payload is still owned. Immutable
binding facts are shared only within that one cleanup operation. A last-owner
unlink retains its charge until the actual directory ACK, including same-original
retry after an absent name. Retiring the native inventory removes its Index and
material references in the original retirement transaction; the durable deletion
marker still owns physical reclamation and contract quota release.

Private format adoption creates these tables and coverage atomically. It does
not scan or translate historical file Indexes or recreate a missing publication.
Missing adopted schema refuses. A lost adoption reply remains Unknown even if
a later open admits its completed transition. Subsequent opens use selected
native rows and targeted pending recovery, not an all-Index integrity sweep.
This representation changes no public wire, identity, permission or limit;
other legacy ownership/history work remains separate and actual public latency
requires matching ordinary-package evidence.

### Indexed Run metadata retirement

The same private database keeps a minimal retirement fence keyed by the complete
metadata key, with an index over the original Run CID. Delivery and publication
operations select that Run alone; they do not enumerate or parse other retired
Runs. The fence denies the whole Run as before, independently of namespace or
Result permission. It is not authorization, capacity or a physical cleanup ACK.

A full deletion marker remains the original pending physical cleanup inventory.
After its actual file and directory ACK, its native fence is staged in the same
transaction that transfers the native publication inventory. A same-lifetime
intent conservatively hides that Run before the transfer ACK. A lost native
reply retains the exact original inventory and fence for confirmation before
other native reads; a legacy file inventory may transfer without a native body.

Only after the original cleanup completes does the native fence record retirement.
The full marker is then unlinked and its directory really acknowledged. A failed
final ACK retains the same cleanup even if the marker is absent and the native
row is already retired. Retry does not manufacture success from either fact.
Completed fences retain only metadata key, Run and retirement state, not the
deleted metadata bodies. They do not permit re-creation of that Run.

Current-format building coverage reads its full and compact marker files
in bounded native batches. Durable coverage is completed before redundant compact
files are removed. Interrupted coverage resumes the same tuples idempotently;
missing adopted tables or incomplete coverage never mean not-found. Subsequent
opens recover pending physical markers only. Other quota and legacy shared-reference
history work remains separate; this is not fully history-independent startup.

## Same-owner cleanup and inventory

A scoped Result reader retires only after both its use callback ends and its
actual consuming FD closes. The existing consume operation's original close
notification cuts that same generation-reader reference. Failed close leaves
the existing cleanup handle responsible, even after the caller receives an
error; Store close and Result deletion remain blocked by the retained reader.
Retry closes the same FD without reopening, rereading or repeating a sink.
No-consume completion and failure before FD acquisition release only their
scope reference; a successful sibling reader cannot retire this duty twice.

The existing Store retains each active metadata writer's record in its private
writer set before opening its staging FD. Holding publication keeps its existing
exclusive writer-admission fence. A false or rejected close keeps that exact FD and forbids final
publication or staging unlink; retry only closes/unlinks/syncs the original
staging alias, never rewrites bytes or creates a new holding. Cleanup is
single-flight, and `Store.close` retains/drains the same duty even if the
caller sanitized or discarded its error. Original prepared-object custody and
the holding-directory ACK remain independent. No key, ownership or capacity
is released merely because a callback returned or cancellation was requested.
After confirmed cleanup, an escaped cleanup handle drops its explicit original
Store/writer association; its retired status does not retain that live set.

Prepared-schema restart recovery first selects its pending marker names. An
empty set performs no contracts/objects directory acknowledgement: it has no
schema transition to confirm. A nonempty set retains the original directory
acknowledgements before recovering its exact markers and physical allocations.
Selected reads and subsequent writes retain their own integrity and real ACKs.

An existing schema preparation retains the device/inode scalars already checked
by its actual semantic reader against the digest object's hard link and extent.
It joins those same-operation facts to the existing prepared-schema generation
instead of immediately repeating both pathname observations. Only this reader
requests the extra frozen generation pair; ordinary contract reads do not retain
another generation object. The reader still hashes its actual bytes, compares
the requested schema and closes its original FD before returning. A later
preparation reacquires its own reader, and a changed retained generation refuses.
New or pending writers keep their final alias observations and real durability
and cleanup duties; the reuse supplies neither capacity nor an ACK.

The original metadata envelope includes the admitted record/Buffer, temporary
path/UUID Strings, file and hard-link/directory operations, writer-set entry,
closure/status/cleanup record, pending Promise/flight, retained original FD and
failure/cause references. The original prepared payload and commit queue may
overlap all of these. A successful unlink is not its directory sync, and a
weak reference or GC opportunity is not a physical acknowledgement. This
inventory is not a byte grant or a normal four-role Model profile; unknown
layout/bootstrap costs remain unknown, and existing limits do not increase.

### Trusted clock write observation

Ordinary opening admits clock entry names and reclaims interrupted legacy
staging files with their real directory acknowledgement, but does not stat
each stored clock file. The selected clock reader still opens the exact
original with its existing file/type, extent, content/checksum and floor
checks before sampling or accepting an observation. An unavailable selected
floor is not fresh initialization. Name enumeration for legacy staging remains
bounded opening work; this is not a history-independent clock directory.

A warm fixed-length clock update consumes its already typed observation after
the same original file completes write, sync and close. Post-sync FD state and
post-close path state must agree in device, inode, size, modification and change

Each later operation still checks the current physical version; changed bytes
receive ordinary bounded checksum/time admission. Confirmed-floor loss,
rollback, corrupt replacement and unknown durability remain refusal. No write,
sync, close or cold directory acknowledgement is omitted. The no-write flush
and cold/legacy replacement protocol retain their existing post-ACK read; this
optimization introduces no new cold confirmation filesystem operations.

A Result description selects its committed Index and exact Result Binding once.
The description, binding inventory and retention-extension lookup consume those
same admitted values; a private helper is not another authorization or semantic
boundary. A file-backed Index's immutable semantic alias still receives its original
bounded FD, inode and digest checks, but byte-identical canonical wire reuses

The payload reader also consumes the parsed Binding returned by its original
contract read. Selection and the physical verifier reuse that same private body

The existing Store queues, bounded preparation map and cleanup holder retain
request metadata through their actual terminal; no second recovery engine or
new authority is introduced.

File-backed Index publication stages its existing complete publication inventory
before installing the Index body. That same durable owner covers the intended
Index digest and already owns terminal uncommitted metadata reclamation; it
needs no duplicate physical-preparation transactions. Independently present
Index aliases still undergo their actual original acquisition and physical
binding checks. All file/directory acknowledgements, commit reconciliation,
Result custody, current checks and selected readers remain mandatory.

The real SQLite/filesystem tests distinguish pre-alias process exit, an alias
whose directory reply was lost, an unknown borrower, independent adoption and
both committed and rolled-back native settlement uncertainty. Raw quota census
fixtures interrupt only an unlinked write or an already acknowledged raw writer;
an unacknowledged semantic body is not an adopted physical Result.

### Physical allocation ownership through retirement

A content CID and an observed device/inode pair do not identify a fresh allocation
forever: the filesystem may reuse an unlinked inode. Before an owned physical
unlink, the Store retains an actual read-only FD to that exact original and marks
its existing native physical lifetime dirty. The FD prevents inode reuse while
unlink or its containing-directory acknowledgement remains pending. A replacement
can share the same content CID, but is a distinct allocation and has its own charge.
Pending cleanup carries the immutable retirement holder, never a fresh CID lookup.

The original unlink is single-flight even when cleanup reaches it through different
Store serializers. A retry checks the same retained FD and cannot unlink a pathname
now naming a replacement. After the real directory acknowledgement, one holder-owned
flight closes that original and settles only its Store quota. Same-CID admission is
fenced through close and quota uncertainty; unrelated content and other Stores do
not borrow that fence. Duplicate and late callbacks reuse the same owner flight.

An unknown native close is not proof that the FD remains open. In Node, the original
FileHandle can invalidate its descriptor before the close promise settles, and a
later close can resolve without repeating or confirming the original operation.
The Store therefore retains the exact original close promise. Rejection or explicit
false quarantines its holder, quota and admission fence; it never retries a numeric
FD or treats a later vacuous close as acknowledgement. This fail-closed lifetime
requires exclusive process recovery, not automatic deletion or guessed success.

After process death, the operating system releases the dead process's FDs. Before
admitting any new writer, the existing exclusive Store opening protocol observes
its durably dirty lifetime, acknowledges the actual object directory, and reconciles
the bounded physical census and retained custody originals. A replacement admitted
before that death could not reuse the still-held old inode. Clean current-format
reopen remains unchanged. This introduces no new public identity, normative version,
capacity grant, private-format migration, or second physical accounting authority.

### Store owner metadata publication

On supported normal Local Files bindings, a new owner record is written, synced
and closed in a private `.owner-opening-<UUID>` directory. Its directory is synced
before the existing platform no-replace rename publishes the fixed `owner` name;
the Store root then receives its separate durability acknowledgement. An existing
empty directory, symlink or foreign owner is never an overwrite condition.
Unpublished stages remain owned by their original opening handles. Another
opener preserves them: its execution lease cannot prove that a concurrent fresh
preparer, which has not qualified that lease yet, stopped or returned custody.
An empty or corrupt *final* owner record remains invalid, including records left
by an older implementation. This protocol does not repair historical state.

Fresh preparation retains its existing root descriptor before staging but defers
execution-lease qualification until Store startup, as before. Qualification keeps
the original prepared owner and token. It writes a separate complete lease record,
syncs and closes its writer, and atomically replaces only the original owner file.
The private native replacement checks the old file identity, extent and timestamps
under the original owner-directory descriptor immediately before replacement. Its
committed replacement becomes the retained physical original before any subsequent
child-close or directory-sync failure. A copied token in another inode is refused.

The existing opening/retirement custody owns the temporary path, original writer,
old/new metadata overlap and temporary native directory child. Failed writer close
remains pending; a consumed native-close Unknown is never retried as a numeric FD.
That child must retire before the owner metadata, stable lease, root or key can
retire. Unsupported native delivery retains its conservative legacy behavior and
cannot issue an execution-stop receipt. Public Files publication and Store identity,
authorization, quotas, durable history and format contracts are unchanged.
