# Installed HubSpot row Source

The normal installation table selects this Source factory. Its component tests
use actual separately compiled Common and HubSpot runtimes, the original
Account/Credential owners, SQLite and loopback HTTPS. This is not evidence of a
pristine installed distribution, live service, adopted numerical profile or the
complete HubSpot read/write target.

- Responsibility: supply original account/property metadata, physical target
  binding and requests to the existing generic installed row Source. The Common
  declaration, checked Program, Account decisions, RowRun, capture and cleanup
  remain with their original owners.
- Inputs and outputs: a closed explicit Source/Site profile and bounded complete
  original metadata bytes produce the Common full relation declaration. Every
  observed property goes through the existing provider value contract; unknown
  types refuse rather than disappear. The factory exposes the standard Source
  port, never raw credentials or a parallel acquired result.
- Identity: bind connector, canonical portal, origin, original metadata, Site
  generation, runtime and Account context. Managed identity uses the same observed-FD CA bytes that reach Site; the standalone utility keeps its DATA-only hashing purpose and cannot load a Source. The top-level original record id is
  a conditional declared candidate key. Provider page admission and cross-page
  duplicate checks must succeed before capture; company domain is not a key.
- Ownership: the registered factory requires the same loader-bound Source context, managed configuration reader and Host service before metadata/native entry. The existing bound facade reserves each original decoded metadata/native constructor peak on that initial parent before projection. The original Environment is passed unchanged to RowSource and its registration/finish; Source retirement precedes initial-parent close. The generic Host retains the original acquisition, one borrowed
  response/cleanup port and the same private Credential binding. The connector
  installs that cleanup callback before I/O. Initialization failures retain any
  already acquired Site on the existing cleanup carrier.
- Synchronization: separate current Account decisions cover data, account
  details and properties. Each operation has its own authorized nominal use;
  current checks surround awaits and the physical send. The retained binding
  prevents a resolver rotation from substituting another account's token.
- Failure: preserve original codes, complete received observations, physical
  Unknown and cleanup custody. Schema drift, duplicates, foreign metadata or
  exhausted bounds refuse a complete Source. No replacement lookup, partial
  capture or implicit retry is performed.
- Cancellation: forward the original signal. Cancellation is not a close ACK;
  the original RowRun response cleanup and Credential binding must confirm
  retirement before releasing the original retention.
- Resources: original decoded metadata and each native account/property constructor compose with the same initial Source envelope before projection. Original parser/value/declaration node counts stay separate from decoded text and wire limits; the full selected native peak is retained through retirement. The trusted installer supplies independent positive response,
  parse, page/request/row, schema/output and secret limits. Every received
  identity/schema/data body is charged to the same original acquisition before
  decode. These units and the cleanup callback do not establish wholephase
  simultaneous retention funding or a normal numerical profile.
- Extension: use the normal connector bundle generator and existing Common
  declaration/Account/RowRun APIs. No connector-local ledger, finish/capture
  owner, permission fallback, sampled schema or Provider URL redirection.
- Verification: `../test/installed-hubspot-source.test.mjs` checks full decimal
  and array schema, exact record ids, same-RowRun capture, separate metadata
  permission, current token rotation, foreign originals, cross-page duplicates,
  final schema drift and cancellation. `../test/hubspot-object-schema.test.mjs`
  retains independent full schema and key-fact expectations. Execution/runtime
  source and artifact correspondence are recorded separately from this source
  reference. The current registered-loader fixture owns its actual initial Resource, Sources and cleanup carriers, and retires children before the original parent. The standalone prefix fixture consumes its original typed installed sequence contract. Its explicit RowRun/Ledger cases do not certify ordinary Request/Plan/provider output/failed-child funding, pristine distribution or public acceptance.

## Remaining-row request bound

The object reader captures one pageRows value from the smaller of perPage
and the same original acquisition's remaining row allowance, before preparing
that page's request. The outgoing list limit and the actual provider decoder
consume that same value. A positive remaining allowance is required before
another request; no response is sliced to make a larger page fit.

A next cursor at the row ceiling still refuses completion without another
request. A server response exceeding the requested allowance still fails
complete page admission. Original response charging, retained failure bytes,
Account/current and nominal use checks, cursor handling and final property
recheck keep their existing owners and ordering. This bound neither raises
limits nor supplies Source authority, funding, completion or physical close.

HubSpot's [list endpoint](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/companies/get-companies)
defines limit as the per-page result maximum and after as the original
forward cursor. No response-provided link is followed. The same operation,
properties and archived selector remain selected by the existing reader.

The private `prepareInstalledHubSpotMaterials` entry is the same metadata and
Catalog constructor used by the standard Source loader and the installed Effect
assembly. It retains every declared resource and observed property, including
read-only fields; an Effect mapping must not replace this full Source inventory.
It runs through the supplied original parent construction ports, returns the
same provider-runtime Catalogs and Common declaration, and opens no Site or
authorization. Native-only explicit-port component cases check this material
correspondence and failure ordering; they do not establish whole-initialization
Ledger funding or a normal installed Effect flow.

The Source freezes the same validated JSON metadata records and object array
in place before native preparation. Accessors and non-data array members are
not JSON originals. The existing `prepareReadTarget` constructor and Common
quantity retain one frozen target inventory with the original ordered fields;
strings are borrowed, and the one metadata digest is retained once. The real
reader's object type, approval matching and Common physical target selection
consume that same inventory. The complete Site binding preimage is unchanged.
Common may reuse only its original generation and ordered-field correspondence;
fresh Account/current checks, metadata observations and retirement still run.
The connector supplies no alternate checking, permission or cleanup owner.

The same metadata validation observes its closed original token/String extent.
The existing Core profile identity recipe and native input constructor fund
canonical/hash workspace before the one loader metadata hash, then fold that
workspace away after retaining the actual targets/digest. The final Site binding
uses that digest through the same private preimage as the metadata-taking public
utility; its complete wire identity is unchanged. Refusal precedes hashing, and
no parser, whole-tree measurement or policy-maximum estimate is added.


## Managed Source protocol

The standard HubSpot loader registers its original `providerReader` through
`sourceReaderImplementation` and `createSourceReader` before creating the Row
Source. The same Plan selects that reader; the old physical `readPages` port is
not a fallback for a missing managed constructor. Account identity, initial and
final property Catalog checks and complete page projection remain provider
rules. Metadata resources require their own fresh Account decisions and
original grants; a data grant cannot authorize either metadata resource.

The generic Reader owns physical response custody, charge-before-decode,
current/cancellation fences and cleanup-bound RowRun retirement. The private
Common quantity composes that reader's original inventory with the bounded
HubSpot sequence. Each charged body adds its actual byte extent before any
native projection, including complete earlier/failed prefixes. Empty Sets and
body arrays carry no future row/page/request entries. Their current prefix and
one predecode page are bounded from received extents and the original per-page
limit; increasing unused total ceilings adds no initial allocation. Row output and
writer bounds stay independent; no limit, permission or Ledger is issued by
these quantities. Duplicate ids/cursors, page/request/row limits and the final
Catalog recheck remain mandatory before successful completion. Protocol tests
with explicit Reader ports prove provider rules only; actual normal distribution,
approval, UPDATE, Saved and physical cleanup require their respective consumers.


Effect metadata authorizations retain the exact Site-issued original beside
their physical `useId`. The observation adapter passes that original unchanged
to the existing managed Credential child; the useId stays in its physical input.
Target rows keep their existing same-row authorization lookup. A copied grant
scope/body cannot establish issuer purpose, and no new grant or permission is
inferred from equal fields. This two-field metadata view replaces the former
three-field copied envelope and needs no additional constructor representation.

Each physical Effect occurrence stages its own Account, property or target
constructor at both the initial and maximum extents. Received-input growth uses
that same constructor, operation and transfer inventory. The shared capture may
keep a combined metadata bound, but that bound cannot replace an Account-only
operation's initial retained material. Core still requires the live physical
backing to fit the received-input extent and its original maximum; response
projection completion and actual child retirement keep their existing duties.

Cold request reconstruction keeps the original policy wire/text envelope.
Only its actual owned Preview/recovery byte extent selects the existing Host
parser staging port. A smaller saved input cannot replace the already retained
policy ceiling; Core retains the original maximum and checked-row quantities.
