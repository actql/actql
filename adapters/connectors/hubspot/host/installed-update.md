# Installed HubSpot update preparation

- Responsibility: HubSpot adapters prepare one original UPDATE request and decode Account, complete property Catalog and selected target observations. The private row driver delegates these operations to the existing common row Effect, which retains Program admission, Preview, approval, current checks, durable claim, dispatch and cleanup. These helpers alone do not register an installed Effect.
- Inputs and outputs: The same installed Catalog and Mapping produce a logical request, then a marked physical request using the common owner's original dispatch key. The target-read request is also constructed once inside the warm row constructor or original cold recovery constructor, and is retained by that same request holder through finalization. Every physical read still rechecks its complete original Catalog against both current describes. Describe reads Account and schema. Each target observation reads Account, schema-before, the exact target and schema-after. Native projectors retain decimal strings, array values, complete schema correspondence and response bounds.
- Identity: The logical request binds connector, HTTPS origin, portal, resource, Mapping reference/CID, existing marker property, complete value and selector. The physical identity additionally binds the actual dispatch key and complete marked body. A target version binds portal, object type, Mapping and the complete canonical typed row including its update timestamp. A digest supplies no authority or atomic provider comparison.
- Ownership: Private request and current carriers belong to their original adapter instance. Cold request restoration reconstructs through fresh Native originals and compares complete saved wire and both identities. Foreign or copied carriers are refused. Source and Effect share the same Native Account identity projection rather than separate validation rules.
- Synchronization: Named credential read slots select distinct original member or row operations inside the existing total-operation limit. Fixed metadata resources use their own fresh Account read decisions, including the existing before-send check. Only the exact target slot consumes the retained same-row target authorization. The driver captures original Site/Account methods before reentry and retains only the original invocation/dispatch/control scope after Describe completes. Fresh current checks and the existing physical Credential binding remain mandatory before every send and after every read. A Checkpoint decision is delegated to the same Site only after its original facts name this member, Mapping and installation binding.
- Failure: A rejected HTTP outcome, foreign portal, changed Catalog, wrong/missing/archived/duplicate target, incomplete response, malformed marker or changed restored body is refused. Private failure custody retains the original received response sequence. The send hook performs one batch update under the original physical child and grant. Only a complete Native response correlated to the same single target produces an applied outcome. Transport errors and malformed/partial/non-success replies remain unclassified for the common Owner; no driver retry or terminal-failure guess is introduced. Nothing classifies these failures as absence, permits a write or authorizes a resend.
- Cancellation: Original signal/current refusal propagates without completing a target observation. A synchronous response projection must finish inside the original physical child; asynchronous callbacks or pending results cannot acknowledge projection completion. Existing failed/pending physical children remain the common owner's cleanup duty.
- Resources: Request and read constructors use captured immutable limits. Named slots do not raise operation, transfer or response limits. Each read retains its original funded response extent until Native decoding completes. The existing signed metadata scopes cover at most the three declared phases' Account and schema occurrences for the bounded member rows. Distinct original authorizations and use IDs retain the existing durable use inventory; reissuing an equal signed scope does not refill it. No new quantity price, Owner, ledger, cache or reusable permission is introduced. The installing recipe must fund all constructors and physical occurrences before these helpers are used by a standard factory.

The existing Common described-record quantity composer preserves its original
three-phase defaults. A multi-read recipe may explicitly add metadata and
target-phase Grant occurrences without reducing either original count. The
original control quantity retains each additional returned Grant; its signing
workspace remains sequential on that same frame. This inherits the existing
per-checked-row control envelope, including its conservative member-metadata
bound. The quantities do not claim exact allocation or new authority. A target
decoder selected to run inside its physical child additionally carries its
complete private workspace there until the existing projection-complete cut;
body/result retention and failed/pending cleanup responsibility remain.
- Extension: Further connector drivers may reuse the common named read slots and synchronous projection boundary while retaining their own Native request/response meaning. Unlabelled existing recipes keep their prior selection. Named and unlabelled selection cannot mix within a phase; unsupported write/check/confirmation slots and resource substitution are refused.
- Verification: Focused tests exercise the actual recipe parser and caller functions with explicit physical ports, complete Native request/target projection, independent request identity preimages, cold reconstruction, schema/current/cancellation refusal and original Account response interleavings. Row-driver tests additionally cover original metadata/target grant separation, denied metadata, exact single send, unclassified reply loss, complete approved value/target/dispatch/claim correspondence on pure recovery, original Checkpoint fact selection and captured-method reentry. Compatibility with an immutable prior runtime remains distinct from a matching new normal installation, real Credential/Account/Ledger, TLS, public approval, provider updates and Saved execution.

The standard installed Effect profile names an absolute `sourceProfilePath` and
a nonempty `writes` list. Each write selects one original resource, distinct
fields, and an existing writable string `markerProperty` outside those business
fields. Loading uses the same full Source metadata constructor and declaration,
then the same-parent Native Mapping/Environment preparation. No provider
property is created. The original request constructor validates the marker
against the complete Catalog before any update can be sent.

The installed factory opens the shared original Row Site without caller-supplied
credential implementation bounds. The Host selects the existing Common policy
once on its same Effect constructor; the factory retains its Account/context and physical cleanup, and
installs the original driver plus one UPDATE recipe through the existing
constructor owner. Site and generation digests bind current Site/context,
runtime, metadata, full Environment, mappings and marker configuration. The
Target inventory delegates semantic/current selection to the existing Common
owner and binds every original member independently to its physical read tuple.
No metadata read or equal JSON replaces a Checkpoint decision/current proof.
Registration and source/component tests are separate from matching normal
software, TLS approval/update, Saved recovery and physical cleanup acceptance.

Host-owned `queryAliases` in the referenced Source profile are checked and
separated by the existing `splitSourceAliasProfile` owner before the connector's
closed provider-profile validator runs. Their exact immutable DATA remains in
the Effect identity; empty alias metadata has the same omission semantics as
the standard Source. The existing JSON configuration reader's complete
checked-profile/split/identity envelope funds this path. No alias is a current
namespace proof or a permission, and the full provider validation still runs.
