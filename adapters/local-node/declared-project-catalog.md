# Declared project catalog installation

## Responsibility

`declared-project-catalog.mjs` projects explicitly selected model declarations
into the existing generic declared-file installation. Common admits the
original catalog and owns native relation declarations, schema identities,
Mappings and File contracts. This adapter validates its closed metadata shapes,
derives their declared File facts and connects each constructor to the original
Source initialization owner. It does not infer a model from sample rows, names
or Tasks, acquire fixture data, issue capabilities or execute an Effect.

## Inputs and outputs

The loader receives the original runtime, directory and selected catalog/data
locators, admitted connections, currentness callback and, for installed use,
the actual installation inventory and original connection wrapper. The wrapper
must contain the exact supplied connections original. Installed catalog bytes
come from that inventory's bounded strict UTF-8 metadata reader. Catalog native
admission is separately quoted before the original parser runs.

Each returned source retains its exact `sourceMember`, `sourcePrepared`, and,
when writable, `effectMember` and `effectPrepared`. The final native declaration,
already-owned export wire, physical declaration originals, checked Mapping
bodies, File bindings and alias descriptors are borrowed from the funded stages.
No independently parsed Environment or reconstructed Mapping is supplied in
place of those original prepared tuples. The no-inventory route is an explicit
non-installed declaration diagnostic; runtime installers require the real
members and never select that route as a funding fallback.

Query aliases may carry an explicit `request` JSON object. Its admitted parsed
reference remains deeply frozen and is forwarded as literal DATA. Omission and
an explicit empty object remain distinct; no fields or null defaults are added.
The existing Request checker retains responsibility for required fields, types
and keyed/static conflicts. These values grant no parameter, binding, Source or
Effect authority.

Installed `loadDeclaredProjectCatalog` requires the actual nominal inventory.
Metadata-only `inspectDeclaredProjectCatalog` is a separately named entrance
sharing the private projection implementation, not an omitted-inventory mode of
the installed API. Inspection produces no issued Source/Effect member or
prepared installation tuple, and cannot enter physical factories.

## Identity

Connection selection scans the bounded admitted collection to obtain the exact
configured index. Catalog order and connection order may differ. The logical
Catalog/SourceRef `connectorId` is the connection name; its configured provider
is separate DATA. The scope CID hashes both domains separately: `connection`
uses the connection name, `connector` uses the configured provider namespace.
The exact catalog original and resolved data locator also participate. Equal
provider names do not merge two logical connection namespaces or original
Source contexts.

The physical supplier registration is `declared_file/0.1`; an explicit physical
schema override has the independent `declared_file_data/0.1` declaration. File
facts use the carrier schema CIDs exported by their actual initial native
declaration. A final declaration, a physical override and an initial File
restoration remain distinct originals even when some exported values agree.

## Ownership

The inventory's metadata reader and all connection-specific contexts belong to
the same already-existing installed Source material. Entry, scope, File facts,
physical override payloads and native intermediate projections use the source
member's `prepareNativeInput`. That method retains each original projection and
result without installing it as the final prepared tuple.

All physical override restores precede final source preparation, which closes
that context's native-input entrance. The effect prepares its Mapping inputs
before borrowing the same source declaration, then uses the existing generic
Mapping/Environment owner. Final aggregate descriptors use the original
metadata projection owner, which remains available after final declaration
preparation; they do not acquire a new Resource or consume a provider read slot.
Physical Site and reader custody starts later in the actual factory owners.

## Synchronization

Declaration and connection runtime methods are captured before asynchronous reads. Currentness is checked
before and after catalog reading and after each completed source descriptor;
the inventory and contexts perform their own currentness and original-material
checks around admission and reservation.

For each connection the sequence is: begin the actual source member; reserve
raw JSON parsing and recursive freezing before inspecting the entry; reserve
projection from that immutable entry; reserve scope hashing and a separate
saved-view serialization with its parallel native input arrays. For File
bindings only, reserve the initial native restore and export, then separately
reserve returned-wire parsing/freezing, File-fact construction into copied
saved records, and final saved-view serialization. Preserve the original frozen
records rather than mutating them. Then reserve
physical override payloads and each actual native override; prepare the final
native declaration once. Ordinary relations omit the initial File restore.
An effect then begins its original context, constructs its reserved UPDATE
inputs, borrows the source declaration and prepares its checked Mappings.
The final descriptor stage receives the existing Mapping records directly,
without an earlier projection array or a second declaration export.

## Failure

Missing, extra or duplicate connections, malformed closed metadata, duplicate
aliases/resources, invalid File bindings and unsupported writable shapes
refuse before fixture acquisition. Common independently refuses invalid schema
or Mapping semantics. Missing native quantities refuse before restore or export;
there is no guessed allowance, direct installed Mapping fallback or late
reservation after construction.

Each stage's completed originals and failed prefix remain retained by the same
material. A thrown parser, native restore, Mapping or currentness failure is
propagated to the enclosing installation failure path. The inventory retains
earlier contexts and joins active construction before cleanup. This loader
does not manufacture successful adapters to finish metadata-only contexts or
claim that a later physical cleanup has completed.

## Cancellation

The loader has no separate cancellation or retry owner. Currentness refusal
stops further projection; enclosing installed startup invokes the inventory's
failure path. An interrupted read retains its actual configuration-reader close
obligation. Refusal is not proof of stopped physical work. Neither a changed
locator nor a newly created projection permits replacing an already-failed
installation's original context.

## Resources

The parse, projection, saved-input, Scope, FileFacts, PhysicalOverrides,
MappingInputs and FinalDescriptors recipes describe pure JS retained/workspace
overlap. The parse recipe scans borrowed original Strings before parsing. Later
recipes scan already-funded immutable JSON originals, actual selected schemas,
CID Strings and descriptor counts without parsing, hashing or serializing input
to measure its budget. Every successful and failed construction peak remains
retained under the same original material; this staging neither raises its
normal capacity limit nor assumes scratch lifetime has ended.
The existing source-construction capacity API converts those recipes before
`prepareNativeInput` or metadata preparation invokes the constructor.

Each native restore quote receives the exact saved-view wire plus its seven
parallel resource/kind/schema/request/facts/acquisition/identity arrays. That
quantity covers that invocation's restore and export. The final installed
export is performed by `prepareNativeDeclaration` and its returned wire is
reused. Initial File and physical override exports are each performed once
inside their own reserved input projection.

Connection lookup uses bounded scalar scans instead of an unfunded index Map.
The physical override stage constructs one quoted Map and later replaces its
existing values with restored originals. Final descriptors borrow the original
Mapping array and native wires. No native quote is credited for these JS
containers. Counts come from funded validated metadata, not fixture row counts,
provider labels or invented capacity limits. The current Effect adapter admits
one writable target; that explicit adapter constraint is not a general language
restriction.

## Extension

New models change declarations and separately replaceable sample data. No
business-specific source, hardcoded connection vocabulary, per-example Runtime
or selected-entry fabrication belongs here. Additional physical representations
or writable operations must have explicit model metadata, existing Common
semantic admission, corresponding pre-constructor quantities and the same
Source/Effect identity and ownership boundaries. A new profile label cannot
confer Account authority, Source read permission or Effect approval.

## Verification

`declared-project-catalog.actual.test.mjs` exercises real Common declaration,
File and Mapping semantics with explicit non-installed metadata diagnostics and
replacement data. These tests do not establish installed resource funding or a
packaged runtime workflow. They use an explicitly selected matching compiled
runtime rather than treating a source hash as execution evidence.

The staged catalog cases in `declared-file-installation.test.mjs` use the real
nominal inventory, Project registry, initialization contexts and Row Source
factory with explicit Common/resource fixtures. They check reversed connection
order, distinct same-provider namespaces, exact source/effect tuple references,
independent native restore/export counts, generic UPDATE selection, missing
quotes, reservation refusal before constructors and entry parsing, failed-prefix
cleanup and NativeInput separation from final preparation. Their fixture quotes
do not prove production quantity sufficiency. The geometry owner's tests cover
the declared JS constructor recipes; full installed Source/Content/Effect,
Account, cross-target and actual-package acceptance remain separate checks.
